IP, DNS & SSL

Pilns iesācēja ceļvedis: kas ir IP adrese, DNS un SSL, un ko darīt, kad kaut kas nestrādā — katrai tēmai pilns skaidrojums un komandas, ko var iekopēt un uzreiz palaist.

Kur meklēt vainīgo

Kad pārlūkā parādās kļūda, pirmais un svarīgākais solis ir noskaidrot, kurā slānī problēma radusies — jo katrs slānis prasa pavisam citu risinājumu. Ceļš no domēna ieraksta līdz redzamai vietnei iet cauri četriem posmiem: (1) DNS — domēns jāpārvērš IP adresē; (2) savienojums — pārlūkam jāizveido tīkla savienojums ar šo IP; (3) šifrēšana (TLS/SSL) — jāizveido drošs kanāls; (4) serveris/aplikācija — serverim jāatgriež pati lapa. Kļūdas ziņojums parasti pasaka, kurā no šiem posmiem process apstājās.

DNS_PROBE_FINISHED_NXDOMAIN

Domēns vispār neeksistē DNS acīs — apstājās posmā (1).

CONNECTION_REFUSED / TIMED_OUT

Serveris nesasniedzams vai neatbild — apstājās posmā (2).

SSL_PROTOCOL_ERROR / CERT_*

Problēma ar HTTPS/sertifikātu — apstājās posmā (3).

502 / 503 / 504

Serveris strādā, bet backend — nē — apstājās posmā (4).

DNS_PROBE_FINISHED_NXDOMAIN

Šī Chrome/Edge kļūda nozīmē, ka pārlūks mēģināja izšķirt (atrisināt) domēnu, taču DNS sistēma atbildēja, ka tāda domēna vispār nav (NXDOMAIN = "Non-Existent Domain"). Svarīgi saprast: tā nav servera problēma — process apstājās vēl pirms pārlūks vispār mēģināja pieslēgties jebkuram serverim, tāpēc servera pusē neko labot nevar, kamēr nav atrisināts pats DNS ieraksts.

📅 Domēns nav reģistrēts / beidzies

Reģistrācijas termiņš beidzies vai domēns vēl nemaz nav iegādāts.

⏳ DNS vēl nav iestatīts

Jaunam domēnam/serverim A/NS ieraksti vēl nav pievienoti vai nav propagējušies.

✏️ Pareizrakstības kļūda

Pārbaudi, vai domēna nosaukums ierakstīts pareizi — pārsteidzoši bieži tas ir vainīgais.

💻 Lokāla DNS/hosts problēma

Vecs kešotais ieraksts vai nepareiza rinda operētājsistēmas hosts failā.

Ieteicamā diagnostikas secība — izpildi terminālī (Windows: CMD vai PowerShell; Mac/Linux: Terminal) pēc kārtas, nomainot piemers.lv uz savu domēnu:

bash# 1. Vai domēns vispār reģistrēts un derīgs
whois piemers.lv

# 2. Vai domēnam iestatīti nameserveri
dig piemers.lv NS

# 3. Vai eksistē A ieraksts (IP adrese)
dig piemers.lv A

# 4. Pamēģini citu DNS resolveri, lai izslēgtu sava ISP problēmu
dig @8.8.8.8 piemers.lv

# 5. Notīri lokālo DNS kešu (Windows)
ipconfig /flushdns

Ja 4. solī, vaicājot tieši Google publiskajam resolverim (8.8.8.8), joprojām nav atbildes — problēma nav tavā datorā vai internetā, tā ir pašā domēna DNS konfigurācijā (jāgaida propagācija vai jāpārbauda ieraksti pie reģistrētāja).

Ja dig/nslookup no cita tīkla vai ierīces (piem., telefona ar mobilo internetu, nevis WiFi) arī nerāda nekādu ierakstu, tas apstiprina, ka problēma ir DNS/servera pusē, nevis tavā konkrētajā datorā.

Hosts fails (ātrais labojums)

Ja zini servera IP adresi, bet DNS vēl nestrādā (piemēram, gaidi propagāciju vai domēns vēl nav pievienots), vari "piespiest" savu datoru izmantot konkrēto IP šim domēnam, apejot DNS pilnībā. Šis paņēmiens maina rezultātu tikai tavā datorā — neviens cits apmeklētājs neko neredzēs savādāk, un tas nekādi neietekmē reālo DNS vai serveri.

Windows soļi:

cmd1. Nospied Windows taustiņu, ieraksti "cmd", labais klikšķis uz "Command Prompt" → "Run as administrator"
2. Ievadi šo komandu, lai atvērtu hosts failu Notepad:
notepad C:\Windows\System32\drivers\etc\hosts

3. Faila pašās beigās pievieno rindu (nomaini uz savu IP un domēnu):
81.198.171.19   piemers.lv

4. Saglabā (Ctrl+S), tad notīri DNS kešu un pārbaudi:
ipconfig /flushdns

Mac/Linux soļi:

bash# Atver hosts failu ar redaktoru (sudo, jo fails ir aizsargāts)
sudo nano /etc/hosts

# Pievieno tajā pašā formātā, saglabā ar Ctrl+O, iziet ar Ctrl+X
81.198.171.19   piemers.lv

Pēc saglabāšanas atver pārlūku un ej uz http://piemers.lv — pārlūkam tagad vajadzētu doties tieši uz norādīto IP, apejot DNS vaicājumu pavisam.

"Access is denied" saglabājot? Notepad nav atvērts kā administrators — aizver to un atkārto no 1. soļa. Redzi hostinga paneļa lapu, nevis savu vietni? Tas ir sagaidāms un normāls nākamais solis — skat. "Redzu paneļa sveiciena lapu" zemāk. Kad testēšana pabeigta, neaizmirsti izdzēst pievienoto rindu — pretējā gadījumā pēc mēnešiem var rasties mulsinoša situācija, kad tavā datorā vietne izskatās savādāk nekā visiem citiem.

CONNECTION_REFUSED / TIMED_OUT

Abas šīs kļūdas nozīmē, ka DNS jau ir atrisinājies veiksmīgi (domēns pareizi noved pie IP adreses), bet neizdodas izveidot tīkla savienojumu ar pašu serveri. Atšķirība ir kā tieši tas neizdodas:

🚫 REFUSED

Serveris aktīvi atsaka savienojumu — atbild uzreiz ar "nē". Cēlonis: pakalpojums (Nginx/Apache) nav palaists, vai neviens serviss neklausās uz šī porta.

⏱️ TIMED_OUT

Pieprasījums pazūd klusumā — pārlūks gaida un beidzot padodas. Cēlonis: ugunsmūris/drošības grupa klusi nomet paketes, vai IP adrese ir nepareiza/vairs neaktīva.

Diagnostikas komandas (izpildi serverī pa SSH vai attālināti no sava datora):

bash# Serverī — vai serviss vispār darbojas un klausās
sudo systemctl status nginx
sudo ss -tulpn | grep :443

# No sava datora — vai ports vispār sasniedzams no ārpuses
telnet piemers.lv 443

Ja ss serverī rāda, ka serviss klausās uz porta, bet telnet no ārpuses "karājas" vai atsaka — problēma ir ugunsmūrī starp tevi un serveri (servera OS ugunsmūris ar ufw/iptables, vai mākoņa nodrošinātāja drošības grupas noteikumi — pēdējais ir bieži aizmirsta vieta, jo tas atrodas ārpus paša servera konfigurācijas).

SSL kļūdas

ERR_SSL_PROTOCOL_ERROR parādās, kad TCP savienojums ar serveri izveidojas veiksmīgi, bet TLS "sarunas" (handshake, skat. zemāk) neizdodas pabeigt. Biežākais iemesls — pārlūks mēģina runāt HTTPS ar portu vai servisu, kas TLS vispār nesatur (piem., serveris klausās tikai uz parastā HTTP porta 80).

🔌 Nepareizs ports

HTTPS mēģina savienoties ar portu, kur serveris runā tikai parasto HTTP.

🧓 Novecojis TLS

Serveris atbalsta tikai novecojušas, jau izslēgtas TLS versijas.

🔀 Reverse proxy konflikts

Cloudflare/Nginx priekšā sagaida HTTPS, bet backend serveris to nenodrošina.

Ja kļūda saistīta ar paša sertifikāta saturu (NET::ERR_CERT_COMMON_NAME_INVALID — domēns nesakrīt; ERR_CERT_AUTHORITY_INVALID — neuzticams izdevējs; ERR_CERT_DATE_INVALID — beidzies), risinājums aprakstīts sadaļā "Sertifikāti īsumā" zemāk. Ātrai pārbaudei, ko tieši serveris atbild:

bashecho | openssl s_client -connect piemers.lv:443 -servername piemers.lv 2>/dev/null | openssl x509 -noout -dates -subject

Šī komanda parāda sertifikāta derīguma termiņu un to, kuram domēnam sertifikāts izsniegts — ja domēns šeit nesakrīt ar to, kuru apmeklē pārlūkā, tas ir tieši cēlonis.

TOO_MANY_REDIRECTS

Šī kļūda nozīmē, ka vietne novirza pati uz sevi bezgalīgā ciklā — pārlūks pēc noteikta skaita pāradresāciju (parasti ap 20) padodas un parāda kļūdu, nevis mēģina bezgalīgi.

⚙️ WordPress Address/Site Address

Iestatījumos viens ir http://, otrs https:// — WordPress mēģina pastāvīgi "izlabot" adresi, radot ciklu.

☁️ Cloudflare "Flexible" SSL

Cloudflare sūta pieprasījumu serverim pa HTTP, bet serveris pats piespiedu kārtā novirza atpakaļ uz HTTPS — Cloudflare to atkal pārtver un cikls turpinās. Risinājums: Cloudflare panelī pārslēgt SSL/TLS režīmu uz "Full" vai "Full (strict)".

📄 .htaccess redirect cikls

Pretrunīgi vai pārklājoši RewriteRule noteikumi, kas piespiedu kārtā novirza uz HTTPS, paši sevi "ķeksē" bezgalīgi.

Pirmais solis diagnostikai — pārbaudi, cik reižu un uz kurieni notiek pāradresācija:

bashcurl -IL https://piemers.lv

-I parāda tikai galvenes (bez satura), -L seko pāradresācijām — izvadā redzēsi katru soli (301/302 un Location: galveni), kas parāda tieši, kur cikls sākas atkārtoties.

502 / 503 / 504

Šīs kļūdas nozīmē, ka pats serveris ir sasniedzams (DNS un savienojums strādā), bet kaut kas nogāja greizi tālāk — parasti backend (PHP-FPM, Node.js process, datubāze) līmenī, nevis pašā tīkla savienojumā.

502 Bad Gateway

Reverse proxy (Nginx) nesaņem derīgu atbildi no backend — visbiežāk nokritis PHP-FPM vai app process.

503 Service Unavailable

Serveris pārslogots (pārāk daudz vienlaicīgu pieprasījumu) vai apzināti pārslēgts uzturēšanas režīmā.

504 Gateway Timeout

Backend atbild pārāk lēni — smags datubāzes vaicājums, bezgalīga cilpa kodā vai resursu (RAM/CPU) trūkums.

Precīzu iemeslu gandrīz vienmēr atklāj servera žurnāli — pieslēdzies pa SSH un skaties tos tiešraidē, kamēr atsvaidzini lapu pārlūkā:

bash# Nginx kļūdu žurnāls tiešraidē
sudo tail -f /var/log/nginx/error.log

# PHP-FPM statuss — vai process vispār darbojas
sudo systemctl status php8.1-fpm

Redzu hostinga paneļa sveiciena lapu, nevis savu vietni

Bieži sastopams scenārijs: domēns (vai hosts failā pievienots ieraksts) pareizi ved uz servera IP, pārlūks veiksmīgi izveido savienojumu — taču tā vietā, lai redzētu paredzēto vietni, parādās hostinga vadības paneļa (VestaCP, cPanel, Plesk) noklusējuma "Welcome" lapa, dažkārt ar 301 pāradresāciju uz kaut ko līdzīgu vps-1.piemers.lv.

Pareizs IP ≠ pareiza vietne. Viens fizisks serveris var apkalpot desmitiem dažādu domēnu vienlaikus. Kuru tieši vietni rādīt konkrētam pieprasījumam, tīmekļa serveris (Apache/Nginx) izvēlas pēc pieprasījuma Host galvenes — to sauc par virtual host mehānismu. Ja šim konkrētajam domēnam serverī vēl nav izveidots atbilstošs ieraksts, serveris vienkārši parāda savu noklusējuma (paneļa) vietni.

Risinājuma soļi:

text1. Pieslēdzies hostinga vadības panelim (VestaCP/cPanel/Plesk) pārlūkā
2. Atrodi sadaļu domēnu/Web Domain pārvaldībai
3. Izveido/pievieno šo konkrēto domēnu kā "Web Domain" tieši šajā kontā
4. Pārliecinies, ka domēna DocumentRoot norāda uz pareizo mapi ar vietnes failiem
5. Saglabā izmaiņas un atsvaidzini vietni pārlūkā — efekts parasti redzams uzreiz

HTTP statusa kodi

Katra servera atbilde nāk kopā ar trīsciparu kodu, kas pasaka, kas tieši notika — pārlūks (un izstrādātāja rīki) to izmanto, lai izlemtu, kā rīkoties tālāk (rādīt lapu, sekot pāradresācijai, parādīt kļūdu).

text200 OK                    → pieprasījums izdevās, šeit ir saturs
301 Moved Permanently     → resurss pastāvīgi pārvietots (piem., http → https)
302 Found                 → pagaidu pāradresācija
403 Forbidden             → serveris saprot pieprasījumu, bet atsaka piekļuvi
404 Not Found             → šāda adrese/lapa neeksistē
500 Internal Server Error → neapstrādāta kļūda servera/aplikācijas kodā

Kodu var pārbaudīt tieši no komandrindas, neatverot pārlūku — ērti, lai ātri pārbaudītu, ko serveris atbild:

bashcurl -I https://piemers.lv
# Pirmā izvada rinda būs, piem.: HTTP/2 200

CORS kļūda

CORS (Cross-Origin Resource Sharing) kļūda parādās pārlūka konsolē, kad lapā ielādēts JavaScript no viena domēna (piem., mana-app.lv) mēģina ar fetch() piekļūt datiem no cita domēna (piem., api.citssrverits.lv), un tas serveris skaidri nav atļāvis šādus pieprasījumus. Tas ir pārlūka iebūvēts drošības mehānisms, kas pasargā lietotājus no ļaunprātīgas datu nolasīšanas starp vietnēm.

Kļūda konsolē parasti izskatās aptuveni šādi:

textAccess to fetch at 'https://api.citssrverits.lv/dati' from origin
'https://mana-app.lv' has been blocked by CORS policy: No
'Access-Control-Allow-Origin' header is present on the requested resource.

Risinājums vienmēr ir servera pusē (tajā serverī, no kura tiek prasīti dati) — tas jāpaziņo, kuriem domēniem drīkst piekļūt. Ar Node.js/Express to izdara šādi:

js// Servera (Express) kodā
app.use((req, res, next) => {
  res.setHeader('Access-Control-Allow-Origin', 'https://mana-app.lv');
  next();
});

CORS kļūdu nevar apiet, mainot kodu pārlūka pusē (klienta JavaScript) — tas ir apzināti tā izveidots, lai tikai servera īpašnieks varētu atļaut piekļuvi. Ja tas nav "tavs" API, jāsazinās ar tā uzturētāju.

Kas ir IP adrese

Katrai ierīcei, kas ir tieši pieejama internetā, ir sava unikāla adrese — līdzīgi kā mājas adrese pasta piegādei. Visizplatītākais formāts ir IPv4 — četri skaitļi no 0 līdz 255, atdalīti ar punktiem, piemēram, 81.198.171.19. Domēns (piemers.lv) ir tikai cilvēkam ērtāks vārds šai adresei — DNS (skat. zemāk) tos savieno.

Tā kā IPv4 adrešu skaits (~4.3 miljardi) ir izsīcis, ieviests jaunāks formāts IPv6 ar praktiski neierobežotu apjomu — piemēram, 2a02:6b8::1. Ir arī adreses, kas strādā tikai vietējā tīklā, nevis internetā, piem. 192.168.1.1 (tipiska mājas rūtera adrese) vai 127.0.0.1 (adrese, ar kuru dators "runā pats ar sevi" — noder lokālai izstrādei).

bash# Uzzini savu publisko IP adresi (ar kuru tevi redz internets)
curl ifconfig.me

Porti

Viena IP adrese var apkalpot vairākus pakalpojumus vienlaikus — ports (skaitlis no 0 līdz 65535) pasaka, kuram tieši pakalpojumam serverī adresēts konkrētais pieprasījums. Ja IP adrese ir kā mājas adrese, ports ir kā konkrēta dzīvokļa numurs tajā mājā.

text80    → HTTP  (parastā, nešifrētā tīmekļa satiksme)
443   → HTTPS (šifrētā tīmekļa satiksme)
22    → SSH   (drošs attālinātais pieslēgums serverim)
3306  → MySQL (datubāzes savienojumi)

Adresējot vietni pārlūkā parasti portu neraksta, jo http:// noklusēti nozīmē 80, bet https:// — 443. Citiem servisiem to bieži norāda skaidri, piem. piemers.lv:8080.

Kas ir DNS

DNS (Domain Name System) ir sadalīta, hierarhiska "tālruņu grāmata" internetam — tā pārvērš cilvēkam ērtu domēna vārdu (piemers.lv) par IP adresi, kuru pārlūks tehniski var izmantot savienojuma izveidei.

Kad pārlūkā ieraksti adresi, notiek aptuveni šāda secība: pārlūks vaicā DNS resolverim (parasti interneta pakalpojumu sniedzēja vai publiskam, piem. 8.8.8.8) → resolvers vaicā root serveriem → tie norāda uz attiecīgā domēna zonas (.lv) serveriem → tie norāda uz domēna paša autoritatīvajiem nameserveriem → tie beidzot atbild ar konkrētu IP adresi. Rezultāts tiek kešots uz noteiktu laiku (TTL, Time To Live), lai nevajadzētu atkārtot visu ceļu katru reizi — tieši tāpēc DNS izmaiņas var kļūt redzamas ne uzreiz visiem, bet dažu minūšu līdz pat 48 stundu laikā ("propagācija").

bashdig piemers.lv +short
# izvada tikai IP adresi, piem.: 81.198.171.19

DNS ieraksti (A, CNAME, MX...)

Domēnam pieder vairāki dažāda tipa ieraksti — katrs pasaka DNS sistēmai kaut ko citu par šo domēnu:

textA       → domēns ved uz konkrētu IPv4 adresi
AAAA    → tas pats, bet IPv6 adresei
CNAME   → alias uz citu domēnu (piem. www → piemers.lv)
MX      → kurš serveris apstrādā šī domēna e-pastu
TXT     → brīvs teksts (bieži domēna verifikācijai vai SPF e-pasta drošībai)
NS      → kurš serveris ir "atbildīgais" (autoritatīvais) par šo domēnu

Piemērs, kā šie ieraksti izskatās domēna DNS zonas iestatījumos:

textpiemers.lv.       A       81.198.171.19
piemers.lv.       MX  10  mail.piemers.lv.
www.piemers.lv.   CNAME   piemers.lv.

Konkrētu ieraksta tipu var pārbaudīt atsevišķi:

bashdig piemers.lv MX
dig piemers.lv TXT

www vs bez-www

Tehniski piemers.lv un www.piemers.lv ir divas dažādas adreses DNS acīs, kaut arī cilvēkam tās šķiet vienādas. Vēsturiski www apzīmēja "World Wide Web" servisu atsevišķi no citiem tā paša domēna servisiem (piem., e-pasta). Mūsdienās izvēle, kuru versiju darīt par "galveno", ir tikai stila jautājums — abas parasti tiek sasaistītas, lai vietne strādātu neatkarīgi no tā, kā apmeklētājs to ieraksta.

Praksē to panāk ar CNAME ierakstu un pāradresāciju, piemēram:

textwww.piemers.lv.   CNAME   piemers.lv.

Un servera pusē (piem., Nginx) pievieno noteikumu, kas www versiju pāradresē uz galveno (vai otrādi) ar 301 (pastāvīgu) pāradresāciju, lai meklētājprogrammas neuzskatītu abas versijas par diviem atsevišķiem, dublētiem saturiem.

CDN īsumā

CDN (Content Delivery Network, piem. Cloudflare, Fastly) ir tīkls no serveriem, kas izvietoti dažādās pasaules vietās un glabā vietnes satura kopijas. Kad apmeklētājs atver vietni, viņu apkalpo ģeogrāfiski tuvākais CDN serveris, nevis vienmēr tas pats oriģinālais serveris — tas ievērojami paātrina lapas ielādi, īpaši apmeklētājiem, kas atrodas tālu no oriģinālā servera.

Blakusefekts, kas iesācējus bieži mulsina: kad domēns ir "aiz" CDN, DNS uzziņas (dig) parāda CDN servera IP adresi, nevis īsto vietnes servera IP — tas apzināti tā, lai īstā servera adrese paliktu paslēpta un aizsargāta no tiešiem uzbrukumiem.

Kas ir SSL/HTTPS

SSL (Secure Sockets Layer) un tā mūsdienu, drošāks pēctecis TLS (Transport Layer Security) ir protokoli, kas šifrē datu plūsmu starp pārlūku un serveri, lai neviens pa vidu (piem., tajā pašā publiskajā WiFi tīklā) nevarētu to nolasīt vai klusi izmainīt. HTTPS = HTTP + šis šifrējums. Ikdienā termins "SSL" joprojām tiek lietots, kaut arī tehniski visur jau strādā TLS.

Process, kā pārlūks un serveris vienojas par šifrēšanu, saucas TLS handshake: pārlūks piedāvā atbalstītās TLS versijas → serveris atbild ar savu sertifikātu → pārlūks pārbauda sertifikātu (izsniedzējs, derīgums, domēns) → abas puses vienojas par kopīgu, sesijai unikālu šifrēšanas atslēgu → sākas šifrēta saziņa.

Bez HTTPS pārlūki atzīmē vietni kā "Nedrošu", paroļu lauki tiek īpaši brīdināti, un Google to izmanto arī kā ranžēšanas faktoru — mūsdienās HTTPS ir obligāts minimums jebkurai publiskai vietnei.

Sertifikāti īsumā

SSL/TLS sertifikātu izsniedz uzticama iestāde — Sertifikācijas iestāde (Certificate Authority, CA), kurai pārlūki un operētājsistēmas jau uzticas "no rūpnīcas". Populārākā un bezmaksas — Let's Encrypt, kas sertifikātus izsniedz automatizēti. Sertifikāts apliecina, ka vietne, ar kuru sazinies, tiešām pieder norādītajam domēnam.

Let's Encrypt sertifikāti derīgi tikai 90 dienas — apzināti īss termiņš, lai piespiestu automatizēt atjaunošanu, nevis paļauties uz manuālu atcerēšanos. Rīks certbot to iestata automātiski:

bash# Uzstāda certbot (Ubuntu/Debian serverim ar Nginx)
sudo apt install certbot python3-certbot-nginx

# Iegūst un automātiski konfigurē sertifikātu konkrētam domēnam
sudo certbot --nginx -d piemers.lv -d www.piemers.lv

# Pārbauda, vai automātiskā atjaunošana strādās (nemaina neko reāli)
sudo certbot renew --dry-run

Ja pēc uzstādīšanas jāpārbauda, kas tieši ir instalēts un cik ilgi tas vēl derīgs:

bashecho | openssl s_client -connect piemers.lv:443 2>/dev/null | openssl x509 -noout -dates

Šī komanda izvadīs divas rindas — notBefore (kopš kura brīža sertifikāts derīgs) un notAfter (kad tas beidzas).

Noderīgas komandas

Kopsavilkums — visas komandas, kas parādījās šajā lapā, vienuviet ātrai uzziņai. Visas darbojas jebkura moderna operētājsistēmas terminālī (Windows: CMD/PowerShell ar ipconfig, Mac/Linux ar attiecīgajiem ekvivalentiem):

bash# DNS pārbaude
nslookup piemers.lv
dig piemers.lv +short
dig piemers.lv MX
dig piemers.lv NS

# Kam pieder domēns / kad reģistrēts
whois piemers.lv

# HTTP statusa kods un pāradresācijas
curl -IL https://piemers.lv

# SSL sertifikāta pārbaude tieši no servera
echo | openssl s_client -connect piemers.lv:443 2>/dev/null | openssl x509 -noout -dates

# Vietējais DNS keša tīrīšana (Windows)
ipconfig /flushdns
