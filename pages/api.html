Sākums API

API

Pilns iesācēja ceļvedis: kas ir API, kādi ir tā veidi, kā to droši lietot un kā uzbūvēt savu - ar reāliem, darbojošos koda piemēriem, ko var iekopēt un uzreiz palaist.

Kas ir API?

API (Application Programming Interface) ir "līgums" starp divām programmām - tas apraksta, kā viena programma var pieprasīt datus vai darbību no otras, nezinot neko par to, kā otra programma iekšēji strādā. Tu izsauc noteiktu adresi ar noteiktiem parametriem un saņem atpakaļ paredzamu atbildi.

Vienkāršākā analoģija - restorāns: tu (klients) pats neej uz virtuvi gatavot ēdienu. Tu dod pasūtījumu viesmīlim (API), viesmīlis aiznes to uz virtuvi (serveris), un atnes atpakaļ gatavu ēdienu (atbilde). Tev nekad nav jāzina, KĀ virtuve strādā iekšēji - tikai jāzina, KO un KĀ pasūtīt.

🙋 Klients

Tavs kods (pārlūks, mobilā app, cits serveris) - sūta pieprasījumu.

📨 Pieprasījums

Adrese + metode + (dažreiz) dati - kas tieši jāizdara.

🖥️ Serveris

Apstrādā pieprasījumu, piekļūst datubāzei vai citai loģikai.

📬 Atbilde

Dati (parasti JSON) vai apstiprinājums, ka darbība izdevās.

Web izstrādē visbiežāk sastopamais API tips ir Web API - tas strādā pāri HTTP protokolam, tam pašam, ko lieto pārlūks, atverot jebkuru vietni. Tāpēc, lai saprastu API, vispirms jāsaprot HTTP pamati - nākamajā sadaļā.

API nav specifiska tehnoloģija vai valoda - tas ir jēdziens/princips. API var būt starp diviem serveriem, starp pārlūku un serveri (visbiežāk sastopamais gadījums) vai pat starp divām funkcijām vienā programmā (bibliotēkas API). Šī lapa fokusējas uz web API, ko izsauc caur internetu.

HTTP metodes & statusa kodi

Katrs web API pieprasījums izmanto HTTP metodi, kas pasaka, ko tu gribi darīt ar resursu:

MetodeNozīmePiemērs

GET, PUT un DELETE ir idempotentas - izsaucot tās vairākas reizes ar tiem pašiem datiem, rezultāts ir tāds pats kā izsaucot vienu reizi. POST nav idempotenta - divi vienādi POST /users pieprasījumi izveidos divus lietotājus. Tas svarīgi zināt, plānojot atkārtotus mēģinājumus (retry) pēc tīkla kļūdas.

JSON formāts

Gandrīz visi mūsdienu web API sūta un saņem datus JSON (JavaScript Object Notation) formātā - cilvēkam lasāms teksta formāts, kas dabiski atbilst JavaScript objektiem, bet ko saprot praktiski katra programmēšanas valoda.

json{
  "id": 5,
  "vards": "Anna",
  "aktivs": true,
  "epasts": null,
  "lomas": ["admin", "redaktors"],
  "adrese": {
    "pilseta": "Rīga",
    "indekss": "LV-1010"
  }
}

Pamata tipi: teksts pēdiņās "...", skaitļi bez pēdiņām, true/false, null (tukša vērtība), masīvi [...] un iegultie objekti {...}. Atslēgas vienmēr dubultpēdiņās - JSON, atšķirībā no JS, neatļauj vienpēdiņas vai atslēgas bez pēdiņām.

JavaScript - pārvēršana starp JS objektu un JSON tekstu:

jsconst objekts = { vards: "Anna", vecums: 25 };

// Objekts → JSON teksts (piem., lai nosūtītu API pieprasījumā)
const teksts = JSON.stringify(objekts);
// '{"vards":"Anna","vecums":25}'

// JSON teksts → JS objekts (piem., API atbildi apstrādājot)
const atpakal = JSON.parse(teksts);
console.log(atpakal.vards); // "Anna"

PHP - tas pats ar json_encode/json_decode:

php<?php
$masivs = ['vards' => 'Anna', 'vecums' => 25];

$teksts = json_encode($masivs);
// '{"vards":"Anna","vecums":25}'

// "true" otrais parametrs - atgriež PHP masīvu, nevis objektu
$atpakal = json_decode($teksts, true);
echo $atpakal['vards']; // Anna

Sūtot JSON pieprasījuma ķermenī (POST/PUT), vienmēr pievieno galveni Content-Type: application/json - bez tās serveris nezina, kā parsēt saņemto tekstu, un bieži atmet pieprasījumu ar 400 vai 415 kļūdu.

REST principi

REST (Representational State Transfer) nav tehnoloģija vai standarts, ko var "instalēt" - tas ir principu kopums, kā organizēt API, lai tas būtu paredzams un viegli saprotams. Lielākā daļa mūsdienu web API sauc sevi par "RESTful", kaut arī reti ievēro visus principus stingri.

📦 Resursi ir lietvārdi

URL apraksta LIETU (/users), nevis darbību - darbību jau pasaka HTTP metode.

🚫 Bezstāvokļa

Katrs pieprasījums satur visu nepieciešamo informāciju; serveris neatceras iepriekšējos pieprasījumus.

🔗 Vienota saskarne

Konsekventa URL un atbilžu struktūra visā API - nav pārsteigumu no endpointa uz endpointu.

🔢 Versionēšana

/api/v1/... ļauj vēlāk mainīt API, nesalaužot vecos klientus.

Prakse: URL vienmēr veido no lietvārda, HTTP metode nosaka darbību, ligzdošana apraksta piederību:

Labi (lietvārds + metode)Slikti (darbība URL)
GET /usersGET /getUsers
POST /usersPOST /createUser
DELETE /users/5POST /deleteUser?id=5
GET /users/5/ordersGET /getOrdersForUser?id=5

GET /users/5/orders - ligzdots URL, kas nolasāms kā teikums: "iegūsti lietotāja 5 pasūtījumus". Tā ir laba prakse attēlot piederību starp resursiem tieši URL struktūrā.

Pārskats: REST, GraphQL, SOAP, WebSocket, gRPC, Webhooks

"API" ir plašs jēdziens - pastāv vairāki atšķirīgi veidi, kā to realizēt. Zemāk īss pārskats, kad kuru izmantot:

🌐 REST

Visizplatītākais - HTTP + JSON, resursu-orientēts. Lielākā daļa publisko API (šajā lapā fokusējamies uz to).

🔷 GraphQL

Klients pats izvēlas, kādus laukus grib atpakaļ, vienā endpointā. Der elastīgiem frontend datu pieprasījumiem.

📄 SOAP

Vecāks, XML-balstīts, stingrs standarts. Joprojām sastopams bankās/valsts sistēmās, retāk jaunos projektos.

🔌 WebSocket

Divvirzienu, pastāvīgs savienojums reāllaika datiem - čats, live cenas, paziņojumi.

⚡ gRPC

Ātrs, binārs protokols starp serveriem (mikroservisi). Reti izmantots tieši no pārlūka.

🪝 Webhooks

"Apgrieztais API" - serveris PATS zvana tavam endpointam, kad kaut kas notiek. Pilns piemērs Stripe integrācijā.

Iesācējam gandrīz vienmēr pietiek ar REST - tas ir visizplatītākais, vienkāršākais saprast un lielākā daļa dokumentācijas/rīku ir tam veidoti. Pārējie veidi der specifiskiem gadījumiem (reāllaiks, ļoti elastīgi datu pieprasījumi), nevis kā noklusējuma izvēle.

REST API piemērs (reāls)

Lai neizgudrotu neko mākslīgu, šeit lieto JSONPlaceholder (jsonplaceholder.typicode.com) - bezmaksas, publisku testa API, kas domāts tieši mācībām. Var brīvi sūtīt pieprasījumus, nekas reāli netiek saglabāts.

GET pieprasījums terminālī (cURL):

bashcurl https://jsonplaceholder.typicode.com/posts/1

Atbilde (statuss 200 OK):

json{
  "userId": 1,
  "id": 1,
  "title": "sunt aut facere repellat...",
  "body": "quia et suscipit..."
}

POST pieprasījums - jauna ieraksta izveide (JSONPlaceholder to reāli nesaglabā, bet atgriež, it kā būtu izveidots):

bashcurl -X POST https://jsonplaceholder.typicode.com/posts \
  -H "Content-Type: application/json" \
  -d '{"title":"Mans raksts","body":"Saturs...","userId":1}'

Atbilde (statuss 201 Created, ar jaunizveidoto id):

json{
  "title": "Mans raksts",
  "body": "Saturs...",
  "userId": 1,
  "id": 101
}

Laba prakse - pirms API integrācijas savā projektā vienmēr vispirms izmēģini to terminālī ar cURL vai Postman (skat. Testēšana), lai zinātu, kāda tieši ir atbilde, pirms raksti kodu, kas to apstrādā.

GraphQL

REST problēma: dažreiz endpoints atgriež pārāk daudz datu (over-fetching) vai pārāk maz, liekot taisīt vairākus secīgus pieprasījumus (under-fetching). GraphQL to risina - klients pats apraksta, tieši kādus laukus grib, vienā pieprasījumā, uz vienu endpointu.

Piemērs ar publisku GraphQL testa API (countries.trevorblades.com) - pieprasa TIKAI nosaukumu un galvaspilsētu, neko vairāk:

graphql{
  country(code: "LV") {
    name
    capital
    currency
  }
}

Atbilde satur tikai pieprasītos laukus, neko lieku:

json{
  "data": {
    "country": {
      "name": "Latvia",
      "capital": "Riga",
      "currency": "EUR"
    }
  }
}

WebSocket (reāllaika)

REST un GraphQL abi strādā pēc "pieprasījums → atbilde" principa - klients vienmēr sāk sarunu. Bet ko darīt, ja serverim jāpaziņo klientam uzreiz, kad kaut kas notiek (jauna čata ziņa, cenas izmaiņa), bez klienta jautāšanas ik pēc pāris sekundēm (polling)? Tur der WebSocket - pastāvīgs, divvirzienu savienojums, kas paliek atvērts.

Piemērs ar publisku, bezmaksas echo testa serveri (viss, ko nosūti, atnāk atpakaļ nemainīts):

jsconst soks = new WebSocket('wss://echo.websocket.org');

soks.onopen = function () {
    console.log('Savienojums atvērts');
    soks.send('Sveiks, serveri!');
};

soks.onmessage = function (notikums) {
    console.log('Saņemts:', notikums.data);
};

soks.onerror = function (kluda) {
    console.error('WebSocket kļūda:', kluda);
};

soks.onclose = function () {
    console.log('Savienojums aizvērts');
};

"Polling" (parasts fetch() ik pēc N sekundēm) ir vienkāršāk implementēt un pietiek lielākajai daļai gadījumu. WebSocket ir efektīvāks augstas biežuma datiem, bet sarežģītāk uzturēt - jārisina savienojuma pārtraukumi (onclose) un atkārtota pieslēgšanās (reconnect). Sāc ar polling un pāriet uz WebSocket tikai, ja reāli jūti nepieciešamību.

Autentifikācija - API atslēgas, Bearer, OAuth 2.0, JWT

Lielākā daļa API pieprasa pierādīt, kas tu esi, pirms atļauj piekļuvi datiem. Pastāv vairāki veidi, kā to izdarīt:

MetodeKā strādāPiemērs

Basic AuthLietotājvārds:parole, base64 kodētsAuthorization: Basic dXNlcjpwYXNz
Bearer TokenToken, kas iegūts pēc pieteikšanās, sūta katrā pieprasījumāAuthorization: Bearer eyJhbGc...
OAuth 2.0Lietotājs piekrīt trešajai pusei piekļūt saviem datiem bez paroles nodošanas"Pierakstīties ar Google" poga
JWTPašpietiekams token ar iekodētu info, pārbaudāms bez datubāzesBieži lietots kopā ar Bearer

Praksē visbiežāk sastopamais gadījums - Bearer token, ko pievieno Authorization galvenei:

jsconst atbilde = await fetch('https://api.piemers.lv/mani-dati', {
    headers: {
        'Authorization': `Bearer ${tavsTokens}`
    }
});

Nekad neieliec slepenu API atslēgu tieši frontend JS kodā, kas nonāk pārlūkā - jebkurš var to nokopēt no lapas avota (View Source / DevTools). Slepenas atslēgas glabā serverī (piem., wp-config.php, kā jebkurā citā šīs dokumentācijas integrācijā) un sūti pieprasījumus caur savu serveri, nevis tieši no pārlūka.

Drošība - CORS, HTTPS, rate limiting

CORS (Cross-Origin Resource Sharing) - pārlūks pēc noklusējuma bloķē JavaScript pieprasījumus uz citu domēnu, nevis to, no kura ielādēta lapa (drošības iemeslu dēļ). Ja API serveris nav skaidri atļāvis tavu domēnu, konsolē redzēsi kļūdu, un pieprasījums neizpildīsies, pat ja serveris atbild pareizi:

textAccess to fetch at 'https://api.piemers.lv/dati' from origin
'https://tavavietne.lv' has been blocked by CORS policy: No
'Access-Control-Allow-Origin' header is present on the requested
resource.

To risina serveris (ne klients) - pievienojot atbildes galveni, kas skaidri atļauj konkrētu domēnu. Konkrētus komandrindas soļus (Nginx konfigurācija, PHP alternatīva bez SSH) skaties "CORS kļūda" problēmu risinājumu lapā.

textAccess-Control-Allow-Origin: https://tavavietne.lv

HTTPS - jebkuram API, kas pārsūta autentifikācijas datus (tokenus, atslēgas, paroles), obligāti jāstrādā pāri HTTPS, nevis HTTP. Bez tā dati ceļo tīklā atklātā tekstā, un jebkurš pa vidu var tos nolasīt.

Rate limiting - lielākā daļa publisko API ierobežo, cik pieprasījumu drīksti sūtīt noteiktā laika periodā. Pārsniedzot limitu, saņemsi 429 Too Many Requests, bieži ar galveni Retry-After, kas pasaka, cik ilgi jāgaida:

jsasync function pieprasijumsArAtkartojumu(url, meginajums = 1) {
    const atbilde = await fetch(url);

    if (atbilde.status === 429 && meginajums <= 3) {
        const gaidit = Number(atbilde.headers.get('Retry-After')) || meginajums * 2;
        await new Promise(r => setTimeout(r, gaidit * 1000));
        return pieprasijumsArAtkartojumu(url, meginajums + 1); // eksponenciāls backoff
    }
    return atbilde;
}

Kods augstāk atkārto pieprasījumu, ja tas neizdodas - bet atkārtot POST ir bīstami (skat. 1. sadaļu, POST nav idempotenta). Ja tīkla kļūda notiek pēc tam, kad serveris jau paspēja apstrādāt maksājumu vai citu "notiek tikai vienreiz" darbību, atkārtots POST var to izpildīt divreiz. Risinājums - Idempotency-Key galvene: klients pats ģenerē unikālu ID katram "loģiskajam" pieprasījumam un sūta to katrā mēģinājumā; serveris atceras, kuri ID jau apstrādāti, un otrreiz atgriež to pašu iepriekšējo rezultātu, neizpildot darbību atkārtoti.

jsconst unikalsId = crypto.randomUUID(); // ģenerē VIENU reizi šim mēģinājumam

await fetch('https://api.piemers.lv/pirkumi', {
    method: 'POST',
    headers: {
        'Content-Type': 'application/json',
        'Idempotency-Key': unikalsId, // tas pats ID visos atkārtotajos mēģinājumos
    },
    body: JSON.stringify({ summa: 25 }),
});

Šī nav pašsaprotama funkcionalitāte - API serverim jābūt to skaidri implementējušam (kā, piemēram, Stripe dara reālajā Checkout Session izveidē). Ja API dokumentācija nemin Idempotency-Key, tas, visticamāk, netiek atbalstīts, un atkārtoti mēģinājumi maksājumu/pasūtījumu endpointiem jāveic ar īpašu piesardzību.

API patēriņš ar JavaScript (fetch)

Pilns, reāli strādājošs piemērs - dati no JSONPlaceholder, ar pareizu kļūdu apstrādi:

jsasync function ieguvValu() {
    try {
        const atbilde = await fetch('https://jsonplaceholder.typicode.com/posts/1');

        // fetch() NEsviest kļūdu 404/500 gadījumā - tas jāpārbauda pašrocīgi
        if (!atbilde.ok) {
            throw new Error(`API kļūda: ${atbilde.status}`);
        }

        const dati = await atbilde.json();
        console.log(dati.title);
        return dati;
    } catch (kluda) {
        // šeit nonāk gan tīkla kļūdas, gan mūsu pašu throw augstāk
        console.error('Neizdevās ielādēt datus:', kluda.message);
        return null;
    }
}

POST piemērs - jaunu datu nosūtīšana ar galvenēm un JSON ķermeni:

jsasync function izveidotIerakstu(virsraksts, saturs) {
    const atbilde = await fetch('https://jsonplaceholder.typicode.com/posts', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ title: virsraksts, body: saturs, userId: 1 }),
    });

    if (!atbilde.ok) throw new Error(`Neizdevās izveidot: ${atbilde.status}`);
    return await atbilde.json();
}

fetch() noraida (reject) Promise tikai tīkla kļūdas gadījumā (piem., nav interneta) - 404 vai 500 atbildes tas uzskata par "veiksmīgu" pieprasījumu ar sliktu saturu. Tāpēc vienmēr pārbaudi atbilde.ok pašrocīgi, kā piemērā augstāk - pretējā gadījumā kļūdas paliks nepamanītas.

fetch() pēc noklusējuma negaida bezgalīgi - ja serveris karājas un neatbild vispār (nevis atgriež kļūdu, bet vienkārši klusē), pieprasījums var palikt "iekārts" uz nenoteiktu laiku, iesaldējot arī pārējo koda izpildi, kas gaida uz to. To risina AbortController - piespiedu kārtā atceļ pieprasījumu pēc noteikta laika:

jsasync function ieguvValuArTimeoutu(url, laiksMs = 5000) {
    const kontrolieris = new AbortController();
    const taimeris = setTimeout(() => kontrolieris.abort(), laiksMs);

    try {
        const atbilde = await fetch(url, { signal: kontrolieris.signal });
        return await atbilde.json();
    } catch (kluda) {
        if (kluda.name === 'AbortError') {
            throw new Error(`Pieprasījums pārsniedza ${laiksMs}ms`);
        }
        throw kluda;
    } finally {
        clearTimeout(taimeris);
    }
}

    echo esc_html($dati['title']);
}

WordPress projektā vienmēr izmanto wp_remote_get/wp_remote_post nevis tiešu curl_* - tas ievēro servera proxy iestatījumus, WordPress filtrus un strādā arī serveros, kur cURL paplašinājums nav pieejams (WordPress automātiski pārslēdzas uz alternatīvu metodi).

Sava REST API endpointa izveide

1. variants - tīrs PHP (vienkāršs endpoints bez ietvara, der mazam projektam):

php// api.php - atver ar https://tavavietne.lv/api.php?id=5
<?php
header('Content-Type: application/json');

$metode = $_SERVER['REQUEST_METHOD'];

if ($metode === 'GET') {
    $id = intval($_GET['id'] ?? 0);

    if (!$id) {
        http_response_code(400);
        echo json_encode(['kluda' => 'Trūkst id parametra']);
        exit;
    }

    // šeit reālā projektā būtu datubāzes vaicājums pēc $id
    echo json_encode(['id' => $id, 'vards' => 'Anna']);
    exit;
}

http_response_code(405);
echo json_encode(['kluda' => 'Metode nav atbalstīta']);

2. variants - WordPress REST API (ieteicams, ja projekts jau ir WordPress - automātiski dabū URL routēšanu, autentifikāciju un daudz ko citu):

php// functions.php
add_action('rest_api_init', function () {
    register_rest_route('mana-vietne/v1', '/lietotajs/(?P<id>\d+)', [
        'methods'  => 'GET',
        'callback' => 'mana_vietne_iegut_lietotaju',
        // permission_callback nosaka, KAM drīkst piekļūt šim endpointam
        'permission_callback' => '__return_true', // publiski pieejams
    ]);
});

function mana_vietne_iegut_lietotaju(WP_REST_Request $pieprasijums) {
    $id = intval($pieprasijums->get_param('id'));

    // šeit reālā projektā būtu WP_User_Query vai $wpdb vaicājums
    return new WP_REST_Response([
        'id'    => $id,
        'vards' => 'Anna',
    ], 200);
}

intval() šeit pasargā $id, jo skaitli nevar padarīt par SQL kodu. Bet jebkurš cits no ārpuses nākošs dati - teksta lauki, meklēšanas frāzes, filtri - pirms nokļūšanas datubāzes vaicājumā vienmēr jāiet cauri $wpdb->prepare(), nekad tieši jāieliek vaicājuma tekstā ar konkatenāciju. Pretējā gadījumā endpoints ir atvērts SQL injection uzbrukumam - apmeklētājs var nosūtīt SQL kodu URL parametra vietā, un tas izpildīsies tavā datubāzē.

Pēc pievienošanas endpoints ir sasniedzams zem /wp-json/:

bashcurl https://tavavietne.lv/wp-json/mana-vietne/v1/lietotajs/5

permission_callback ir obligāts parametrs - WordPress met brīdinājumu, ja to izlaiž. __return_true nozīmē "publiski pieejams visiem"; ja endpoints atgriež sensitīvus vai lietotājam specifiskus datus, tur jāliek reāla pārbaude, piem., fn() => current_user_can('read'), nevis vienmēr true.

Kad savam API ir vairāki endpointi, tos aprakstīt ērtāk ir standartizēti, nevis brīvā tekstā - tam domāts OpenAPI (agrāk saukts Swagger). Tas ir YAML/JSON fails, kas apraksta katru endpointu, tā parametrus un iespējamās atbildes; no šī faila rīki (piem., Swagger UI) automātiski uzģenerē interaktīvu, testējamu dokumentācijas lapu - nav jāraksta atsevišķi.

yaml# openapi.yaml - fragments
/lietotajs/{id}:
  get:
    summary: Iegūst lietotāju pēc ID
    parameters:
      - name: id
        in: path
        required: true
        schema: { type: integer }
    responses:
      '200': { description: Veiksmīga atbilde }
      '404': { description: Lietotājs nav atrasts }

Testēšana (Postman, cURL, DevTools)

Postman - bezmaksas rīks API pieprasījumu sūtīšanai bez koda rakstīšanas:

text1. Lejupielādē un uzstādi Postman (postman.com)
2. "New" → "HTTP Request"
3. Izvēlies metodi (GET/POST/...) un ievadi URL
4. Ja vajag - cilnē "Headers" pievieno Authorization/Content-Type
5. Ja vajag - cilnē "Body" pievieno JSON datus (POST/PUT)
6. "Send" - apakšā uzreiz redzi statusa kodu un atbildi

cURL - tas pats terminālī, ērti kopēt tieši dokumentācijā vai skriptos:

bash# GET ar galveni
curl -H "Authorization: Bearer TOKENS" https://api.piemers.lv/dati

# POST ar JSON ķermeni, -v rāda pilnu apmaiņu (noderīgi atkļūdošanai)
curl -v -X POST https://api.piemers.lv/dati \
  -H "Content-Type: application/json" \
  -d '{"vards":"Anna"}'

Pārlūka DevTools - noderīgi, ja API izsauc pati tava vietne (nevis ārējs rīks):

text1. Atver DevTools (F12) → cilne "Network"
2. Atzīmē filtru "Fetch/XHR", lai redzētu tikai API pieprasījumus
3. Izpildi darbību savā vietnē, kas izsauc API
4. Uzklikšķini uz pieprasījuma → "Headers" (kas nosūtīts),
   "Response" (kas saņemts atpakaļ), "Timing" (cik ilgi tas ņēma)

Kad kods, kas izsauc API, nestrādā, kā gaidīts - vienmēr vispirms pārbaudi DevTools "Network" cilni, pirms sāc mainīt kodu. Bieži problēma nav tavā JS/PHP loģikā, bet gan pašā pieprasījumā (nepareizs URL, trūkstoša galvene, nepareizs metode) - tas uzreiz redzams tur.

Paginācija & kļūdu apstrāde

Kad resursu ir daudz (piem., tūkstošiem lietotāju), API tos neatgriež visus vienā atbildē - tas būtu lēni un patērētu daudz resursu. Tā vietā izmanto paginācija (lapošana):

VeidsPiemērsKad izmanto
Offset/limit?offset=20&limit=10Vienkāršākais, bet lēnāks lieliem datu apjomiem
Page/per_page?page=3&per_page=10Lietotājam draudzīgākais (lapu numuri)
Cursor-based?after=eyJpZCI6NTB9Ātrākais lieliem/mainīgiem datiem (piem., sociālo tīklu barotnes)

Laba API atbilde ar paginācijas metadatiem izskatās apmēram šādi:

json{
  "dati": [ /* ... 10 ieraksti ... */ ],
  "paginacija": {
    "pasreizeja_lapa": 3,
    "lapas_kopa": 15,
    "ierakstu_kopa": 148
  }
}

Tāpat laba API kļūdas atbild ar konsekventu struktūru, ne tikai vienu tekstu:

json{
  "kluda": {
    "kods": "validation_failed",
    "zinojums": "E-pasta lauks ir obligāts",
    "lauks": "epasts"
  }
}

Veidojot savu API (skat. Sava REST API endpointa izveide), no paša sākuma izvēlies vienu konsekventu kļūdu formātu un lieto to visur - klientam, kas patērē tavu API, jāvar paļauties, ka kļūdas vienmēr izskatās vienādi, neatkarīgi no endpointa.
