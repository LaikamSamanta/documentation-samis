memory_limit, execution time, max workeri - kā izvēlēties vērtības pēc RAM

Visi trīs kopā nedrīkst pārsniegt servera reālo RAM - citādi OOM var nogalināt arī MySQL, ne tikai PHP.

IestatījumsKo daraKā izvēlēties
memory_limitMax RAM, ko drīkst izmantot viens PHP process/skripts.WordPress min. 64M, ar spraudņiem/WooCommerce parasti 256M; smagiem importiem īslaicīgi 512M.
max_execution_timeCik sekundes skripts drīkst darboties, pirms PHP to pārtrauc.30-60s parastām lapām. Neceļ globāli augstu "drošībai" - iestrēdzis skripts tik ilgi tur aizņemtu worker'i.
pm.max_childrenCik PHP-FPM worker procesu drīkst darboties vienlaicīgi (max vienlaicīgi apstrādāto pieprasījumu skaits).Formula: pieejamā RAM priekš PHP-FPM (MB) ÷ vidējais RAM patēriņš uz vienu worker'i (MB) - sk. zemāk, kā izmērīt abus.

pm.max_children × memory_limit = max RAM patēriņš, ja visi worker'i strādā vienlaicīgi. Ja pārsniedz servera reāli atlikušo RAM - OOM var nogalināt arī MySQL.

Kā fiziski izmērīt - SSH

bash# cik RAM serverim kopā un cik brīvs
free -h

# cik CPU kodolu (arī ierobežo, cik worker'us jēga likt)
nproc

# kādi php-fpm procesi vispār strādā (nosaukums atkarīgs no PHP versijas)
ps aux | grep php-fpm

# vidējais reālais RAM patēriņš uz vienu php-fpm worker'i (MB)
ps --no-headers -o rss,cmd -C php-fpm8.1 | awk '{sum+=$1; n++} END {print sum/n/1024" MB videji, "n" workeri"}'

# pašreizējais memory_limit (CLI php var atšķirties no web/FPM!)
php -i | grep -i memory_limit

# kurš php.ini/pool fails faktiski ielādēts
php --ini

Kalkulators - ieliec nomērītās vērtības

Izdod tieši to skaitli, kas jāieliek laukā:

bash# → "Kopējais servera RAM (MB)"
free -m | awk '/Mem:/{print $2}'

# → "Vidējais RAM uz vienu worker'i (MB)" (nomaini php-fpm8.1 uz savu versiju)
ps --no-headers -o rss -C php-fpm8.1 | awk '{s+=$1; n++} END {print s/n/1024}'

Kalkulators - max_execution_time

Pārāk augsts max_execution_time = iestrēdzis skripts ilgi aizņem worker'i, var izsmelt visus (502/503 citiem).

time parāda reālo ilgumu (nomaini komandu):

bash# → "Vislēnākā zināmā leģitīmā darbība (sekundes)"
time wp import lielais-fails.xml # vai jebkura cita smaga komanda/skripts

Kuri faili konkrēti (Plesk)

FailsKo satur
/var/www/vhosts/system/<domēns>/etc/php.iniKonkrētā domēna memory_limit, max_execution_time u.c. - šo failu Plesk ģenerē, kad maini PHP Settings UI.
/opt/plesk/php/<versija>/etc/php.iniGlobālais/noklusējuma php.ini konkrētai PHP versijai (piem. 8.1) - izmanto tikai tad, ja domēnam nav sava override.
FPM pool fails (pm.max_children)Ceļš atšķiras pēc Plesk/PHP versijas - neuzmini, atrodi to dinamiski (sk. komandas zemāk).
 
bash# atrod konkrētā domēna FPM pool failu (nomaini domēnu)
grep -rl "tavsdomens.lv" /opt/plesk/php/*/etc/php-fpm.d/ 2>/dev/null

# ja neatrod - meklē plašāk visā sistēmā
find / -iname "*.conf" -path "*fpm*" 2>/dev/null | xargs grep -l "tavsdomens.lv" 2>/dev/null

# redzi, kuru konfigurāciju php-fpm serviss faktiski palaiž (servisa nosaukums no iepriekšējās komandas)
systemctl status 'plesk-php*-fpm' 2>/dev/null | grep -i conf

pm.max_children maini caur Websites & Domains → domēns → PHP Settings, nevis pool failu tieši - Plesk to var pārrakstīt. Ja tomēr rediģē pašrocīgi, pēc tam systemctl restart attiecīgajam servisam.

Vairāki domēni uz viena servera = katram savs FPM pool - rēķini ar visu domēnu kopējo patēriņu, ne tikai viena.

Kas reāli jāzina kā programmētājam (ne tikai hostinga administratoram)

Lietas, kas sagādā pārsteigumus, kad kaut kas "bez iemesla" nomirst vai neatbilst php.ini.

Trīs dažādi timeout limiti - ne tikai max_execution_time

Trīs līmeņi var pārtraukt pieprasījumu neatkarīgi - uzvar mazākais no tiem.

LīmenisKur iestatītsKo rāda, kad nostrādā
PHP pats (max_execution_time)php.ini / Plesk PHP SettingsPHP error log: Fatal error: Maximum execution time of Xs exceeded. Baltā lapa vai 500.
PHP-FPM (request_terminate_timeout)FPM pool fails (sk. augstāk, kur atrast)PHP-FPM log: child X, script '...' execution timed out. Bieži 502/504.
Web serveris (Nginx fastcgi_read_timeout / Apache ProxyTimeout)Nginx/Apache konfigurācija (Plesk: "Additional nginx directives")Nginx log: upstream timed out. Pārlūkā 504 Gateway Timeout - PHP pats var vēl turpināt strādāt fonā.

Piemērs: max_execution_time=300s, bet FPM/Nginx=60s → nomirst pēc 60s. Visi trīs jāceļ kopā.

Kalkulators - efektīvais timeout

FPM/Nginx noklusējumi (bieži ~60s) var ierobežot pat ja neesi tos mainījis. Ievadi visus trīs - parāda, kurš faktiski nogriež.

FPM pašreizējā vērtība:

bash# → "PHP-FPM request_terminate_timeout" (0, ja rindas nav - nozīmē bez limita)
grep request_terminate_timeout /opt/plesk/php/*/etc/php-fpm.d/*.conf 2>/dev/null
effective-timeout-calc

CLI skripti (WP-CLI/artisan/cron) parasti šos limitus neredz

CLI izmanto citu php.ini - bieži bez limitiem (-1/0), neatkarīgi no web/FPM iestatījumiem. Tāpēc smagas darbības labāk palaist caur SSH/CLI/cron, ne pārlūku.

WordPress: WP_MEMORY_LIMIT / WP_MAX_MEMORY_LIMIT

WordPress ierobežo atmiņu ar savām konstantēm wp-config.php, neatkarīgi no servera memory_limit.

php// wp-config.php - parastām front-end/admin lapām
define('WP_MEMORY_LIMIT', '256M');

// smagām admin darbībām (WordPress šo izmanto wp-admin kontekstā)
define('WP_MAX_MEMORY_LIMIT', '512M');

Noklusējums: WP_MEMORY_LIMIT 40M (64M multisite), WP_MAX_MEMORY_LIMIT 256M.

Kur skatīties, kurš limits nostrādāja

PHP error log: /var/www/vhosts/system/<domēns>/logs/error_log. Ja tukšs, bet pārlūkā 502/504 - vaino FPM/Nginx, ne PHP.
