memory_limit, execution time, max workeri - kā izvēlēties vērtības pēc RAM

Šie trīs iestatījumi ir savstarpēji saistīti - visi kopā nedrīkst pārsniegt serverim faktiski pieejamo RAM, citādi risks ir OOM (out-of-memory), kas var nogalināt arī MySQL vai citus procesus, ne tikai PHP.

IestatījumsKo daraKā izvēlēties
memory_limitMax RAM, ko drīkst izmantot viens PHP process/skripts.WordPress min. 64M, ar spraudņiem/WooCommerce parasti 256M; smagiem importiem īslaicīgi 512M.
max_execution_timeCik sekundes skripts drīkst darboties, pirms PHP to pārtrauc.30-60s parastām lapām. Neceļ globāli augstu "drošībai" - iestrēdzis skripts tik ilgi tur aizņemtu worker'i.
pm.max_childrenCik PHP-FPM worker procesu drīkst darboties vienlaicīgi (max vienlaicīgi apstrādāto pieprasījumu skaits).Formula: pieejamā RAM priekš PHP-FPM (MB) ÷ vidējais RAM patēriņš uz vienu worker'i (MB) - sk. zemāk, kā izmērīt abus.

pm.max_children × memory_limit ir teorētiskais maksimums, ko PHP-FPM var izēst no RAM, ja visi worker'i vienlaicīgi strādā pie smagiem skriptiem. Ja šis reizinājums pārsniedz serverim faktiski atlikušo RAM (pēc MySQL, Plesk, Nginx/Apache u.c.) - serveris var sākt swapot vai OOM killer sāk nogalināt procesus, ieskaitot, iespējams, datubāzi.

Kā fiziski izmērīt - SSH

bash# cik RAM serverim kopā un cik brīvs
free -h

# cik CPU kodolu (arī ierobežo, cik worker'us jēga likt)
nproc

# kādi php-fpm procesi vispār strādā (nosaukums atkarīgs no PHP versijas)
ps aux | grep php-fpm

# vidējais reālais RAM patēriņš uz vienu php-fpm worker'i (MB)
ps --no-headers -o rss,cmd -C php-fpm8.1 | awk '{sum+=$1; n++} END {print sum/n/1024" MB videji, "n" workeri"}'

# pašreizējais memory_limit (CLI php var atšķirties no web/FPM!)
php -i | grep -i memory_limit

# kurš php.ini/pool fails faktiski ielādēts
php --ini

Kalkulators - ieliec nomērītās vērtības

Ērtāk kopēt - šīs komandas uzreiz izdod tikai skaitli, ko ielikt attiecīgajā laukā:

bash# → "Kopējais servera RAM (MB)"
free -m | awk '/Mem:/{print $2}'

# → "Vidējais RAM uz vienu worker'i (MB)" (nomaini php-fpm8.1 uz savu versiju)
ps --no-headers -o rss -C php-fpm8.1 | awk '{s+=$1; n++} END {print s/n/1024}'

Kalkulators - max_execution_time

max_execution_time nevar likt "ar rezervi" pēc jūtas - pārāk augsts, un iestrēdzis/lēns skripts uz ilgu laiku aizņem PHP-FPM worker'i, kas pie noslogota servera var novest pie worker'u izsīkuma (502/503 citiem apmeklētājiem).

Ērtāk kopēt - time parāda, cik sekundes komanda reāli aizņēma (nomaini uz savu smago darbību):

bash# → "Vislēnākā zināmā leģitīmā darbība (sekundes)"
time wp import lielais-fails.xml # vai jebkura cita smaga komanda/skripts

Kuri faili konkrēti (Plesk)

FailsKo satur
/var/www/vhosts/system/<domēns>/etc/php.iniKonkrētā domēna memory_limit, max_execution_time u.c. - šo failu Plesk ģenerē, kad maini PHP Settings UI.
/opt/plesk/php/<versija>/etc/php.iniGlobālais/noklusējuma php.ini konkrētai PHP versijai (piem. 8.1) - izmanto tikai tad, ja domēnam nav sava override.
FPM pool fails (pm.max_children)Ceļš atšķiras pēc Plesk/PHP versijas - neuzmini, atrodi to dinamiski (sk. komandas zemāk).
 
bash# atrod konkrētā domēna FPM pool failu (nomaini domēnu)
grep -rl "tavsdomens.lv" /opt/plesk/php/*/etc/php-fpm.d/ 2>/dev/null

# ja neatrod - meklē plašāk visā sistēmā
find / -iname "*.conf" -path "*fpm*" 2>/dev/null | xargs grep -l "tavsdomens.lv" 2>/dev/null

# redzi, kuru konfigurāciju php-fpm serviss faktiski palaiž (servisa nosaukums no iepriekšējās komandas)
systemctl status 'plesk-php*-fpm' 2>/dev/null | grep -i conf

Plesk katram domēnam/PHP versijai parasti taisa savu FPM pool'u - pm.max_children maini caur Websites & Domains → domēns → PHP Settings (ja tur nav lauka - "Additional configuration directives"), nevis rediģē pool failus tieši, jo Plesk tos var pārrakstīt. Ja tomēr rediģē failu pašrocīgi, pēc izmaiņām jārestartē attiecīgais php-fpm serviss (systemctl restart ar to servisa nosaukumu, kas redzams systemctl list-units | grep php-fpm).

Ja hostē vairākus domēnus uz viena servera - katram var būt savs FPM pool ar savu pm.max_children, tāpēc formulai jāskatās uz visu domēnu kopējo maksimālo patēriņu, ne tikai viena.

Kas reāli jāzina kā programmētājam (ne tikai hostinga administratoram)

Ja pats pārvaldi arī hostingu - šīs ir lietas, kas reāli sagādā pārsteigumus, kad kaut kas "bez iemesla" nomirst vai neatbilst tam, ko liki php.ini.

Trīs dažādi timeout limiti - ne tikai max_execution_time

Pieprasījumu var pārtraukt trīs pavisam dažādos līmeņos. Ja paceļ tikai vienu, bet pārējie divi palikuši zemāki - pieprasījums tik un tā nomirst pēc mazākā no tiem.

LīmenisKur iestatītsKo rāda, kad nostrādā
PHP pats (max_execution_time)php.ini / Plesk PHP SettingsPHP error log: Fatal error: Maximum execution time of Xs exceeded. Baltā lapa vai 500.
PHP-FPM (request_terminate_timeout)FPM pool fails (sk. augstāk, kur atrast)PHP-FPM log: child X, script '...' execution timed out. Bieži 502/504.
Web serveris (Nginx fastcgi_read_timeout / Apache ProxyTimeout)Nginx/Apache konfigurācija (Plesk: "Additional nginx directives")Nginx log: upstream timed out. Pārlūkā 504 Gateway Timeout - PHP pats var vēl turpināt strādāt fonā.

Ja paceļ max_execution_time uz 300s, bet FPM/Nginx timeout paliek 60s - pieprasījums vienalga nomirst pēc 60s, un tā ir klasiska "kāpēc mans imports vienalga apstājas" kļūda. Visi trīs jāceļ kopā.

Kalkulators - efektīvais timeout

Kāpēc tas vajadzīgs: pat ja FPM/Nginx pats neko neesi mainījis, tiem tik un tā ir savas noklusējuma vērtības (Nginx bieži ~60s) - tās var būt zemākas par to, ko liki php.ini, un tieši tās tevi ierobežo, ne tavs iestatījums. Ievadi visus trīs (ar noklusējumiem, ja neesi mainījis) - kalkulators pasaka, kurš no tiem faktiski nogriež pieprasījumu, lai zini, kuru tieši mainīt.

Kā uzzināt pašreizējo FPM vērtību (ja fails jau atrasts ar komandām augstāk):

bash# → "PHP-FPM request_terminate_timeout" (0, ja rindas nav - nozīmē bez limita)
grep request_terminate_timeout /opt/plesk/php/*/etc/php-fpm.d/*.conf 2>/dev/null

CLI skripti (WP-CLI/artisan/cron) parasti šos limitus neredz

PHP CLI (komandrindas) izmanto citu konfigurāciju no web/FPM - bieži ar memory_limit/max_execution_time vispār bez ierobežojuma (-1/0), neatkarīgi no tā, kas iestatīts domēna PHP Settings. Tāpēc smaga darbība (imports, migrācija) caur SSH/WP-CLI/artisan var strādāt bez problēmām, kamēr tā pati darbība, palaista caur pārlūku (wp-admin poga), nomirst pēc 30-60s. Praktisks padoms: smagas darbības labāk palaist caur CLI/cron, nevis caur pārlūku.

WordPress: WP_MEMORY_LIMIT / WP_MAX_MEMORY_LIMIT

WordPress pats ierobežo atmiņu ar savām konstantēm wp-config.php - neatkarīgi no servera memory_limit. Ja serverī uzliec 512M, bet šīs konstantes paliek noklusējumā, WordPress joprojām apstāsies pie sava zemākā limita.

php// wp-config.php - parastām front-end/admin lapām
define('WP_MEMORY_LIMIT', '256M');

// smagām admin darbībām (WordPress šo izmanto wp-admin kontekstā)
define('WP_MAX_MEMORY_LIMIT', '512M');

Noklusējuma vērtības, ja konstantes nav uzliktas: WP_MEMORY_LIMIT - 40M (64M multisite), WP_MAX_MEMORY_LIMIT - 256M.

Kur skatīties, kurš limits konkrēti nostrādāja

Domēna PHP error log Plesk parasti atrodas /var/www/vhosts/system/<domēns>/logs/error_log - tur redz, vai tā bija PHP kļūda (execution time/memory), vai jāskatās FPM/Nginx logs (ja pārlūkā ir 502/504, bet PHP error log klusē - problēma nav pašā PHP).
