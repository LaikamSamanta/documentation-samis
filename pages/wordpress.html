Tēmu izveide

Lai WordPress atpazītu mapi wp-content/themes/ iekšpusē kā tēmu, obligāti nepieciešami tikai divi faili: style.css (ar galvenes komentāru) un index.php. Bez index.php tēma administrācijā parādās kā "Broken Theme" un to nevar aktivizēt.

1. solis - izveido mapi wp-content/themes/mana-tema/ un tajā šo failu:

css/* style.css */
/*
Theme Name: Mana Tēma
Version: 1.0
*/

body { font-family: sans-serif; }

2. solis - tajā pašā mapē izveido index.php:

php<?php get_header(); ?>

<main>
  <?php if (have_posts()) : while (have_posts()) : the_post(); ?>
    <article>
      <h2><?php the_title(); ?></h2>
      <?php the_content(); ?>
    </article>
  <?php endwhile; endif; ?>
</main>

<?php get_footer(); ?>

3. solis - WordPress admin panelī ej uz Izskats → Tēmas → aktivizē "Mana Tēma". Tas ir viss - tēma jau strādā, kaut arī izskatīsies "kaila", jo trūkst header.php/footer.php.

Ja index.php izmanto get_header()/get_footer(), tad header.php/footer.php failiem jau jāeksistē tajā pašā mapē (kaut tukšiem: <html><body> un attiecīgi </body></html>), citādi radīsies kļūda.

Bērnu tēmas (Child Themes)

Viens no biežākajiem un dārgākajiem iesācēju kļūdām: rediģēt lejupielādētu vai iegādātu tēmu tieši (piem., mainīt style.css vai functions.php failā, kas nāca kopā ar tēmu). Kad tēmas autors izlaidīs atjauninājumu un to uzstādīsi, visas tavas izmaiņas tiks pilnībā pārrakstītas un pazudīs - WordPress vienkārši aizvieto veco tēmas mapi ar jauno.

Bērnu tēma atrisina šo problēmu: tā ir atsevišķa, maza tēma, kas "manto" visu no vecāktēmas (parent theme), bet ļauj droši pārrakstīt tikai to, ko vēlies mainīt. Vecāktēmu var brīvi atjaunināt - bērnu tēma un tavas izmaiņas paliek neskartas.

1. solis - izveido jaunu mapi, piem. wp-content/themes/mana-tema-child/, ar šo style.css:

css/*
Theme Name: Mana Tēma Child
Template: mana-tema
Version: 1.0
*/

Template rindā jānorāda tieši vecāktēmas mapes nosaukums (nevis "Theme Name") - šī ir vienīgā obligātā saite starp abām tēmām.

2. solis - tajā pašā mapē izveido functions.php, kas ielādē gan vecāktēmas, gan bērnu tēmas stilus:

php<?php
add_action('wp_enqueue_scripts', function() {
    // Vispirms ielādē vecāktēmas stilus
    wp_enqueue_style(
        'parent-style',
        get_template_directory_uri() . '/style.css'
    );

    // Tad bērnu tēmas stilus - "vecāks" no parent-style,
    // lai tas ielādētos PĒC un varētu pārrakstīt tā noteikumus
    wp_enqueue_style(
        'child-style',
        get_stylesheet_uri(),
        ['parent-style']
    );
});

3. solis - Izskats → Tēmas → aktivizē "Mana Tēma Child". Vietne izskatīsies tieši tāpat kā ar vecāktēmu, bet tagad droši vari pievienot savu CSS style.css beigās vai pārrakstīt atsevišķus .php failus (piem., footer.php), tos nokopējot no vecāktēmas uz bērnu tēmas mapi un tur rediģējot - WordPress vienmēr vispirms meklē failu bērnu tēmā, un tikai tad vecāktēmā.

Ja plāno izmantot lejupielādētu vai iegādātu tēmu (ne pašrakstītu), vienmēr izveido tai bērnu tēmu uzreiz sākumā, pirms sāc jebko rediģēt - daudz vieglāk to izdarīt no paša sākuma, nekā mēģināt "izvilkt" izmaiņas no galvenās tēmas failiem vēlāk.

wp-config.php

Galvenais konfigurācijas fails, kas atrodas WordPress saknes mapē (blakus wp-admin, wp-content) - satur datubāzes pieejas datus un svarīgākos globālos iestatījumus. Šo failu neveido pats - to automātiski izveido WordPress instalācijas laikā, bet vēlāk to var rediģēt.

php<?php
// --- Datubāze ---
define('DB_NAME', 'mana_datubaze');
define('DB_USER', 'root');
define('DB_PASSWORD', 'secret');
define('DB_HOST', 'localhost');
define('DB_CHARSET', 'utf8mb4');
define('DB_COLLATE', '');

// Tabulu prefikss - maini no noklusējuma "wp_" drošības apsvērumu dēļ
$table_prefix = 'wp_';

// --- Autentifikācijas atslēgas un "sāls" (salts) ---
// Ģenerē unikālas katrai instalācijai: https://api.wordpress.org/secret-key/1.1/salt/
// Maiņa šeit uzreiz atslēdz visus esošos pieteikšanās sesiju "cookies"
define('AUTH_KEY',         'ievieto-unikālu-virkni-šeit');
define('SECURE_AUTH_KEY',  'ievieto-unikālu-virkni-šeit');
// ... un tā tālāk visām 8 atslēgām

// --- Vides tips (WordPress 5.5+) - ietekmē, kā daži spraudņi/tēmas uzvedas ---
define('WP_ENVIRONMENT_TYPE', 'production'); // local | development | staging | production

// --- Atkļūdošana (izstrādes vidē) ---
define('WP_DEBUG', true);          // ieslēdz kļūdu apstrādi kopumā
define('WP_DEBUG_LOG', true);      // raksta kļūdas failā wp-content/debug.log
define('WP_DEBUG_DISPLAY', false); // bet neizvada tās ekrānā apmeklētājiem
define('SCRIPT_DEBUG', true);      // ielādē nesaspiestās (.js/.css) kodola versijas

// --- Drošība (ražošanas vidē) ---
define('DISALLOW_FILE_EDIT', true);   // izslēdz tēmas/spraudņu redaktoru admin panelī
define('DISALLOW_FILE_MODS', true);   // bloķē spraudņu/tēmu instalēšanu un atjaunināšanu no admin paneļa
define('FORCE_SSL_ADMIN', true);      // piespiedu HTTPS admin panelim un pieteikšanās lapai

// --- Veiktspēja ---
define('WP_MEMORY_LIMIT', '256M');  // PHP atmiņas limits, ko WordPress drīkst izmantot
define('WP_POST_REVISIONS', 5);   // ierobežo revīziju skaitu (noklusējumā neierobežots)
define('AUTOSAVE_INTERVAL', 120); // automātiskās saglabāšanas intervāls sekundēs

// --- Automātiskie atjauninājumi ---
define('WP_AUTO_UPDATE_CORE', 'minor'); // true | false | 'minor' (tikai drošības ielāpi)

if ( ! defined( 'ABSPATH' ) ) {
    define( 'ABSPATH', __DIR__ . '/' );
}
require_once ABSPATH . 'wp-settings.php';

WP_ENVIRONMENT_TYPE

Kopš WP 5.5 ļauj kodam/spraudņiem uzvesties atšķirīgi lokālajā, staging un production vidē (wp_get_environment_type()).

Autentifikācijas atslēgas

8 nejaušas virknes, kas šifrē pieteikšanās "cookies" - ģenerē ar WordPress.org rīku, nevis izdomā pašrocīgi.

DISALLOW_FILE_EDIT

Ražošanas vietnē vienmēr izslēdz iebūvēto koda redaktoru - bieži izmantots uzbrukuma vektors, ja admin konts tiek kompromitēts.

Tabulu prefikss

Maiņa no noklusējuma wp_ uz kaut ko unikālu apgrūtina automatizētus SQL injection uzbrukumus, kas pieņem noklusējuma nosaukumu.

Pirms vietnes publicēšanas obligāti iestati WP_DEBUG_DISPLAY uz false (vai vienkārši WP_DEBUG uz false) - kļūdu izvade ražošanas vietnē var atklāt failu ceļus un citu jutīgu informāciju apmeklētājiem. Izmanto WP_DEBUG_LOG, lai kļūdas tik un tā redzētu failā, neparādot tās apmeklētājiem.

Spraudņa pamatstruktūra

Ja funkcionalitātei jāpaliek neatkarīgai no tēmas (nemainās, kad nomaina dizainu - piem., kontaktforma, ziņu abonēšana), to noformē kā spraudni, nevis functions.php. Minimāls spraudnis ir viens PHP fails ar galvenes komentāru - WordPress to atpazīst pēc šī komentāra formāta, nevis pēc faila nosaukuma.

Izveido wp-content/plugins/mans-spraudnis/mans-spraudnis.php:

php<?php
/**
 * Plugin Name: Mans Spraudnis
 * Description: Īss apraksts, ko tas dara
 * Version: 1.0
 * Author: Tavs vārds
 */

// Pasargā failu no tiešas piekļuves ārpus WordPress
defined('ABSPATH') || exit;

// No šejienes tālāk - tieši tāda pati sintakse kā functions.php
add_action('wp_footer', function() {
    echo '<!-- Mans spraudnis strādā -->';
});

Pēc faila saglabāšanas admin panelī Spraudņi → Uzstādītie spraudņi parādīsies "Mans Spraudnis" ar pogu "Aktivizēt".

Template Hierarchy

Kad apmeklētājs atver lapu, WordPress automātiski izvēlas, kuru veidnes failu izmantot, sekojot noteiktai prioritāšu secībai - pirmo atrasto failu tēmas mapē tas arī izmanto. Ja specifiskāka veidne neeksistē, WordPress "krīt atpakaļ" uz vispārīgāku, un galu galā vienmēr uz index.php (vienīgo patiešām obligāto failu).

textSākumlapa:        front-page.php → home.php → index.php
Viens ieraksts:    single-{post-type}.php → single.php → index.php
Statiska lapa:     page-{slug}.php → page.php → index.php
Ierakstu arhīvs:   archive-{post-type}.php → archive.php → index.php
Kategorija:        category-{slug}.php → category.php → archive.php → index.php
Birka:             tag-{slug}.php → tag.php → archive.php → index.php
Meklēšana:         search.php → index.php
Kļūda 404:         404.php → index.php

Piemērs: ja tēmā izveido single-produkts.php, tas automātiski parādīsies visiem "produkts" CPT ierakstiem, nevajag neko papildus reģistrēt - WordPress pats atrod šo failu pēc nosaukuma.

The Loop

WordPress ierakstus lapā izvada ar "The Loop" - standarta ciklu, ko izmanto gandrīz katrā veidnes failā (index.php, archive.php, single.php). have_posts() pārbauda, vai vēl ir ieraksti; the_post() "sagatavo" nākamo ierakstu, lai funkcijas kā the_title() zinātu, par kuru ierakstu runāt.

php<?php if (have_posts()) : ?>

  <?php while (have_posts()) : the_post(); ?>

    <article>
      <h2><a href="<?php the_permalink(); ?>"><?php the_title(); ?></a></h2>
      <p>Ieraksta ID: <?php echo get_the_ID(); ?></p>
      <?php the_content(); ?>
    </article>

  <?php endwhile; ?>

<?php else : ?>
  <p>Ieraksti nav atrasti.</p>
<?php endif; ?>

Šo bloku ievieto jebkurā veidnes failā, kur jāparāda ierakstu saraksts vai saturs - visbiežāk index.php, archive.php vai single.php.

Template Tags

Template tags ir funkcijas, ko izsauc The Loop iekšienē (starp have_posts() un endwhile), lai izvadītu konkrētā ieraksta datus - nosaukumu, saturu, datumu, izcēlattēlu.

the_title()

Izvada ieraksta virsrakstu tieši (echo).

the_content()

Izvada pilnu ieraksta saturu (ar formatējumu).

the_excerpt()

Izvada īsu izvilkumu - noder sarakstu skatiem.

the_permalink()

Izvada pilnu URL uz ierakstu.

the_date()

Izvada publicēšanas datumu.

the_post_thumbnail()

Izvada izcēlattēlu kā <img> tagu.

Katrai the_*() funkcijai ir arī get_the_*() versija (piem. get_the_title()), kas atgriež vērtību, nevis izvada uzreiz - noderīga, ja vērtība jāapstrādā pirms izvades:

php$virsraksts = get_the_title();
echo strtoupper($virsraksts); // virsraksts LIELAJIEM BURTIEM

// Izcēlattēls prasa aktivizēt atbalstu functions.php failā:
add_theme_support('post-thumbnails');

Conditional Tags

Funkcijas, kas atgriež true/false, lai noteiktu, kāda veida lapa pašlaik tiek rādīta - īpaši noderīgas koplietotos failos (header.php, footer.php), kur jāizvada dažāds saturs atkarībā no lapas.

Lapas veids:

textis_front_page()       → vai šī ir sākumlapa
is_home()              → vai šī ir ierakstu plūsmas lapa
is_single()            → vai šis ir viens ieraksts (post vai CPT ar atbalstu)
is_singular()          → tas pats, bet plašāk - ietver arī lapas un pielikumus
is_page()              → vai šī ir statiska lapa
is_page_template()     → vai lapa izmanto konkrētu lapas veidni
is_archive()           → vai šī ir jebkāds arhīvs
is_category() / is_tag() → vai konkrēta kategorija/birka
is_tax()               → vai pielāgotas taksonomijas arhīva lapa
is_author()            → vai autora arhīva lapa
is_date() / is_year() / is_month() / is_day() → vai datuma arhīvs (un cik precīzs)
is_search()            → vai šī ir meklēšanas rezultātu lapa
is_404()               → vai šī ir "nav atrasts" lapa
is_paged()             → vai tā ir 2. vai tālāka arhīva/saraksta lapa
is_attachment()        → vai atsevišķa pielikuma (attēla/faila) lapa

Lietotājs & vide:

textis_user_logged_in()   → vai apmeklētājs ir pieteicies
is_admin()            → vai atrodamies admin panelī (nevis publiskajā daļā)
is_super_admin()      → vai lietotājam ir tīkla superadmina tiesības (multisite)
is_multisite()        → vai instalācija ir WordPress Multisite tīkls
is_main_site()        → vai šī ir Multisite tīkla galvenā vietne
is_ssl()              → vai pašreizējais pieprasījums notiek pa HTTPS
wp_is_mobile()        → rupjš mobilās ierīces "guess" pēc User-Agent (ne 100% precīzs)
is_customize_preview() → vai skats tiek rādīts Customizer priekšskatījumā

Ieraksta stāvoklis (izsauc The Loop iekšpusē, konkrētam ierakstam):

texthas_excerpt()         → vai ierakstam ir manuāli uzrakstīts izvilkums
has_post_thumbnail()  → vai ierakstam ir iestatīts izcēlattēls
comments_open()       → vai komentāri šim ierakstam ir atvērti
pings_open()          → vai pingback/trackback ir atvērti šim ierakstam
phpif (is_front_page()) {
    echo 'Laipni lūdzam sākumlapā!';
} elseif (is_singular('produkts')) {
    echo 'Skaties vienu produktu.';
} elseif (!is_user_logged_in()) {
    echo 'Lūdzu, piesakies, lai redzētu vairāk.';
}

is_single() pēc noklusējuma aptver arī pielāgotos ierakstu tipus (CPT), bet ne lapas - ja nepieciešams pārbaudīt "vai šis ir viens ieraksts, jebkāds tips, ieskaitot lapas", izmanto plašāko is_singular() tā vietā.

WP_Query (pielāgoti vaicājumi)

Kad jāizgūst ieraksti ārpus galvenā The Loop (piem., "Populārākie raksti" bloks sānjoslā), izmanto WP_Query klasi. Pēc pielāgotā cikla vienmēr jāizsauc wp_reset_postdata(), lai atjaunotu globālo $post mainīgo - citādi galvenais Loop tālāk lapā var sākt rādīt nepareizus datus.

php$vaicajums = new WP_Query([
    'post_type'      => 'post',
    'posts_per_page' => 5,
    'orderby'        => 'date',
    'order'          => 'DESC',
]);

if ($vaicajums->have_posts()) :
    while ($vaicajums->have_posts()) : $vaicajums->the_post(); ?>
        <h3><?php the_title(); ?></h3>
    <?php endwhile;
endif;

wp_reset_postdata(); // obligāti pēc pielāgota vaicājuma!

Lai galvenajā arhīva vaicājumā mainītu iestatījumus (piem., cik ierakstu rādīt vienā lapā), labāk izmanto āķi pre_get_posts, nevis jaunu WP_Query:

phpadd_action('pre_get_posts', function($query) {
    if (!is_admin() && $query->is_main_query() && $query->is_category('jaunumi')) {
        $query->set('posts_per_page', 12);
    }
});

Taksonomijas

Taksonomija ir veids, kā grupēt saturu - WordPress jau nāk ar divām iebūvētām: kategorijas (hierarhiskas, ar apakškategorijām) un birkas (plakanas, bez hierarhijas). Savu taksonomiju izveido ar register_taxonomy(), un to var piesaistīt gan parastiem ierakstiem, gan CPT.

phpadd_action('init', function() {
    register_taxonomy('zime', 'post', [
        'label'              => 'Zīmes',
        'hierarchical'       => true,  // true = kā kategorijas, false = kā birkas
        'show_in_rest'       => true,  // vajadzīgs Gutenberg redaktoram
        'show_admin_column'  => true,  // parāda kolonnu ierakstu sarakstā
    ]);
});

Rādīšana veidnē - ierakstam piesaistīto terminu saraksts:

php<?php echo get_the_term_list(get_the_ID(), 'zime', '', ', '); ?>

Citi register_taxonomy() argumenti

rewrite

Masīvs, piem. ['slug' => 'zimes'] - nosaka, kāds vārds parādās URL taksonomijas arhīva lapā (/zimes/kaut-kas/), nevis noklusējuma taksonomijas nosaukumu.

show_ui

Vai admin panelī rādīt rediģēšanas saskarni (formu terminu pievienošanai). Pēc noklusējuma seko public vērtībai.

show_in_menu

Vai taksonomija parādās kreisajā admin izvēlnē. Var būt arī cita ieraksta tipa menu_slug virkne, lai iegultu apakšizvēlnē tam.

show_tagcloud

Vai taksonomija pieejama "Birku mākoņa" (Tag Cloud) widžetā - parasti izslēdz hierarhiskām taksonomijām.

query_var

true ļauj vaicāt ?zime=nosaukums; var norādīt arī savu virkni cita mainīgā nosaukuma vietā.

public

Vispārējs "galvenais slēdzis" - kad true, automātiski iestata saprātīgas noklusējuma vērtības pārējiem redzamības argumentiem, ja tie nav norādīti atsevišķi.

Pilnāks piemērs ar visiem biežāk lietotajiem argumentiem un pilnu labels masīvu (nevis īsinājumu 'label') - der kopēt kā sākumpunktu jebkurai jaunai taksonomijai:

phpadd_action('init', function() {
    register_taxonomy('zime', ['post', 'produkts'], [
        'labels' => [
            'name'          => 'Zīmes',
            'singular_name' => 'Zīme',
            'search_items'  => 'Meklēt zīmes',
            'all_items'     => 'Visas zīmes',
            'edit_item'     => 'Rediģēt zīmi',
            'add_new_item'  => 'Pievienot jaunu zīmi',
        ],
        'hierarchical'      => true,
        'public'            => true,
        'show_ui'           => true,
        'show_in_menu'      => true,
        'show_in_rest'      => true,
        'show_admin_column' => true,
        'show_tagcloud'     => false,
        'query_var'         => true,
        'rewrite'           => ['slug' => 'zimes'],
    ]);
});

Otrais register_taxonomy() parametrs var būt gan viena virkne ('post'), gan masīvs ar vairākiem ierakstu tipiem - šis piemērs piesaista taksonomiju gan parastiem ierakstiem, gan CPT produkts vienlaicīgi.

Custom Post Types (CPT)

Papildus ierakstiem un lapām WordPress ļauj izveidot savus, strukturētus satura tipus - piemēram, "Produkti" vai "Atsauksmes", katru ar savu administrācijas sadaļu. Reģistrē tos ar register_post_type(), izsauktu caur init āķi.

php// functions.php
add_action('init', function() {
    register_post_type('produkts', [
        'labels'       => [
            'name'          => 'Produkti',
            'singular_name' => 'Produkts',
        ],
        'public'       => true,
        'has_archive'  => true,
        'show_in_rest' => true, // vajadzīgs Gutenberg redaktoram
        'menu_icon'    => 'dashicons-cart',
        'supports'     => ['title', 'editor', 'thumbnail'],
    ]);
});

Pēc šī koda pievienošanas un lapas atsvaidzināšanas admin panelī sānizvēlnē parādīsies jauna sadaļa "Produkti" ar savu grozāmo ikonu - tur var pievienot jaunus ierakstus tāpat kā parastus WordPress ierakstus.

Pēc pievienošanas ejot uz jaunā CPT publisko lapu (piem., /produkts/kaut-kas/) var rādīties 404 - jāatjauno pastāvīgās saites: Iestatījumi → Pastāvīgās saites → Saglabāt (nekas nav jāmaina, pats saglabāšanas klikšķis atjauno noteikumus).

Citi register_post_type() argumenti

rewrite

Masīvs, piem. ['slug' => 'produkti'] - nomaina URL priekšā /produkts/ uz ko citu, nemainot pašu ierakstu tipa nosaukumu kodā.

hierarchical

true = uzvedas kā lapas (var norādīt vecāku, admin sarakstā parādās ar atkāpēm); false = uzvedas kā ieraksti (bez hierarhijas).

menu_position

Skaitlis, kur admin izvēlnē parādās ikona - 5 zem "Ierakstiem", 20 zem "Lapām", 25 zem "Komentāriem" utt.

show_in_menu

true/false, vai virkne ar cita izvēlnes vienuma menu_slug - iegultu CPT kā apakšizvēlni, nevis atsevišķu izvēlnes punktu.

capability_type

Kontrolē, kādas lietotāja tiesības nepieciešamas rediģēšanai/dzēšanai. Noklusējums 'post' ir korekts vairumam gadījumu.

publicly_queryable

Vai ierakstiem var piekļūt tieši caur front-end URL vaicājumiem. Pēc noklusējuma seko public vērtībai.

Skriptu/stilu pieslēgšana

CSS un JS failus tēmā nekad nepievieno tieši ar <link>/<script> tagiem veidnē - tā vietā izmanto wp_enqueue_scripts āķi. Tas ļauj WordPress pašam pārvaldīt failu ielādes secību un izvairīties no konfliktiem, ja vēlāk spraudnis mēģina pievienot to pašu bibliotēku.

php// functions.php
add_action('wp_enqueue_scripts', function() {
    // Tēmas galvenais CSS fails (style.css)
    wp_enqueue_style('mana-tema-style', get_stylesheet_uri());

    // Pielāgots JS fails no tēmas /js/ mapes
    wp_enqueue_script(
        'mana-tema-main',
        get_template_directory_uri() . '/js/main.js',
        [],       // atkarības (piem., ['jquery'])
        '1.0',     // versija (kešošanas atjaunošanai)
        true       // ielādēt lapas beigās, ne <head>
    );
});

Lai šis piemērs strādātu, jāizveido reāls fails js/main.js tēmas mapē - pretējā gadījumā pārlūka konsolē redzēsi 404 kļūdu tam vienam failam (pati vietne turpinās strādāt).

Tailwind CSS kompilēšana (bez CDN)

Tailwind CDN skripts (<script src="https://cdn.tailwindcss.com">) ir domāts tikai izmēģināšanai - tas ģenerē CSS pārlūkā katru reizi no jauna un pats brīdina konsolē: "cdn.tailwindcss.com should not be used in production". Ražošanas vietnei Tailwind jāsakompilē par vienu, mazu, jau gatavu CSS failu. Šeit - pilns ceļš uz strādājošu rezultātu bez Node.js/npm instalēšanas grūtībām (kas uz dažiem serveriem ar root lietotāju var neizdoties atļauju problēmu dēļ) - izmantojot Tailwind Standalone CLI, kas ir viens patstāvīgs izpildfails.

1. Lejupielādē Standalone CLI

Pieslēdzies serverim caur SSH (skat. SSH kategoriju), dodies uz tēmas mapi un izpildi:

bashcurl -sLO https://github.com/tailwindlabs/tailwindcss/releases/latest/download/tailwindcss-linux-x64
chmod +x tailwindcss-linux-x64
mv tailwindcss-linux-x64 tailwindcss

Standalone CLI ietver iekšā visu Tailwind dzinēju - nevajag ne node_modules, ne npm install, ne uztraukties par Node.js versiju vai servera lietotāja tiesībām. Šī lejupielādētā versija ir Tailwind v4, kas atšķiras no v3 - konfigurācija dzīvo CSS failā, nevis atsevišķā tailwind.config.js failā.

2. Izveido/pārraksti avota CSS failu

Tēmas mapē izveido src/input.css. Ja iepriekš tavai CDN versijai bija pielāgota konfigurācija (krāsas, fonti, atstarpes - tailwind.config = {...} CDN formātā), pārceļ to uz jauno @theme bloku:

css@import "tailwindcss";

@theme {

    --font-sans: "Georgia", serif;
    --font-title: "Beau Rivage", cursive;

    /* Atstarpes */
    --spacing-18: 4.5rem;
    --spacing-22: 5.5rem;

    /* Krāsas */
    --color-stone-800: #292524;
    --color-custom-accent: #c8b3d0;
    --color-custom-button-bg: #1e1b4b;
    --color-custom-button-text: #ffffff;

    /* Stūru noapaļojumi */
    --radius-xl: 1rem;
    --radius-2xl: 1.5rem;
}

Tailwind v4 automātiski noskenē visus .php failus tēmas mapē, meklējot izmantotās klases - vairs nav vajadzīga content masīva norādīšana kā v3 versijā. Ja tev jau bija atsevišķs tailwind.config.js fails, to droši var izdzēst - v4 to vairs nelasa.

3. Pievieno kompilēšanas skriptus

package.json failā (ja tāda vēl nav, izveido to ar npm init -y - bet ievēro, ka paketes nosaukumā nedrīkst būt garumzīmes vai lielie burti):

json{
  "scripts": {
    "dev": "./tailwindcss -i ./src/input.css -o ./style.css --watch",
    "build": "./tailwindcss -i ./src/input.css -o ./style.css --minify"
  }
}

4. Palaid kompilatoru

bashnpm run dev

Šī komanda paliek darboties fonā (--watch režīms) un automātiski pārkompilē style.css ikreiz, kad saglabā izmaiņas kādā .php failā. Termināļa logam jāpaliek atvērtam, kamēr programmē; darbu beidz ar Ctrl+C. Pirms lapas publicēšanas palaid npm run build - tas sakompilē mazāku, minificētu versiju bez novērošanas režīma.

5. Aizvieto CDN kodu ar sakompilēto CSS

Atrodi un pilnībā izdzēs veco CDN pieslēgšanu no functions.php:

php// IZDZĒŠAMS - vairs nav vajadzīgs

    wp_enqueue_script( 'tailwind-cdn', 'https://cdn.tailwindcss.com', [], null, true );
    wp_enqueue_script(
        'tailwind-config',
        get_stylesheet_directory_uri() . '/assets/js/tailwind-config.js',
        ['tailwind-cdn'], null, true
    );
}

Un aizvieto ar sakompilētā faila pieslēgšanu - ja izvadi kompilē tieši tēmas style.css, der jau esošais standarta enqueue piemērs augstāk šajā lapā, kas jau ielādē get_stylesheet_uri(). Ja izvadi kompilē uz atsevišķu failu (piem., assets/css/tailwind.css), norādi to tieši:

phpadd_action('wp_enqueue_scripts', function() {
    wp_enqueue_style(
        'tailwind-compiled',
        get_stylesheet_directory_uri() . '/assets/css/tailwind.css',
        [],
        filemtime( get_stylesheet_directory() . '/assets/css/tailwind.css' )
    );
});

Rezultāts: pārlūka konsolē vairs nav "cdn.tailwindcss.com should not be used in production" brīdinājuma, nav 404 kļūdas uz veco config failu, un lapa ielādē tikai to CSS, kas reāli izmantots - mazāks fails, ātrāka ielāde.

Hooks & Filters

Hooks ir WordPress galvenais mehānisms, kā mainīt vai papildināt uzvedību, neaiztiekot kodola failus. Actions ļauj izpildīt savu kodu noteiktā brīdī (piem., lapas ielādes laikā), filters ļauj pārtvert un mainīt vērtību pirms tā tiek izmantota tālāk.

php// Action - pievieno kaut ko pirms </body> tagā (piem., analītikas skriptu)
add_action('wp_footer', function() {
    echo '<!-- Šis teksts parādās katras lapas HTML kodā pirms </body> -->';
});

// Filter - maina ieraksta virsrakstu pirms tas tiek attēlots
add_filter('the_title', function($title) {
    return '★ ' . $title;
});

Pēc šī koda pievienošanas functions.php failā un lapas atsvaidzināšanas - katra ieraksta virsraksts sāksies ar "★ ", un pārlūka izejas kodā (View Source) redzēsi jauno komentāru pirms </body>.

Biežākie āķi, ar kuriem sāksi: init (WordPress ielādēts), wp_enqueue_scripts (CSS/JS), wp_head/wp_footer (lapas sākums/beigas).

Kur atrast VISUS pieejamos hooks? - šeit parādīti tikai daži piemēri no simtiem, kas eksistē WordPress kodolā. Pilns, meklējams saraksts ar katra hook aprakstu un pieejamajiem parametriem ir developer.wordpress.org/reference/hooks/ - tā ir oficiālā WordPress dokumentācija, ne kāda trešās puses vietne. Tur pat var redzēt, kurā WordPress versijā konkrētais hook parādījās.

Tā pati vietne (developer.wordpress.org/reference/) satur arī pilnu WordPress funkciju uzziņu (piem., ko tieši dara get_post_meta(), kādi tai parametri) - tas ir pareizais pirmais pieturas punkts, ja neesi drošs, ko konkrēta WordPress funkcija dara vai vai tāda vispār eksistē priekš tavas vajadzības, nevis meklēt Google pēc nejaušiem forumu ierakstiem.

AJAX pamati

AJAX ļauj lapai apmainīties ar datiem ar serveri bez pilnas pārlādēšanas (piem., "Ielādēt vairāk" poga). WordPress visiem AJAX pieprasījumiem izmanto vienu kopīgu galapunktu - admin-ajax.php. PHP pusē reģistrē divus āķus ar vienādu vārdu: wp_ajax_{action} ielogotiem lietotājiem, wp_ajax_nopriv_{action} - pārējiem.

php// 1) Nododam JS pusei ajax_url un nonce
add_action('wp_enqueue_scripts', function() {
    wp_enqueue_script('mana-tema-main', get_template_directory_uri() . '/js/main.js', [], '1.0', true);
    wp_localize_script('mana-tema-main', 'MyAjax', [
        'ajax_url' => admin_url('admin-ajax.php'),
        'nonce'    => wp_create_nonce('my_ajax_nonce'),
    ]);
});

// 2) Apstrādājam pieprasījumu servera pusē
add_action('wp_ajax_paskaitit',        'mana_tema_paskaitit');
add_action('wp_ajax_nopriv_paskaitit', 'mana_tema_paskaitit');

function mana_tema_paskaitit(): void {
    if (!wp_verify_nonce($_POST['nonce'] ?? '', 'my_ajax_nonce')) {
        wp_send_json_error(['message' => 'Drošības kļūda']);
    }
    $a = (int) ($_POST['a'] ?? 0);
    $b = (int) ($_POST['b'] ?? 0);
    wp_send_json_success(['summa' => $a + $b]);
}
js// js/main.js - pieprasījums no pārlūka puses
fetch(MyAjax.ajax_url, {
  method: 'POST',
  body: new URLSearchParams({ action: 'paskaitit', nonce: MyAjax.nonce, a: 2, b: 3 }),
})
  .then(res => res.json())
  .then(data => console.log(data.data.summa)); // 5

fetch()

Pārlūkā iebūvēta funkcija tīkla pieprasījumu sūtīšanai - WordPress kontekstā ar to nosūta datus uz admin-ajax.php bez lapas pārlādēšanas. Atgriež Promise (solījumu par vēlāku atbildi), tāpēc lieto ar .then().

new URLSearchParams(objekts)

Pārlūka iebūvēta klase, kas parastu JS objektu pārvērš formā, ko servera $_POST spēj nolasīt tieši (tas pats formāts, ko sūta parasta HTML forma). Bez tās fetch() nosūtītu JSON tekstu, ko $_POST nesaprastu.

res.json()

res ir servera atbilde no fetch(). .json() pārvērš to no jēla teksta par lietojamu JS objektu - arī tas atgriež Promise, tāpēc seko vēl viens .then(), lai piekļūtu jau pārveidotajiem datiem.

Tulkošana (i18n)

Ja tēma vai spraudnis paredzēts izplatīšanai (arī citiem lietotājiem, ne tikai vienai vietnei), visi lietotājam redzamie teksti jāietver tulkošanas funkcijās - tas ļauj vēlāk pievienot jebkuru valodu bez koda maiņas.

1. solis - reģistrē "text domain" (unikālu identifikatoru tulkojumiem):

phpadd_action('after_setup_theme', function() {
    load_theme_textdomain('mana-tema', get_template_directory() . '/languages');
});

2. solis - ietver katru redzamo tekstu attiecīgajā funkcijā (otrais parametrs vienmēr ir text domain no 1. soļa):

php// Atgriež tulkoto tekstu (jāizmanto echo/turpmākai apstrādei)
$teksts = __('Sveiki, pasaule!', 'mana-tema');

// Uzreiz izvada tulkoto tekstu (saīsinājums echo __(...))
_e('Sveiki, pasaule!', 'mana-tema');

// Apvieno tulkošanu ar drošu HTML izvadi - visbiežāk lietotā kombinācija veidnēs
echo esc_html__('Sveiki, pasaule!', 'mana-tema');

Pašus tulkojumus glabā .po/.mo failos languages mapē - tos ģenerē un rediģē ar rīkiem kā Poedit, kas nolasa kodā izmantotos __()/_e() izsaukumus un veido no tiem tulkojamo tekstu sarakstu.

Drošība: nonce & escaping

Divi drošības jēdzieni, kas jāzina no paša sākuma. Escaping - izvadot jebkādus datus HTML, izmanto esc_html()/esc_attr(), lai novērstu XSS (kāds ievieto ļaunprātīgu <script> tagu, kas izpildās citu apmeklētāju pārlūkos). Nonce - formas, kas maina datus, aizsargā ar vienreizēju "biļeti", kas apliecina, ka pieprasījums patiešām nāk no tavas lapas.

php// Veidnē - droša izvade
echo esc_html($lietotaja_teksts);

// Formā - pievieno slēptu, unikālu lauku
<form method="post">
    <?php wp_nonce_field('mana_darbiba', 'mans_nonce'); ?>
    <input type="text" name="komentars">
    <button type="submit">Sūtīt</button>
</form>

// Apstrādājot formu - vispirms pārbauda nonce
<?php
if (!wp_verify_nonce($_POST['mans_nonce'] ?? '', 'mana_darbiba')) {
    die('Drošības pārbaude neizdevās');
}
// ... šeit droši apstrādā $_POST['komentars']

Sanitizācija: ievades attīrīšana

Escaping (iepriekš) padara datus drošus izvadei. Sanitizācija ir cits solis - padara lietotāja ievadītos datus drošus saglabāšanai, noņemot vai pārveidojot nevēlamu saturu, pirms tas nonāk datubāzē.

php// Atļauj tikai konkrētus HTML tagus/atribūtus, pārējo izfiltrē - noder,
// kad lietotājam jāļauj neliels formatējums (piem., komentāros)
$atlautie_tagi = [
    'a'      => ['href' => true, 'title' => true],
    'strong' => [],
    'em'     => [],
];
echo wp_kses($lietotaja_html, $atlautie_tagi);

// Citas bieži lietotas sanitizācijas funkcijas pēc datu veida
sanitize_email($_POST['epasts']);
sanitize_key($_POST['id']);            // tikai mazie burti, cipari, "-", "_"
absint($_POST['skaits']);           // piespiedu kārtā pozitīvs vesels skaitlis
sanitize_textarea_field($_POST['zinojums']);

Vienkāršs likums: sanitizē pie ievades (pirms saglabā datubāzē), escapē pie izvades (tieši pirms echo). Dari abus - nepaļaujies, ka viens aizstāj otru.

$wpdb vaicājumi

Kad WP_Query nesniedz vajadzīgo elastību (piem., savai, pielāgotai datubāzes tabulai), globālais $wpdb objekts ļauj rakstīt SQL tieši. Lietotāja ievadi nekad nesalīmē tieši vaicājuma tekstā - vienmēr izmanto $wpdb->prepare().

phpglobal $wpdb;

// Droši - vērtība tiek automātiski attīrīta
$rezultati = $wpdb->get_results(
    $wpdb->prepare("SELECT * FROM {$wpdb->prefix}atsauksmes WHERE vertejums >= %d", 4)
);

foreach ($rezultati as $rinda) {
    echo esc_html($rinda->teksts);
}

{$wpdb->prefix} automātiski ievieto pareizo tabulu prefiksu (parasti wp_, bet var atšķirties) - nekad nehardkodē wp_ tieši.

Šis piemērs pieņem, ka tabula {$wpdb->prefix}atsauksmes jau eksistē datubāzē - $wpdb tikai vaicā esošai tabulai, tas neko neizveido. Pašu tabulu parasti izveido vienreiz, spraudņa aktivizācijas brīdī, ar WordPress dbDelta() funkciju. Šo konkrēto vaicājuma-un-cikla bloku liec jebkur, kur jāizvada rezultāts, - templatē (piem., page-atsauksmes.php), shortcode funkcijā vai AJAX apstrādātājā.

Options API

Vienkāršākais un biežāk lietotais veids, kā saglabāt vietnes iestatījumus - WordPress tos glabā wp_options tabulā kā atslēga-vērtība pārus. Ideāli piemērots tēmas/spraudņa iestatījumiem, kur nav vajadzīga sarežģīta datu struktūra.

php// Saglabā vai pārraksta vērtību
update_option('mana_tema_krasa', '#ff0000');

// Nolasa vērtību - otrais parametrs ir noklusējums, ja opcija vēl neeksistē
$krasa = get_option('mana_tema_krasa', '#000000');

// Pievieno tikai tad, ja opcija vēl neeksistē (update_option pārraksta vienmēr)
add_option('mana_tema_versija', '1.0');

// Izdzēš opciju pilnībā
delete_option('mana_tema_versija');

update_option() un add_option() pieņem arī trešo parametru $autoload (true/false). Ar true (noklusējums) opcija tiek ielādēta katrā lapas pieprasījumā - der biežai lietošanai. Retāk vajadzīgām, lielām vērtībām iestati false, lai nepalēninātu katru lapas ielādi.

Pilns piemērs: no kurienes vērtība rodas un kur tā tiek izmantota

Augstākie piemēri parāda tikai atsevišķas funkcijas - paši par sevi tie nav gatava, strādājoša loģika, jo trūkst konteksta: kas izsauc update_option() un kad, un kur tieši get_option() rezultāts nonāk. Reālā vietnē tas parasti izskatās pēc šādas ķēdes:

1. Admins aizpilda formu

Iestatījumu lapā WordPress admin panelī (Iestatījumi → Tēmas iestatījumi) ievada, piemēram, krāsu, un nospiež "Saglabāt".

2. PHP saglabā to

Tā pati funkcija, kas izvada formu, pārbauda, vai tā tikko iesniegta, un izsauc update_option() - dati nonāk wp_options tabulā.

3. Tēma to nolasa un lieto

Jebkurā citā vietā - šeit header.php - get_option() nolasa saglabāto vērtību no datubāzes un izmanto to reālajā HTML/CSS izvadē.

1.-2. solis - jauna admin izvēlnes lapa ar formu, kas pati sevi saglabā (pievieno functions.php):

php// Reģistrē jaunu lapu zem "Iestatījumi" izvēlnes
add_action('admin_menu', function() {
    add_options_page(
        'Mana tēmas iestatījumi',      // <title> lapas cilnē
        'Tēmas iestatījumi',           // teksts izvēlnē
        'manage_options',              // nepieciešamā tiesība
        'mana-tema-iestatijumi',       // lapas slug (?page=...)
        'mana_tema_iestatijumu_lapa'  // funkcija, kas izvada HTML
    );
});

function mana_tema_iestatijumu_lapa(): void {
    if (!current_user_can('manage_options')) {
        return;
    }

    // === ŠEIT SAGLABĀ === ja forma tikko iesniegta, saglabā jauno vērtību
    if (
        isset($_POST['mana_tema_krasa_nonce']) &&
        wp_verify_nonce($_POST['mana_tema_krasa_nonce'], 'mana_tema_saglabat')
    ) {
        update_option('mana_tema_krasa', sanitize_hex_color($_POST['mana_tema_krasa'] ?? ''));
        echo '<div class="updated"><p>Saglabāts!</p></div>';
    }

    // === ŠEIT NOLASA === pašreizējo vērtību, lai parādītu formā jau ievadītu
    $saglabata_krasa = get_option('mana_tema_krasa', '#0073aa');
    ?>
    <div class="wrap">
        <h1>Tēmas iestatījumi</h1>
        <form method="post">
            <?php wp_nonce_field('mana_tema_saglabat', 'mana_tema_krasa_nonce'); ?>
            <label for="mana_tema_krasa">Galvenā krāsa</label>
            <input type="color" name="mana_tema_krasa" id="mana_tema_krasa"
                   value="<?php echo esc_attr($saglabata_krasa); ?>">
            <?php submit_button(); ?>
        </form>
    </div>
    <?php
}

3. solis - tēmas header.php (vai jebkurā citā failā) nolasa TO PAŠU opciju un izmanto to reālajā izvadē:

php// === ŠEIT NOLASA === tā pati opcija, ko saglabāja admin panelī augstāk
<?php $krasa = get_option('mana_tema_krasa', '#0073aa'); ?>
<style>
    a { color: <?php echo esc_html($krasa); ?>; }
</style>

Svarīgākais: 'mana_tema_krasa' ir vienkārši teksts (opcijas nosaukums) - WordPress to nesaista automātiski ne ar vienu konkrētu formu vai lapu. Saikne pastāv tikai tāpēc, ka tu pats lieto to pašu virkni gan tur, kur saglabā (update_option), gan tur, kur nolasi (get_option). Ja kaut kur uzraksti citu nosaukumu (piem., 'temas_krasa' nevis 'mana_tema_krasa'), savienojums pazūd un get_option() vienkārši atgriezīs noklusējuma vērtību.

Šis piemērs saglabā formu ar "roku" (manuāla $_POST pārbaude + nonce) - der, lai skaidri redzētu, kas notiek. Sarežģītākām iestatījumu lapām (vairāki lauki, validācija) WordPress iesaka iebūvēto Settings API (register_setting(), add_settings_field()) - tā automātiski apstrādā saglabāšanu un validāciju, bet slēpj vairāk no augstāk redzamās plūsmas aiz WordPress iekšējiem izsaukumiem.

Tas pats piemērs ar Settings API

Precīzi tā pati funkcionalitāte (viena krāsas opcija mana_tema_krasa), bet saglabāšanu, nonce pārbaudi un sanitizāciju tagad dara WordPress pati - tev jāapraksta tikai kas jāsaglabā, nevis kā:

php// 1) Reģistrē opciju + sekciju + lauku - viss vienā "admin_init" āķī
add_action('admin_init', function() {

    );

    );

    add_settings_field(
        'mana_tema_krasa_lauks',

        'mana_tema_sekcija'
    );
});

// 2) Admin izvēlnes lapa - tas pats, kas manuālajā piemērā augstāk
add_action('admin_menu', function() {
    add_options_page(
        'Mana tēmas iestatījumi', 'Tēmas iestatījumi', 'manage_options',

});

    }
    ?>

Front-end pusē (piem., header.php) nekas nemainās - get_option('mana_tema_krasa', '#0073aa') paliek tieši tāds pats kā manuālajā piemērā, jo abas versijas saglabā datus tajā pašā wp_options ierakstā.

Forma sūta uz options.php

Nevis pati uz sevi (kā manuālajā versijā) - options.php ir WordPress kodola fails, kas pārbauda nonce, izsauc sanitize_callback un pats izsauc update_option() par tevi.

Automātisks paziņojums

Pēc veiksmīgas saglabāšanas options.php novirza atpakaļ uz iestatījumu lapu ar ?settings-updated=true - WordPress pati parāda standarta zaļo "Iestatījumi saglabāti." paziņojumu, nav jāraksta pašam.

sanitize_callback

Izsaukts automātiski PIRMS saglabāšanas - aizstāj manuālo sanitize_hex_color() izsaukumu no $_POST apstrādes pusē pilnībā.

Viens punkts, kas bieži mulsina: add_settings_field() callback drukā HTML tieši ar echo, nevis to atgriež (return) - tas atšķiras no citām WordPress konvencijām (piem., shortcodes, kur return ir obligāts). Ja aizmirsti echo un uzraksti return tā vietā, lauks admin panelī vienkārši būs tukšs, bez kļūdas paziņojuma.

Transients (kešošana)

Transients ir pagaidu vērtība ar derīguma termiņu - glabājas datubāzē (vai kešošanas sistēmā, ja tāda uzstādīta). Pamatproblēma, ko tas risina: dažas darbības ir lēnas vai dārgas (ārējs API izsaukums, sarežģīts vaicājums pa tūkstošiem ierakstu), bet WordPress veidnes kods izpildās no jauna katram apmeklētājam, katrai lapas ielādei. Bez kešošanas 1000 apmeklētāju stundā nozīmētu 1000 identiskus, lēnus izsaukumus - ar transientu tas notiek vienreiz, un pārējie 999 saņem jau gatavu, saglabātu rezultātu.

Kad tas reāli noder

🌐 Ārējs API izsaukums

Valūtas kurss, laika ziņas, GitHub zvaigžņu skaits, Instagram plūsma - jebkas, kas nāk no cita servera un nemainās katru sekundi. Bez kešošanas katra lapas ielāde gaidītu uz svešu serveri.

🐌 Smags datubāzes vaicājums

Piem., "10 komentētākie raksti šomēnes" - vaicājums, kas skaita cauri tūkstošiem komentāru. Rezultāts sekundi vecs nekaitē, bet vaicājums katrā ielādē gan.

🚦 Ierobežojums (rate limiting)

Piem., neļauj vienam IP nosūtīt kontaktformu biežāk kā reizi minūtē - transients ar IP kā atslēgu un īsu derīgumu darbojas kā vienkāršs "vai šis jau nesen noticis?" pārbaudītājs.

🔔 Vienreizējs admin paziņojums

Piem., "Spraudnis aktivizēts!" josla, kas jārāda tikai vienu reizi pēc aktivizācijas, ne katrā admin lapā mūžīgi - transients ar īsu derīgumu kalpo kā pagaidu karodziņš.

Pilns, reāls piemērs - GitHub zvaigžņu skaits

Šis apvieno jau iepriekš mācīto HTTP API ar transientu - bez kešošanas katra lapas ielāde sūtītu pieprasījumu uz GitHub, kas gan lēni, gan riskanti (GitHub ierobežo, cik reizes stundā drīkst vaicāt bez autorizācijas):

phpfunction iegut_github_zvaigznes(string $repo): int {
    $transienta_atslega = 'github_zvaigznes_' . sanitize_key($repo);

    // 1) Vispirms mēģina paņemt no kešatmiņas
    $saglabats = get_transient($transienta_atslega);
    if ($saglabats !== false) {
        return (int) $saglabats;
    }

    // 2) Nav kešatmiņā (vai termiņš beidzies) - jāizsauc ārējais API
    $atbilde = wp_remote_get("https://api.github.com/repos/{$repo}");

    if (is_wp_error($atbilde)) {
        return 0; // tīkla kļūda - der atgriezt drošu noklusējumu, ne izmest kļūdu
    }

    $dati       = json_decode(wp_remote_retrieve_body($atbilde), true);
    $zvaigznes = (int) ($dati['stargazers_count'] ?? 0);

    // 3) Saglabā uz 6 stundām - nākamie apmeklētāji šai laikā API vispār neskars
    set_transient($transienta_atslega, $zvaigznes, 6 * HOUR_IN_SECONDS);

    return $zvaigznes;
}

// Lietošana veidnē: <?php echo iegut_github_zvaigznes('wordpress/wordpress'); ?>

Trīs soļi vienmēr atkārtojas: (1) mēģini paņemt no kešatmiņas ar get_transient(), (2) ja false - dari to lēno darbu, (3) saglabā rezultātu ar set_transient(), lai nākamreiz atkal netiktu pie 2. soļa. get_transient() atgriež tieši false (nevis null vai tukšu virkni), kad transienta nav vai tas beidzies - tāpēc pārbauda ar !== false, nevis vienkārši if (!$saglabats), jo pati saglabātā vērtība varētu būt 0 vai tukša virkne, kas arī novērtētos kā "nepatiess".

Derīguma termiņš (HOUR_IN_SECONDS, DAY_IN_SECONDS u.c. - WordPress iebūvētas konstantes) jāizvēlas pēc tā, cik "svaigi" dati patiešām nepieciešami: valūtas kursam derētu stunda, "populārāko rakstu" sarakstam - diena, bet lietotāja sesijas datiem transients nav piemērots vispār (tam der $_SESSION vai cookies). Ja termiņš pārāk īss, kešošanai nav jēgas (API tik un tā izsaucas gandrīz katru reizi); ja pārāk garš, apmeklētāji redz novecojušu informāciju.

Cron uzdevumi

WordPress Cron nav īsts servera cron - tas ieplānoto uzdevumu pārbauda un izpilda tikai tad, kad kāds apmeklē vietni. Vienmēr vispirms pārbaudi ar wp_next_scheduled(), vai uzdevums jau nav ieplānots, citādi katrā aktivizācijā izveidosi dublikātus.

php// Ieplāno uzdevumu, ja tas vēl nav ieplānots
if (!wp_next_scheduled('mana_tema_dienas_uzdevums')) {
    wp_schedule_event(time(), 'daily', 'mana_tema_dienas_uzdevums');
}

// Pieslēdz reālo funkciju šim āķim
add_action('mana_tema_dienas_uzdevums', function() {
    // piem., iztīra vecus pagaidu ierakstus
});

Zemapmeklētai vietnei WP-Cron var kavēties (nav apmeklētāju = nav trigera). Ražošanas vietnēm bieži atspējo iebūvēto sistēmu (define('DISABLE_WP_CRON', true) failā wp-config.php) un aizstāj ar īstu servera cron, kas ik minūti izsauc wp-cron.php.

Reāls cron caur Plesk - ja hostings ir Plesk (vai līdzīgs panelis), servera cron var iestatīt bez SSH, tieši panelī:

text1. Plesk paneli: Websites & Domains → tava vietne → Scheduled Tasks
2. "Add Task" → izvēlies tipu "Run a command"
3. Norāda komandu (izvēlies VIENU no divām):

   a) Ar wget (visbiežāk der, ja PHP CLI nav pieejams):
      wget -q -O /dev/null "https://tavavietne.lv/wp-cron.php?doing_wp_cron"

   b) Tieši ar PHP CLI (ātrāk, apiet HTTP pieprasījumu pavisam):
      php /var/www/vhosts/tavavietne.lv/httpdocs/wp-cron.php

4. Biežums: izvēlies "Every 15 minutes" (parasti pietiek,
   nevis katru minūti kā komandrindas piemērā augstāk)
5. Saglabā - Plesk pats izveido servera crontab ierakstu fonā

Neaizmirsti soli 1 no augšas - DISABLE_WP_CRON konstante wp-config.php failā - pretējā gadījumā uzdevumi izpildīsies divreiz: reizi no Plesk ieplānotā uzdevuma, reizi no WordPress pašas pseido-cron sistēmas, kad kāds apmeklētājs atver lapu. Ja tavā serverī ir SSH pieeja un vēlies to pašu izdarīt caur termināli (crontab -e), pilns piemērs ir SSH dokumentācijā.

HTTP API (wp_remote_*)

Kad PHP kodam jāizsauc ārējs API (maksājumu serviss, laika ziņas, cita vietne), WordPress iesaka izmantot iebūvēto HTTP API, nevis tiešu cURL - tas automātiski ievēro servera starpniekservera (proxy) iestatījumus un WordPress filtrus, un vienādi strādā visos hostingos.

php// GET pieprasījums
$atbilde = wp_remote_get('https://api.piemers.lv/dati', [
    'timeout' => 10, // sekundes - noklusējums (5s) bieži par īsu lēnākiem API
]);

// VIENMĒR vispirms pārbauda, vai pats pieprasījums neizdevās (tīkla kļūda u.c.)
if (is_wp_error($atbilde)) {
    error_log($atbilde->get_error_message());
    return;
}

$body = wp_remote_retrieve_body($atbilde);
$dati = json_decode($body, true);

POST pieprasījumam ar datiem un galvenēm:

php$atbilde = wp_remote_post('https://api.piemers.lv/pasutijumi', [
    'headers' => ['Content-Type' => 'application/json'],
    'body'    => json_encode(['summa' => 49.99]),
]);

is_wp_error() pārbauda tikai to, vai pieprasījums tehniski izdevās (sasniedza serveri). Pat veiksmīga savienojuma gadījumā serveris var atbildēt ar kļūdas statusa kodu (404, 500) - to pārbauda atsevišķi ar wp_remote_retrieve_response_code($atbilde).

REST API pamati

WordPress jau nāk ar iebūvētu REST API - bez papildu koda ieraksti pieejami kā JSON adresē /wp-json/wp/v2/posts. Savus, pielāgotus galapunktus izveido ar register_rest_route().

textGET /wp-json/wp/v2/posts        → visi publicētie ieraksti kā JSON
GET /wp-json/wp/v2/posts/5      → viens ieraksts (ID=5)
GET /wp-json/wp/v2/produkts     → CPT ieraksti (ja show_in_rest: true)
phpadd_action('rest_api_init', function() {
    register_rest_route('mana-tema/v1', '/sveiciens', [
        'methods'  => 'GET',
        'callback' => function() {
            return ['teksts' => 'Sveiki no pielāgota REST galapunkta!'];
        },
        'permission_callback' => '__return_true', // publiski pieejams
    ]);
});
// Pieejams: /wp-json/mana-tema/v1/sveiciens

JSON kodēšana/dekodēšana

JSON ir teksta formāts datu apmaiņai - to izmanto REST API atbildes, AJAX pieprasījumi un ārējo servisu izsaukumi (skat. augstāk). PHP pusē datu pārvēršanu uz/no JSON dara json_encode()/json_decode(), taču WordPress kodā priekšroka jādod savietojamajam wp_json_encode().

wp_json_encode() pret json_encode()

php$dati = [
    'nosaukums' => 'Kafijas tase',
    'cena'      => 12.50,
    'pieejams'  => true,
];

$json = wp_json_encode($dati);
// {"nosaukums":"Kafijas tase","cena":12.5,"pieejams":true}

wp_json_encode() uzvedas tāpat kā json_encode(), bet ir filtrējams (wp_json_encode_options filtrs) un pareizi apstrādā datus, kas nāk no vecāku WordPress instalāciju datubāzēm ar nekonsekventu UTF-8 kodējumu - gadījumos, kad tīrs json_encode() klusi atgrieztu false. Praktiski: WordPress kodā vienmēr izmanto wp_json_encode(), plain json_encode() patur ārpus-WordPress PHP kodam.

Dekodēšana atpakaļ uz PHP masīvu

php$json = '{"nosaukums":"Kafijas tase","cena":12.5}';

$dati = json_decode($json, true); // true = asociatīvs masīvs, nevis stdClass objekts

echo $dati['nosaukums']; // Kafijas tase

Bez otrā parametra true, json_decode() atgriež stdClass objektu (piekļuve ar ->, piem. $dati->nosaukums), nevis masīvu ([]) - WordPress kods gandrīz vienmēr sagaida masīvu, tāpēc true aizmirst ir bieža kļūdas cēlonis. Ja pats JSON teksts ir nederīgs, json_decode() klusi atgriež null - pārbaudi ar json_last_error() !== JSON_ERROR_NONE, ja jāatšķir "nederīgs JSON" no "derīgs JSON, kas satur null".

Strukturētu datu glabāšana kā JSON teksts

WordPress update_option()/update_post_meta() masīvus automātiski saglabā ar PHP serialize(), nevis JSON - tāpēc parasti nav obligāti pašam kodēt JSON, lai saglabātu masīvu. Manuāla JSON kodēšana der, kad dati jālasa arī ārpus WordPress/PHP (citam skriptam, tiešam SQL vaicājumam datubāzē) vai jāpaliek cilvēkam lasāmi datubāzē:

phpupdate_option('uznemuma_dati', wp_json_encode([
    'nosaukums'        => 'SIA Piemērs',
    'registracijas_nr' => '40001234567',
]));

// Nolasot atpakaļ vēlāk
$uznemuma_dati = json_decode(get_option('uznemuma_dati'), true);
echo $uznemuma_dati['nosaukums'];

Ienākoša JSON pieprasījuma nolasīšana (webhook)

Ārējie servisi (maksājumu sistēmas, automatizācijas rīki) bieži sūta webhook paziņojumus kā tīru JSON tekstu pieprasījuma "body", nevis parastu formas datu formātā - tādā gadījumā $_POST paliks tukšs. REST API galapunktā to nolasa ar get_json_params():

phpadd_action('rest_api_init', function() {
    register_rest_route('mana-tema/v1', '/webhook', [
        'methods'  => 'POST',
        'callback' => function( WP_REST_Request $request ) {
            $dati = $request->get_json_params(); // jau automātiski dekodēts asociatīvs masīvs

            error_log(print_r($dati, true));
            return ['status' => 'ok'];
        },
        'permission_callback' => '__return_true',
    ]);
});

Ārpus REST API (piem., vecākā stila admin-ajax.php galapunktā) to pašu izdara manuāli:

php$raw  = file_get_contents('php://input');
$dati = json_decode($raw, true);

Ja debugojot pamani, ka $_POST ir tukšs masīvs, kaut sūtītājs apgalvo, ka dati nosūtīti - pirmā aizdoma vienmēr jābūt, ka dati nāk kā JSON body (Content-Type: application/json), nevis application/x-www-form-urlencoded. AJAX/fetch pieprasījumu ar JS pusi skat. AJAX pamati augstāk, ārēju API izsaukšanu ar wp_remote_* - HTTP API. JS pusē JSON.stringify()/JSON.parse() skaidrots JavaScript → JSON.

Ātruma mērīšana (Core Web Vitals rīki)

Ko tieši nozīmē LCP, INP un CLS, skaties SEO → Core Web Vitals. Šī sadaļa fokusējas uz kur tos pārbaudīt un kā pareizi interpretēt rezultātus WordPress vietnei.

Field Data pret Lab Data - vissvarīgākā atšķirība

📊 Field Data (reālie dati)

Savākti no īstiem apmeklētājiem pēdējo 28 dienu laikā (Chrome User Experience Report). Tas ir tas, ko Google izmanto ranžēšanai. Mazām vietnēm ar maz trafika šo datu var vēl nebūt ("Not enough data").

🧪 Lab Data (laboratorijas dati)

Viena simulēta lapas ielāde uz vienas, fiksētas ierīces/interneta ātruma. Pieejama uzreiz, ideāla, lai atrastu konkrētu problēmu un pārbaudītu, vai labojums palīdzēja - bet var atšķirties no tā, ko reāli redz apmeklētāji.

Kur pārbaudīt

1. Google Search Console

Sadaļa "Core Web Vitals" - rāda reālos (field) datus, sagrupētus pa līdzīgu lapu grupām. Šeit redzi tieši to, kas ietekmē ranžošanu - sāc pārbaudi vienmēr no šejienes.

2. PageSpeed Insights

pagespeed.web.dev - ielīmē URL, uzreiz redzi gan field, gan lab datus vienā vietā, plus konkrētus, prioritizētus ieteikumus katrai problēmai.

3. Chrome DevTools → Lighthouse

F12 → cilne "Lighthouse" → "Analyze page load". Lokāls lab tests bez interneta gaidīšanas - ideāls, lai ātri pārbaudītu, vai tikko izdarītā izmaiņa tiešām palīdzēja.

4. web-vitals bibliotēka

Pašam savākt reālo lietotāju datus tieši savā vietnē (piem., nosūtot uz analītiku). Pilns koda piemērs: SEO → Core Web Vitals.

WordPress: kā atrast, kas tieši bremzē

Minēt ir bezjēdzīgi - uzstādi Query Monitor spraudni, kas katrai lapas ielādei rāda tieši, kurš spraudnis, veidne vai datubāzes vaicājums patērē visvairāk laika:

bashwp plugin install query-monitor --activate

🔁 Trūkstoša kešošana

Biežākais cēlonis. Skat. Problēmas → Lēna WordPress vietne konkrētiem SSH labojumiem.

🧱 Page builder bloāts

Elementor, Divi u.c. bieži katrai lapai ģenerē savu, smagu CSS/JS failu - pārbaudi, vai builderim ir "optimizācijas" iestatījumi (neizmantotā CSS noņemšana).

🖼️ Neoptimizēti attēli

Skat. SEO → Attēlu optimizācija - srcset, loading="lazy", pareizi izmēri.

🐌 Lēns hosting (augsts TTFB)

Ja pat tukša lapa ielādējas lēni, problēma nav WordPress kodā - pārbaudi servera atbildes laiku (Time to First Byte) atsevišķi no pārējiem rādītājiem.

Ieteicamā secība: (1) PageSpeed Insights vai Lighthouse - noskaidro, kura konkrētā metrika (LCP/INP/CLS) ir sliktākā; (2) Query Monitor - atrod konkrēto vainīgo spraudni/vaicājumu; (3) labo tieši to; (4) pārbaudi vēlreiz ar to pašu rīku, lai apstiprinātu uzlabojumu. Neoptimizē "aklu" - vienmēr izmēri pirms un pēc.
