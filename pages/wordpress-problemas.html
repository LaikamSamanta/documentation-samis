Sākums WordPress Problēmas

WordPress kļūdas un problēmu risinājumi

Biežākās WordPress kļūdas — iespējamie cēloņi un pilns risinājums katrai, galvenokārt caur SSH (WP-CLI, MySQL, failu tiesības), ar alternatīvu risinājumu caur failiem (FTP, phpMyAdmin), ja SSH piekļuves nav. Pamatus par tēmām, hooks un WP_Query skaties pilnajā WordPress dokumentācijā.

Lielākā daļa SSH risinājumu šajā lapā izmanto WP-CLI — WordPress oficiālo komandrindas rīku. Ja tas serverī vēl nav uzstādīts, sāc ar sadaļu "WP-CLI uzstādīšana" zemāk.

Nevar pieslēgties wp-admin

Aizmirsta parole vai bloķēts konts nozīmē, ka nevar izmantot parastu "Aizmirsu paroli" plūsmu admin panelī, jo tas pats admin panelis nav pieejams. Risinājums ir mainīt paroli tieši, apejot pieteikšanās formu.

🔑 Aizmirsta parole

E-pasts ar atiestatīšanas saiti nepienāk vai konts nav zināms.

🚫 Konts bloķēts

Drošības spraudnis (piem., pēc vairākiem neveiksmīgiem mēģinājumiem) bloķējis IP vai lietotāju.

Risinājums caur SSH — ar WP-CLI parole tiek nomainīta uzreiz, bez e-pasta:

bash# Pieslēdzies serverim un pāriet uz WordPress mapi
cd /var/www/piemers.lv

# Uzskaita lietotājus, lai atrastu pareizo lietotājvārdu
wp user list

# Iestata jaunu paroli konkrētam lietotājam
wp user update admins --user_pass="JaunaDrosaParole123!"

# Ja bloķēts drošības spraudņa dēļ — deaktivizē to pagaidām
wp plugin deactivate wordfence

Alternatīva caur failiem (bez SSH, ar phpMyAdmin): datubāzē atver wp_users tabulu, atrodi lietotāja rindu, laukā user_pass ievadi jaunu paroli un izvēlies funkciju MD5 nolaižamajā sarakstā pirms saglabāšanas — WordPress šifrē paroles ar MD5 apvalkotu hash, tāpēc tekstu nedrīkst ierakstīt "kā ir".

Ja arī phpMyAdmin/datubāze nav pieejama, pievieno pagaidu kodu wp-config.php failam: wp_set_password('JaunaParole', 1); — izpilda vienreiz jebkurā WordPress lapā, tad uzreiz izdzēs šo rindu, citādi parole tiks atiestatīta katru reizi.

Balta lapa (White Screen of Death)

Vietne rāda pilnīgi tukšu, baltu lapu — bez jebkādas kļūdas, bez satura. Tas nozīmē PHP fatālu kļūdu, kas noticis pirms izvades sākuma, un WordPress noklusējuma iestatījumi kļūdu paziņojumus paslēpj apmeklētājiem drošības apsvērumu dēļ.

Risinājums caur SSH — vispirms padari kļūdas redzamas žurnālā:

bash# wp-config.php — pārliecinies, ka ir šīs rindas (parasti jau ir tuvu faila beigām)
grep WP_DEBUG wp-config.php

# Skaties kļūdu žurnālu tiešraidē, kamēr atsvaidzini lapu pārlūkā
tail -f wp-content/debug.log
php// wp-config.php — ieslēdz kļūdu pierakstīšanu failā (nevis rādīšanu apmeklētājiem)
define('WP_DEBUG', true);
define('WP_DEBUG_LOG', true);
define('WP_DEBUG_DISPLAY', false);

Žurnālā redzamā kļūda gandrīz vienmēr norāda tieši uz vainīgo failu un rindu — visbiežāk tas ir spraudnis vai tēma, kas lieto novecojušu PHP funkciju vai kuram trūkst atkarības.

Alternatīva caur failiem (bez SSH): FTP klientā pārsauc wp-content/plugins mapi par, piem., plugins-old — WordPress automātiski deaktivizē visus spraudņus, ja to mape nav atrodama. Ja lapa atkal parādās, pārsauc mapi atpakaļ un deaktivizē spraudņus pa vienam admin panelī, lai atrastu vainīgo.

"There has been a critical error"

Jaunākas WordPress versijas (5.2+) baltās lapas vietā rāda šo ziņojumu ar norādi pārbaudīt e-pastu vai admin paneli — tas ir uzlabojums pār pilnīgi tukšo lapu, bet pati diagnostika ir tāda pati kā WSOD gadījumā.

Risinājums caur SSH — atrodi konkrēto spraudni ar WP-CLI, neatslēdzot visus uzreiz:

bash# Uzskaita aktīvos spraudņus
wp plugin list --status=active

# Deaktivizē visus uzreiz (drošākais pirmais solis)
wp plugin deactivate --all

# Tad aktivizē pa vienam, pārbaudot vietni pēc katra
wp plugin activate nosaukums

Alternatīva caur failiem: tāpat kā ar balto lapu — pārsauc wp-content/plugins mapi caur FTP, lai deaktivizētu visus, tad testē pa vienam, atgriežot failus mapē un aktivizējot spraudņus admin panelī.

Error establishing a database connection

Šī kļūda nozīmē, ka WordPress PHP kods darbojas, bet nevar izveidot savienojumu ar MySQL/MariaDB datubāzi — problēma ir vai nu nepareizos pieslēgšanās datos, vai pašā datubāzes serverī.

🔑 Nepareizi dati wp-config.php

Lietotājvārds, parole vai datubāzes nosaukums nesakrīt ar reālo.

💤 MySQL serviss nestrādā

Datubāzes serveris avarējis vai apturēts.

📈 Pārāk daudz savienojumu

Sasniegts servera maksimālais atļauto savienojumu skaits.

Risinājums caur SSH:

bash# Vai MySQL serviss vispār darbojas
sudo systemctl status mysql

# Pārbauda pieslēgšanos ar tieši tiem datiem, kas ir wp-config.php
mysql -u lietotajvards -p -h localhost datubazes_nosaukums

# Ja serviss nokritis — restartē to
sudo systemctl restart mysql

# Pārbauda pašreizējo savienojumu skaitu un limitu
mysql -u root -p -e "SHOW STATUS LIKE 'Threads_connected'; SHOW VARIABLES LIKE 'max_connections';"

Salīdzini pieslēgšanās datus ar to, kas faktiski norādīts konfigurācijas failā:

bashgrep -A1 "DB_NAME\|DB_USER\|DB_PASSWORD\|DB_HOST" wp-config.php

Alternatīva caur failiem: ja SSH nav, hostinga vadības panelī (cPanel "MySQL Databases") pārbaudi, vai lietotājam ir piešķirtas tiesības konkrētajai datubāzei, un salīdzini datus ar wp-config.php, ko atver caur failu pārvaldnieku vai FTP.

Bojāta datubāze / tabulu prefikss

Pēc neveiksmīgas migrācijas vai importa WordPress var uzrādīt kļūdas par trūkstošām tabulām — visbiežāk tāpēc, ka wp-config.php norādītais tabulu prefikss ($table_prefix) nesakrīt ar to, kāds tabulām faktiski ir datubāzē.

Risinājums caur SSH:

bash# Palaiž WordPress iebūvēto datubāzes labošanas rīku
wp db repair

# Uzskaita reālās tabulas un to prefiksu datubāzē
wp db query "SHOW TABLES;"
php// wp-config.php — prefiksam jāsakrīt ar to, kas redzams "SHOW TABLES" izvadā
$table_prefix = 'wp_';

Alternatīva caur failiem: phpMyAdmin sadaļā "Repair table" var izvēlēties visas tabulas un palaist labošanu no saskarnes, bez komandrindas — noderīgi, ja SSH nav pieejams.

Domēna/URL maiņa datubāzē (search-replace)

Pārvietojot WordPress vietni uz jaunu domēnu vai no localhost uz production, dati par veco adresi paliek iekodēti datubāzē — tostarp serializētos PHP masīvos, kur vienkāršs teksta meklēt/aizvietot var sabojāt datus, ja izmaiņa maina teksta garumu.

Nekad neizmanto parastu SQL UPDATE ... REPLACE() vai phpMyAdmin "Find and replace" serializētiem laukiem (piem., tēmas iestatījumi, Elementor/Divi dati) — tas sabojās datus, jo serializācijā ir iekodēts teksta garums.

Risinājums caur SSH — WP-CLI search-replace apstrādā serializāciju pareizi:

bash# Vispirms "sausais palaidiens" — parāda, kas tiktu mainīts, bet neko nemaina
wp search-replace 'http://vecais-domens.lv' 'https://jauns-domens.lv' --dry-run

# Kad pārliecināts — palaiž reāli, ieskaitot serializētos laukus
wp search-replace 'http://vecais-domens.lv' 'https://jauns-domens.lv' --all-tables

Alternatīva caur failiem (bez SSH): izmanto specializētu WordPress spraudni, piem. "Better Search Replace", kas iestatāms admin panelī un veic to pašu serializācijai drošo aizvietošanu bez komandrindas.

Nepareizas failu tiesības

Nevar augšupielādēt attēlus, atjaunināt spraudņus vai rediģēt tēmu tieši no admin paneļa ("HTTP error" augšupielādei, vai lūgums ievadīt FTP datus atjaunināšanai) — parasti nozīmē, ka failu īpašnieks vai tiesības neatbilst tam, ar kuru strādā web serveris.

Risinājums caur SSH — WordPress ieteiktās standarta tiesības:

bash# Īpašnieks — lietotājs, ar kuru strādā web serveris (bieži www-data)
sudo chown -R www-data:www-data /var/www/piemers.lv

# Mapēm 755, failiem 644
find /var/www/piemers.lv -type d -exec chmod 755 {} \;
find /var/www/piemers.lv -type f -exec chmod 644 {} \;

# wp-config.php drīkst būt stingrāks, jo tajā ir paroles
chmod 600 /var/www/piemers.lv/wp-config.php

Alternatīva caur failiem: FTP klientā (FileZilla) labais klikšķis uz wp-content mapi → "File permissions" → 755, atzīmējot "Recurse into subdirectories" un "Apply to directories only", tad atkārto ar 644 tikai failiem.

Bojāts .htaccess → 500 kļūda

WordPress izmanto .htaccess pastāvīgo saišu (permalinks) darbībai — manuāli pievienots vai spraudņa sabojāts noteikums šajā failā uzreiz padara visu vietni nesasniedzamu ar 500 kļūdu.

Risinājums caur SSH:

bash# Pārdēvē .htaccess, lai pilnībā izslēgtu un pārbaudītu, vai tas ir vainīgais
cd /var/www/piemers.lv
mv .htaccess .htaccess.bak

# Ja vietne tagad strādā, izveido jaunu noklusējuma WordPress .htaccess
wp rewrite flush --hard

Alternatīva caur failiem: ja SSH nav, admin panelī atver "Iestatījumi → Pastāvīgās saites" un nospied "Saglabāt izmaiņas" bez papildu rediģēšanas — WordPress automātiski pārraksta .htaccess ar pareizu, noklusējuma saturu (ja vien admin panelis vispār ir pieejams; ja arī tas rāda 500, jāizmanto FTP, lai izdzēstu/pārsauktu failu manuāli).

wp-config.php sintakses kļūda

Manuāli rediģējot wp-config.php (piemēram, pievienojot WP_DEBUG vai mainot datubāzes datus) un aizmirstot semikolu vai pēdiņu, rezultāts ir tūlītēja "Parse error" visai vietnei, tostarp admin panelim.

Risinājums caur SSH — PHP pati parāda precīzu rindas numuru, kur kļūda:

bash# Pārbauda sintaksi bez vietnes ielādēšanas pārlūkā
php -l wp-config.php

# Izvads norāda precīzu rindu, piem.:
# PHP Parse error: syntax error, unexpected ';' in wp-config.php on line 42

Alternatīva caur failiem: FTP klientā lejupielādē wp-config.php, atver ar teksta redaktoru, salīdzini ar oficiālo wp-config-sample.php struktūru un pārbaudi, vai katra define() rinda beidzas ar semikolu un vai pēdiņas ir pareizi aizvērtas.

Allowed memory size exhausted

PHP kļūda, kas parādās, kad skripts (bieži smags spraudnis, attēlu apstrāde vai plaša datubāzes izguve) mēģina izmantot vairāk atmiņas, nekā PHP konfigurācijā atļauts.

Risinājums caur SSH — atmiņas limitu var palielināt vairākās vietās:

php// wp-config.php — WordPress specifiskais limits
define('WP_MEMORY_LIMIT', '256M');
bash# Servera līmenī — atrod un rediģē php.ini
php --ini
sudo nano /etc/php/8.1/fpm/php.ini
# maini: memory_limit = 256M
sudo systemctl restart php8.1-fpm

Alternatīva caur failiem: daudzos koplietošanas hostingos atmiņas limitu var iestatīt caur .user.ini failu vietnes saknes mapē (satur, piem., memory_limit = 256M) — augšupielādē to caur FTP, izmaiņas stājas spēkā bez servera restartēšanas.

Spraudņa/tēmas konflikts

Vietne strādāja, bet pēc jauna spraudņa/tēmas instalēšanas vai atjaunināšanas parādās kļūdas, izlauzts izkārtojums vai balta lapa — divi spraudņi var arī konfliktēt savā starpā, ne tikai atsevišķi lauzt vietni.

Risinājums caur SSH — sistemātiska bināra meklēšana ar WP-CLI:

bash# Uzskaita visus spraudņus un to statusu
wp plugin list

# Deaktivizē visus, pārbaudi vai vietne atkal strādā
wp plugin deactivate --all

# Aktivizē pa vienam, pārbaudot vietni pēc katras darbības
wp plugin activate akismet
wp plugin activate contact-form-7
# ... turpini, līdz atrodi to, kas salauž vietni

# Ja vainīgs tēma — pārslēdz uz noklusējuma WordPress tēmu
wp theme activate twentytwentyfour

Alternatīva caur failiem: FTP klientā mapē wp-content/plugins pārdēvē katru spraudņa apakšmapi pa vienai (pievienojot, piem., -off nosaukuma beigās), pārbaudot vietni pēc katras — WordPress automātiski deaktivizē spraudni, ja tā mape nav atrodama sagaidītajā vietā.

WP-CLI uzstādīšana

WP-CLI ir oficiāls WordPress komandrindas rīks, kas nepieciešams lielākajai daļai iepriekšējo SSH risinājumu. Tas ļauj pārvaldīt spraudņus, lietotājus, datubāzi un daudz ko citu bez admin paneļa.

bash# Lejupielādē WP-CLI
curl -O https://raw.githubusercontent.com/wp-cli/builds/gh-pages/phar/wp-cli.phar

# Pārbauda, vai strādā
php wp-cli.phar --info

# Padara globāli izsaucamu kā "wp"
chmod +x wp-cli.phar
sudo mv wp-cli.phar /usr/local/bin/wp

# Pārbauda no jebkuras WordPress mapes
cd /var/www/piemers.lv
wp core version

WP-CLI komandas jāizpilda tajā pašā serverī, tajā pašā mapē, kur atrodas wp-config.php — pretējā gadījumā tas nezinās, ar kuru WordPress instalāciju strādāt.

Mixed content pēc SSL migrācijas

Pēc pārejas no HTTP uz HTTPS pārlūks parāda brīdinājumu "Not fully secure" vai bloķē daļu satura — jo daži resursi (attēli, skripti) datubāzē joprojām ir saglabāti ar veco http:// adresi, nevis https://.

Risinājums caur SSH — tas pats search-replace mehānisms kā domēna maiņai:

bashwp search-replace 'http://piemers.lv' 'https://piemers.lv' --all-tables --dry-run
wp search-replace 'http://piemers.lv' 'https://piemers.lv' --all-tables

Alternatīva caur failiem: spraudnis "Better Search Replace" (skat. iepriekš) veic to pašu bez SSH — svarīgi aizvietot tieši ar pilnu domēnu (http://piemers.lv → https://piemers.lv), nevis tikai protokolu, lai izvairītos no daļējām sakritībām citos laukos.

E-pasti netiek nosūtīti

WordPress noklusējuma wp_mail() funkcija izmanto servera vietējo mail() funkciju, ko daudzi hostingi un mākoņa serveri (piem., AWS, DigitalOcean) bloķē vai neuzskata par uzticamu — e-pasti (paroles atiestatīšana, veidlapu paziņojumi) vienkārši pazūd bez kļūdas.

Risinājums caur SSH — pārbaudi, vai serveris vispār var sūtīt pastu, un pāriet uz SMTP:

bash# Pārbauda, vai vietējais mail serviss vispār darbojas
echo "Testa ziņojums" | mail -s "Tests" tavs@epasts.lv

# Uzstāda un konfigurē SMTP spraudni caur WP-CLI
wp plugin install wp-mail-smtp --activate

Pēc uzstādīšanas spraudnis jākonfigurē admin panelī ar reāla SMTP servera datiem (piem., SendGrid, Mailgun vai Gmail SMTP) — tas garantē piegādi, atšķirībā no servera mail() funkcijas.

Alternatīva caur failiem: ja SSH nav, spraudni "WP Mail SMTP" instalē tieši admin panelī (Spraudņi → Pievienot jaunu) bez komandrindas.

Lēna WordPress vietne

Lapas ielādējas manāmi lēni — cēlonis parasti ir kāds no trim: neoptimizēta datubāze, trūkstoša kešošana vai pārāk smagi/nesaspiesti attēli.

🗄️ Neoptimizēta datubāze

Gadu gaitā uzkrājušies revīziju ieraksti, spam komentāri, transients.

🔁 Nav kešošanas

Katrs pieprasījums no jauna izpilda visus datubāzes vaicājumus.

🖼️ Nesaspiesti attēli

Augšupielādēti pilna izmēra attēli bez optimizācijas.

Risinājums caur SSH:

bash# Iztīra vecās ziņu revīzijas un spam komentārus
wp post delete $(wp post list --post_type='revision' --format=ids) --force
wp comment delete $(wp comment list --status=spam --format=ids) --force

# Optimizē datubāzes tabulas
wp db optimize

# Uzstāda kešošanas spraudni
wp plugin install w3-total-cache --activate

Alternatīva caur failiem/paneli: daudziem hostingiem (piem., ar LiteSpeed serveri) ir iebūvēts kešošanas mehānisms, ko ieslēdz vadības panelī bez papildu spraudņa — jāatrod sadaļa "Cache" vai "Performance" hostinga panelī.
