Sākums Tīkls Problēmas

Servera problēmas un risinājumi

Kad vietne nestrādā, pirmais jautājums ir kurā slānī problēma radusies. Katrai kļūdai zemāk - iespējamie cēloņi un pilns risinājums, galvenokārt caur SSH (tiešu piekļuvi serverim), ar alternatīvu risinājumu caur failiem (FTP/paneli), ja SSH piekļuves nav. Pamatus par IP/DNS/SSL skaties Tīkla dokumentācijā.

Kur meklēt vainīgo

Ceļš no domēna ieraksta līdz redzamai vietnei iet cauri četriem posmiem: (1) DNS - domēns jāpārvērš IP adresē; (2) savienojums - pārlūkam jāizveido tīkla savienojums ar šo IP; (3) šifrēšana (TLS/SSL) - jāizveido drošs kanāls; (4) serveris/aplikācija - serverim jāatgriež pati lapa. Kļūdas ziņojums parasti pasaka, kurā no šiem posmiem process apstājās.

DNS_PROBE_FINISHED_NXDOMAIN

Domēns vispār neeksistē DNS acīs - apstājās posmā (1).

CONNECTION_REFUSED / TIMED_OUT

Serveris nesasniedzams vai neatbild - apstājās posmā (2).

SSL_PROTOCOL_ERROR / CERT_*

Problēma ar HTTPS/sertifikātu - apstājās posmā (3).

502 / 503 / 504

Serveris strādā, bet backend - nē - apstājās posmā (4).

Lielākā daļa risinājumu zemāk pieņem, ka tev ir SSH piekļuve serverim (ssh lietotajs@servera-ip). Ja pieejams tikai koplietošanas (shared) hostings bez SSH, katrā sadaļā ir norādīta arī alternatīva caur failu pārvaldnieku/FTP vai vadības paneli.

DNS_PROBE_FINISHED_NXDOMAIN

Šī Chrome/Edge kļūda nozīmē, ka pārlūks mēģināja izšķirt (atrisināt) domēnu, taču DNS sistēma atbildēja, ka tāda domēna vispār nav (NXDOMAIN = "Non-Existent Domain"). Svarīgi saprast: tā nav servera problēma - process apstājās vēl pirms pārlūks vispār mēģināja pieslēgties jebkuram serverim, tāpēc servera pusē neko labot nevar, kamēr nav atrisināts pats DNS ieraksts.

📅 Domēns nav reģistrēts / beidzies

Reģistrācijas termiņš beidzies vai domēns vēl nemaz nav iegādāts.

⏳ DNS vēl nav iestatīts

Jaunam domēnam/serverim A/NS ieraksti vēl nav pievienoti vai nav propagējušies.

✏️ Pareizrakstības kļūda

Pārbaudi, vai domēna nosaukums ierakstīts pareizi - pārsteidzoši bieži tas ir vainīgais.

💻 Lokāla DNS/hosts problēma

Vecs kešotais ieraksts vai nepareiza rinda operētājsistēmas hosts failā.

Risinājums caur SSH (vai lokālo termināli) - diagnostikas secība pēc kārtas, nomainot piemers.lv uz savu domēnu:

bash# 1. Vai domēns vispār reģistrēts un derīgs
whois piemers.lv

# 2. Vai domēnam iestatīti nameserveri
dig piemers.lv NS

# 3. Vai eksistē A ieraksts (IP adrese)
dig piemers.lv A

# 4. Pamēģini citu DNS resolveri, lai izslēgtu sava ISP problēmu
dig @8.8.8.8 piemers.lv

Alternatīva caur failiem: ja SSH nav pieejams, DNS ierakstus pārbauda un labo domēna reģistrētāja vai DNS pārvaldnieka (piem. Cloudflare) tīmekļa panelī - jāatrod A ieraksts un jāpārliecinās, ka tas norāda uz pareizo servera IP adresi.

Ja dig no cita tīkla vai ierīces (piem., telefona ar mobilo internetu) arī nerāda nekādu ierakstu, tas apstiprina, ka problēma ir DNS/servera pusē, nevis tavā konkrētajā datorā.

Hosts fails (ātrais labojums)

Ja zini servera IP adresi, bet DNS vēl nestrādā, vari "piespiest" savu datoru izmantot konkrēto IP šim domēnam, apejot DNS pilnībā. Šis paņēmiens maina rezultātu tikai tavā datorā.

Windows:

cmd1. Atver Command Prompt kā administrators
2. Atver hosts failu Notepad:
notepad C:\Windows\System32\drivers\etc\hosts

3. Pievieno rindu faila beigās:
81.198.171.19   piemers.lv

4. Saglabā un notīri DNS kešu:
ipconfig /flushdns

Mac/Linux (SSH vai lokāli):

bashsudo nano /etc/hosts
# pievieno: 81.198.171.19   piemers.lv

Kad testēšana pabeigta, neaizmirsti izdzēst pievienoto rindu - pretējā gadījumā pēc mēnešiem tavā datorā vietne var izskatīties savādāk nekā visiem citiem.

CONNECTION_REFUSED / TIMED_OUT

Abas šīs kļūdas nozīmē, ka DNS jau ir atrisinājies veiksmīgi, bet neizdodas izveidot tīkla savienojumu ar pašu serveri.

🚫 REFUSED

Serveris aktīvi atsaka savienojumu. Cēlonis: pakalpojums nav palaists, vai neviens serviss neklausās uz šī porta.

⏱️ TIMED_OUT

Pieprasījums pazūd klusumā. Cēlonis: ugunsmūris klusi nomet paketes, vai IP adrese nepareiza.

Risinājums caur SSH - pieslēdzies serverim un pārbaudi:

bash# Serverī - vai serviss vispār darbojas un klausās
sudo systemctl status nginx
sudo ss -tulpn | grep :443

# No sava datora - vai ports vispār sasniedzams no ārpuses
telnet piemers.lv 443

Alternatīva caur failiem/paneli: ja SSH nav, hostinga vadības panelī parasti ir sadaļa "Service Status" vai "Restart Server", kur var pārstartēt tīmekļa servisu bez komandrindas.

Vietne pilnībā nesasniedzama (serveris "guļ")

Vietne bija strādājusi, bet pēkšņi nekas neatbild - nedz DNS, nedz savienojums, nedz kļūdas lapa. Visbiežāk pats serveris ir apstājies vai kritisks serviss uz tā nav palaists.

💥 Serviss avarējis

Nginx/Apache/PHP-FPM process negaidīti apstājies (kļūda, OOM killer nogalinājis).

🔄 Serveris restartējies

Pēc VPS pārstartēšanas serviss nav iestatīts automātiski startēties.

🧠 Trūkst atmiņas (RAM)

Serveris pārslogots, operētājsistēma piespiedu kārtā aptur procesus.

Risinājums caur SSH:

bash# Pārbaudi servisa statusu
sudo systemctl status nginx
sudo systemctl status php8.1-fpm

# Pēdējie 50 žurnāla ieraksti - kāpēc process apstājās
sudo journalctl -u nginx -n 50 --no-pager

# Restartē servisu
sudo systemctl restart nginx

# Pārliecinies, ka serviss startēsies arī pēc nākamās pārstartēšanas
sudo systemctl enable nginx

# Pārbaudi brīvo/aizņemto atmiņu
free -h

Alternatīva caur failiem/paneli: ja SSH piekļuves nav (koplietošanas hostings), jāsazinās ar hostinga tehnisko atbalstu vai jāizmanto vadības paneļa (cPanel/Plesk) poga servisa restartēšanai.

Ports bloķēts ugunsmūrī

Serveris strādā un serviss klausās uz porta, bet ārējie pieprasījumi tik un tā "karājas" vai tiek atteikti - vainīgs parasti ir ugunsmūris, kas nomet paketes klusi, neatgriežot skaidru kļūdu.

🧱 OS ugunsmūris (ufw/iptables)

Servera operētājsistēmas ugunsmūris bloķē portu tieši serverī.

☁️ Mākoņa drošības grupa

AWS Security Group / DigitalOcean Firewall bloķē portu ārpus paša servera - bieži aizmirsta vieta.

Risinājums caur SSH:

bash# Pārbaudi ufw statusu un atļautos portus
sudo ufw status

# Atļauj HTTP un HTTPS trafiku
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw reload

Alternatīva caur failiem/paneli: mākoņa nodrošinātāja (AWS/DigitalOcean/Hetzner) tīmekļa panelī jāatrod "Firewall" vai "Security Group" sadaļa un manuāli jāpievieno noteikums, kas atļauj ienākošo trafiku uz portiem 80 un 443 - šī darbība notiek ārpus paša servera un SSH šeit nepalīdzēs, ja bloķēšana ir tieši šajā slānī.

SSL kļūdas

ERR_SSL_PROTOCOL_ERROR parādās, kad TCP savienojums izveidojas veiksmīgi, bet TLS "sarunas" (handshake) neizdodas pabeigt. Biežākais iemesls - pārlūks mēģina runāt HTTPS ar portu, kas TLS vispār nesatur.

🔌 Nepareizs ports

HTTPS mēģina savienoties ar portu, kur serveris runā tikai parasto HTTP.

🧓 Novecojis TLS

Serveris atbalsta tikai novecojušas, jau izslēgtas TLS versijas.

🔀 Reverse proxy konflikts

Cloudflare/Nginx priekšā sagaida HTTPS, bet backend serveris to nenodrošina.

Risinājums caur SSH - pārbaudi, ko tieši serveris atbild:

bashecho | openssl s_client -connect piemers.lv:443 -servername piemers.lv 2>/dev/null | openssl x509 -noout -dates -subject

Ja kļūda saistīta ar sertifikāta saturu (domēns nesakrīt, neuzticams izdevējs, beidzies termiņš) - skat. "certbot renew neizdodas" zemāk.

certbot renew neizdodas

Let's Encrypt sertifikāti derīgi tikai 90 dienas, un atjaunošanai jānotiek automātiski. Ja process neizdodas, sertifikāts beidzas un pārlūks sāk rādīt drošības brīdinājumu.

🔌 Ports 80 aizņemts

Cits serviss klausās uz porta 80, kas nepieciešams HTTP-01 validācijai.

🌐 DNS izmaiņas

Domēns vairs nenorāda uz šo serveri - validācija neizdodas.

⏳ Rate limit

Let's Encrypt ierobežo pieprasījumu skaitu vienam domēnam noteiktā laika periodā.

Risinājums caur SSH:

bash# Pārbauda, kas tieši atjaunošanā nogāja greizi
sudo certbot renew --dry-run

# Uzskaita esošos sertifikātus un to termiņus
sudo certbot certificates

# Pārliecinies, ka nginx klausās uz porta 80 validācijai
sudo systemctl status nginx

Alternatīva caur failiem/paneli: ja HTTP-01 validācija nav iespējama (ports 80 nepieejams no interneta), var izmantot DNS-01 validāciju - pievienojot certbot norādīto TXT ierakstu domēna DNS panelī manuāli, bez SSH piekļuves serverim šajā solī.

502 / 503 / 504

Šīs kļūdas nozīmē, ka pats serveris ir sasniedzams, bet kaut kas nogāja greizi backend (PHP-FPM, Node.js, datubāze) līmenī.

502 Bad Gateway

Reverse proxy nesaņem derīgu atbildi no backend - visbiežāk nokritis PHP-FPM.

503 Service Unavailable

Serveris pārslogots vai apzināti pārslēgts uzturēšanas režīmā.

504 Gateway Timeout

Backend atbild pārāk lēni - smags vaicājums vai resursu trūkums.

Risinājums caur SSH - precīzu iemeslu gandrīz vienmēr atklāj žurnāli tiešraidē:

bashsudo tail -f /var/log/nginx/error.log
sudo systemctl status php8.1-fpm
sudo systemctl restart php8.1-fpm

Disks pilns (No space left on device)

Kad serverim beidzas brīvā vieta, saraujas viss - datubāze nevar rakstīt, augšupielādes neizdodas, žurnāli pārtrauc pierakstīšanos, dažreiz pat pati vietne kļūst nesasniedzama.

📜 Uzkrājušies žurnāli

Servera/aplikācijas log faili gadu gaitā sasniedz gigabaitus.

🗄️ Vecas dublējumkopijas

Automātiskie backups netiek dzēsti un uzkrājas.

📁 Augšupielādes

Attēli/faili uploads mapē aug bez ierobežojuma.

Risinājums caur SSH:

bash# Vispārējs diska lietojums
df -h

# 10 lielākās mapes /var/log iekšienē
du -sh /var/log/* | sort -rh | head -10

# Iztīri veco žurnālu vēsturi (piem. journald)
sudo journalctl --vacuum-time=7d

Alternatīva caur failiem: FTP/failu pārvaldniekā ("File Manager" hostinga panelī) manuāli jāapskata lielākās mapes (parasti wp-content/uploads, backup mapes) un jāizdzēš nevajadzīgais.

Permission denied kļūdas

Serveris atsakās lasīt vai rakstīt failus, jo tiem ir nepareizs īpašnieks vai piekļuves tiesības - bieži rodas pēc migrācijas, manuālas augšupielādes ar root tiesībām, vai backup atjaunošanas.

Risinājums caur SSH - atgriež standarta WordPress/web tiesības:

bash# Iestata pareizo īpašnieku (lietotājs, ar kuru strādā web serveris)
sudo chown -R www-data:www-data /var/www/piemers.lv

# Mapēm - 755, failiem - 644
find /var/www/piemers.lv -type d -exec chmod 755 {} \;
find /var/www/piemers.lv -type f -exec chmod 644 {} \;

Alternatīva caur failiem: FTP klientā (piem. FileZilla) labais klikšķis uz mapi/failu → "File permissions" → ievadi 755 mapēm un 644 failiem manuāli, ar iespēju piemērot rekursīvi visai mapei.

Nekad neiestati 777 tiesības kā "ātru labojumu" - tas ļauj rakstīt failus jebkuram serverī esošam procesam, tostarp ļaunprātīgam kodam, ja serveris tiek kompromitēts.

WordPress vietnēm der arī papildu solis wp-config.php failam - skaties "Nepareizas failu tiesības" WordPress problēmu lapā.

Strādā lokāli, salūst serverī (case-sensitivity)

Windows un Mac failu sistēmas pēc noklusējuma neatšķir lielos un mazos burtus faila nosaukumā - Config.php un config.php tur ir viens un tas pats fails. Linux (gandrīz visi hostingi) gan atšķir - tie ir divi pilnīgi dažādi faili. Rezultāts: kods, kas lokāli strādā perfekti (jo OS "piedod" nepareizu reģistru), pēc augšupielādes uz serveri met 404 vai failed to open stream: No such file or directory.

php// Fails uz diska: helpers/StringUtils.php
// Šis strādās lokāli Windows/Mac, bet salūzīs Linux serverī:
require 'helpers/stringutils.php'; // nepareizs reģistrs!

Tas pats attiecas uz attēlu/CSS/JS ceļiem HTML kodā (<img src="Logo.png">, kad fails patiesībā ir logo.png) - lokāli attēls parādās, serverī rāda salauztu ikonu.

Ātra pārbaude pirms izvietošanas (deploy) - Git pats var atklāt šīs neatbilstības neatkarīgi no OS: git config core.ignorecase false liek Git stingri atšķirt reģistru arī Windows/Mac lokāli, tāpēc nepareizi rakstīts imports parādīsies kā jauns, nepazīstams fails jau lokāli, nevis tikai pēc izvietošanas serverī.

.htaccess sintakses kļūda → 500

Apache lasa .htaccess failu katrā pieprasījumā - ja tajā ir sintakses kļūda (bieži pēc manuālas rediģēšanas vai spraudņa pievienota noteikuma), rezultāts ir tūlītēja 500 kļūda visai vietnei.

Diagnostika caur SSH:

bash# Pārbauda Apache konfigurācijas sintaksi
sudo apache2ctl configtest

Ja vietne ir uz WordPress - pilnu labošanas soli (pārdēvēšana, jauna .htaccess ģenerēšana caur wp-admin vai wp rewrite flush) skaties "Bojāts .htaccess → 500 kļūda" WordPress problēmu lapā. Citām (ne-WordPress) vietnēm - pārsauc failu, lai to izslēgtu, tad salīdzini ar attiecīgā CMS/framework noklusējuma versiju.

PHP versijas neatbilstība

Pēc hostinga automātiskas PHP versijas atjaunināšanas vecāks kods (novecojis spraudnis, pašrakstīts skripts) var pārtraukt darboties, jo lieto sintaksi vai funkcijas, kas jaunākajā PHP versijā ir noņemtas vai mainījušas uzvedību.

Risinājums caur SSH:

bash# Pārbauda aktīvo PHP versiju
php -v

# Ubuntu/Debian serverī ar vairākām instalētām versijām - pārslēdz
sudo update-alternatives --set php /usr/bin/php8.1

# Skaties kļūdas tiešraidē, kamēr atsvaidzini vietni pārlūkā
sudo tail -f /var/log/php8.1-fpm.log

Alternatīva caur failiem/paneli: koplietošanas hostingā PHP versiju parasti maina caur vadības paneli (cPanel "MultiPHP Manager", Plesk "PHP Settings"), izvēloties konkrētam domēnam vecāku, saderīgu PHP versiju no saraksta - bez SSH piekļuves.

TOO_MANY_REDIRECTS

Šī kļūda nozīmē, ka vietne novirza pati uz sevi bezgalīgā ciklā - pārlūks pēc noteikta skaita pāradresāciju padodas un parāda kļūdu.

⚙️ WordPress Address/Site Address

Iestatījumos viens ir http://, otrs https:// - rodas cikls.

☁️ Cloudflare "Flexible" SSL

Cloudflare sūta pieprasījumu pa HTTP, serveris piespiedu kārtā novirza atpakaļ uz HTTPS. Risinājums: pārslēgt SSL/TLS režīmu uz "Full (strict)".

📄 .htaccess redirect cikls

Pretrunīgi RewriteRule noteikumi paši sevi "ķeksē" bezgalīgi.

Risinājums caur SSH - pārbaudi, cik reižu un uz kurieni notiek pāradresācija:

bashcurl -IL https://piemers.lv

Alternatīva caur failiem: ja cēlonis ir WordPress iestatījumos, tos var labot arī tieši datubāzē (phpMyAdmin) wp_options tabulā, mainot siteurl un home vērtības, ja admin panelis pats nav pieejams redirektu cikla dēļ.

Redzu hostinga paneļa sveiciena lapu, nevis savu vietni

Domēns pareizi ved uz servera IP, savienojums izveidojas - taču tā vietā, lai redzētu paredzēto vietni, parādās hostinga vadības paneļa (VestaCP, cPanel, Plesk) noklusējuma "Welcome" lapa.

Pareizs IP ≠ pareiza vietne. Viens fizisks serveris var apkalpot desmitiem domēnu - kuru rādīt, tīmekļa serveris izvēlas pēc pieprasījuma Host galvenes (virtual host mehānisms). Ja domēnam serverī vēl nav izveidots ieraksts, serveris parāda savu noklusējuma vietni.

Risinājums caur SSH (Nginx virtual host piemērs):

bash# Pārbauda esošos virtual host konfigurācijas failus
ls /etc/nginx/sites-available/

# Izveido jaunu, ja domēnam vēl nav sava ieraksta, tad:
sudo ln -s /etc/nginx/sites-available/piemers.lv /etc/nginx/sites-enabled/
sudo nginx -t
sudo systemctl reload nginx

Alternatīva caur paneli: pieslēdzies hostinga vadības panelim → atrodi sadaļu domēnu pārvaldībai → izveido/pievieno šo domēnu kā "Web Domain" ar pareizu DocumentRoot norādi uz vietnes failu mapi.

CORS kļūda

CORS kļūda parādās, kad lapā ielādēts JavaScript no viena domēna mēģina piekļūt datiem no cita domēna, un tas serveris skaidri nav atļāvis šādus pieprasījumus - pilnu skaidrojumu (kāpēc pārlūks to bloķē un kā izskatās kļūda konsolē) skaties "Drošība - CORS, HTTPS, rate limiting" API kategorijā. Zemāk - tieši, kā to labot servera pusē.

Risinājums vienmēr ir servera pusē - SSH pieslēdzoties serverim, jārediģē Nginx konfigurācija vai backend kods:

bash# Nginx konfigurācijā (piem. /etc/nginx/sites-available/api.conf)
sudo nano /etc/nginx/sites-available/api.conf
# pievieno: add_header 'Access-Control-Allow-Origin' 'https://mana-app.lv';
sudo nginx -t && sudo systemctl reload nginx

Alternatīva caur failiem: ja backend ir PHP/WordPress bez SSH, galveni var pievienot arī tieši aplikācijas kodā (piem. functions.php caur header() funkciju) un augšupielādēt caur FTP.

CORS kļūdu nevar apiet, mainot kodu pārlūka pusē - ja tas nav "tavs" API, jāsazinās ar tā uzturētāju.

HTTP statusa kodi

Katra servera atbilde nāk kopā ar trīsciparu kodu, kas pasaka, kas tieši notika.

text200 OK                    → pieprasījums izdevās, šeit ir saturs
301 Moved Permanently     → resurss pastāvīgi pārvietots (piem., http → https)
302 Found                 → pagaidu pāradresācija
400 Bad Request           → serveris nesaprot pieprasījumu
401 Unauthorized          → nepieciešama autentifikācija
403 Forbidden             → serveris saprot pieprasījumu, bet atsaka piekļuvi
404 Not Found             → šāda adrese/lapa neeksistē
429 Too Many Requests     → pārāk daudz pieprasījumu īsā laikā
500 Internal Server Error → neapstrādāta kļūda servera/aplikācijas kodā
502 Bad Gateway           → proxy nesaņem derīgu atbildi no backend
503 Service Unavailable   → serveris pārslogots vai uzturēšanas režīmā
504 Gateway Timeout       → backend atbild pārāk lēni

Kodu var pārbaudīt tieši no komandrindas, neatverot pārlūku:

bashcurl -I https://piemers.lv
# Pirmā izvada rinda būs, piem.: HTTP/2 200
