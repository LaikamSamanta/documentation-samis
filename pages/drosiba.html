Sākums Drošība

Drošība

Web drošības pamatprincipi, ko jāzina katram programmētājam — ne tikai WordPress kontekstā. Katrai tēmai — kāpēc uzbrukums strādā, un konkrēts, pareizs koda piemērs, kā to novērst.

Hashošana vs šifrēšana (encryption)

Abas pārvērš datus par nesalasāmu virkni, tāpēc tās bieži sajauc — bet tām ir pretēja pamatīpašība: hash ir vienvirziena (nekad neatšifrē atpakaļ), šifrēšana ir divvirzienu (ar pareizu atslēgu var iegūt oriģinālu atpakaļ). Izvēle starp tām ir izvēle starp "vai man dati kādreiz jāatgūst atpakaļ, vai tikai jāpārbauda, ka tie sakrīt".

HashošanaŠifrēšana
VirziensVienvirziena — nav "atšifrē"Divvirzienu — encrypt() un decrypt()
RezultātsVienmēr fiksēta garuma virkneGarums atkarīgs no oriģināla
AtslēgaNav (bet var būt sāls)Obligāta — bez tās nav iespējams atgūt datus
Kad izmantotParoles, failu integritātes pārbaude, čeksummasKredītkaršu dati, personas dati, ziņas, kas jāizlasa vēlāk
 
php// HASHOŠANA — paroles gadījumā oriģinālu vairs NEVAJAG, tikai salīdzināšanu
$hash = password_hash('ManaParole123', PASSWORD_DEFAULT);
// $hash: $2y$10$abc...  — no šī NAV iespējams iegūt atpakaļ 'ManaParole123'
password_verify('ManaParole123', $hash); // true — salīdzina, neatšifrē

// ŠIFRĒŠANA — piem., jāsaglabā lietotāja tālrunis, ko vēlāk jāparāda atpakaļ
$atslega = random_bytes(32); // glabā drošā vietā, NEVIS datubāzē blakus datiem
$iv = random_bytes(16);
$sifrets = openssl_encrypt('+371 20000000', 'aes-256-cbc', $atslega, 0, $iv);
// vēlāk, kad tālrunis atkal jāparāda lietotājam:
$originals = openssl_decrypt($sifrets, 'aes-256-cbc', $atslega, 0, $iv);
// $originals === '+371 20000000'

Pati biežākā kļūda: paroles šifrēt nevis hashot. Ja paroles ir šifrētas, tad, ja uzbrucējs kaut kā iegūst atslēgu (piem., no koda repozitorija vai konfigurācijas faila), viņš iegūst visas paroles vienlaikus tekstā. Ja paroles ir hashotas, tur nav nekādas atslēgas, ko nozagt — hash pats par sevi ir bezvērtīgs uzbrucējam bez milzīga brute-force darba. Skat. arī Paroļu hashošana zemāk.

Simetriskā vs asimetriskā šifrēšana

Iepriekšējā piemērā (openssl_encrypt) izmantota simetriskā šifrēšana — viena un tā pati atslēga gan šifrē, gan atšifrē. Tas ir ātri, bet rada praktisku problēmu: kā droši nodot šo atslēgu otrai pusei, ja sazināšanās kanāls pats vēl nav drošs? Šo problēmu risina asimetriskā šifrēšana.

Simetriskā ātra

Viena atslēga abām darbībām (piem., AES). Ātra, der lielam datu apjomam. Problēma: atslēga jāpārsūta droši abām pusēm iepriekš.

Asimetriskā lēnāka

Divas matemātiski saistītas atslēgas — publiskā (var brīvi izplatīt) un privātā (glabā slepenībā). Ar publisko šifrē, ar privāto atšifrē (piem., RSA, ECC). Lēnāka, tāpēc reti izmanto lieliem datu apjomiem tieši.

Praksē abas kombinē — tā strādā arī HTTPS/TLS (skat. HTTPS/TLS pamati zemāk): asimetrisko šifrēšanu izmanto tikai īsam "roku spiedienam" sākumā, lai droši vienotos par vienreizēju simetrisko atslēgu, un pēc tam visu faktisko datu plūsmu šifrē ar to — ātrāk, bet tikpat droši.

Asimetriskā šifrēšana ir arī pamats digitālajam parakstam (JWT RS256 algoritms, SSL sertifikāti, Git commit parakstīšana) — tikai apgrieztā virzienā: paraksta ar privāto atslēgu, pārbauda ar publisko. Tā jebkurš var pārliecināties, ka ziņu tiešām nosūtīja atslēgas īpašnieks, bet tikai īpašnieks var jaunas parakstīt.

Autentifikācija vs autorizācija

Divi termini, ko pastāvīgi sajauc, jo angliski tie skan un raksta gandrīz vienādi (authentication / authorization) — bet tie atbild uz pilnīgi dažādiem jautājumiem.

Autentifikācija "Kas tu esi?"

Pārbauda identitāti — pieteikšanās ar lietotājvārdu/paroli, 2FA kodu, piekļuves tokenu. Rezultāts: sistēma zina, KURŠ lietotājs tas ir.

Autorizācija "Ko tu drīksti?"

Pārbauda tiesības — vai šim jau zināmajam lietotājam ir atļauts veikt konkrēto darbību (rediģēt šo rakstu, redzēt šo lapu). Notiek PĒC autentifikācijas.

php// AUTENTIFIKĀCIJA — WordPress: "vai lietotājs vispār ir pieteicies?"
if (!is_user_logged_in()) {
    wp_die('Lūdzu, piesakies.');
}

// AUTORIZĀCIJA — WordPress: "vai ŠIM KONKRĒTAJAM lietotājam ir tiesības to darīt?"
if (!current_user_can('edit_posts')) {
    wp_die('Nav tiesību rediģēt rakstus.');
}

Klasiska HTTP statusu kļūda: statuss 401 Unauthorized vēsturiski nosaukts maldinoši — tas patiesībā nozīmē "nav autentificējies" (nav pieteicies vispār), nevis "nav autorizēts". Pareizais statuss trūkstošai autorizācijai (pieteicies, bet nav tiesību) ir 403 Forbidden. Daudzi API to sajauc — pievēršot tam uzmanību, savā kodā to var izdarīt pareizi.

JWT (tokeni) vs sesijas

Divi izplatīti veidi, kā lietotni "atceras", ka lietotājs ir pieteicies starp pieprasījumiem — fundamentāli atšķirīga arhitektūra ar dažādiem kompromisiem.

SesijasJWT
Kur glabājas datiServerī (datubāze/Redis), klientam tikai IDPašā tokenā, klienta pusē
Servera atmiņaJāglabā katra aktīvā sesijaNav jāglabā nekas ("bezstāvokļa")
Atsaukšana pirms termiņaVienkārši — izdzēš ierakstu serverīSarežģīti — tokens derīgs līdz termiņam, ja vien neuztur "melno sarakstu"
Der labiKlasiskai vietnei ar vienu backend serveriAPI starp vairākiem servisiem/mikroservisiem, mobilajām app

WordPress pēc noklusējuma izmanto sesiju/cookie modeli (skat. Sesiju drošība augstāk) — JWT tur parasti parādās tikai tad, ja vietnei ir atsevišķs REST API, ko lieto mobilā app vai cita ārēja sistēma, nevis pats WordPress admin panelis.

JWT galvenā priekšrocība (nav jāglabā stāvoklis serverī) ir vienlaikus arī tā galvenais trūkums: ja lietotāju vajag nekavējoties izslēgt (piem., viņu atlaida no darba), parasts JWT paliks derīgs līdz izbeigšanās laikam — parasti risina ar īsu derīguma termiņu (5-15 min) plus atsevišķu "refresh token", ko VAR atsaukt serverī.

XSS (Cross-Site Scripting)

Uzbrucējs iesmidzina ļaunprātīgu JavaScript kodu lapā, ko pēc tam izpilda cita lietotāja pārlūks — piem., nozogot viņa sesijas sīkdatni. Notiek, kad lietotāja ievade tiek izvadīta HTML bez attīrīšanas.

php// NEDROŠI — lietotāja ievade tiek izvadīta tieši HTML
echo "Sveiks, " . $_GET['vards'];
// Ja ?vards=<script>alert(document.cookie)</script>, tas IZPILDĀS pārlūkā

// DROŠI — htmlspecialchars() pārvērš < > " ' & par HTML entītijām
echo "Sveiks, " . htmlspecialchars($_GET['vards'], ENT_QUOTES, 'UTF-8');

Tas pats princips JavaScript pusē:

js// NEDROŠI — innerHTML izpilda jebkuru HTML/JS, kas ir mainīgajā
element.innerHTML = lietotajaIevade;

// DROŠI — textContent vienmēr rāda tekstu burtiski, neizpildot HTML
element.textContent = lietotajaIevade;

WordPress šim nolūkam piedāvā veselu funkciju saimi — esc_html(), esc_attr(), esc_url() — katra paredzēta konkrētam kontekstam (HTML teksts, atribūts, URL). Nekad neizmanto vienu universālu "escaping" funkciju visur.

SQL Injection

Uzbrucējs ievada SQL kodu formas laukā tā, lai tas mainītu paša vaicājuma nozīmi — var izgūt visu datubāzi, apiet pieteikšanos vai dzēst datus.

php// NEDROŠI — lietotāja ievade tieši SQL vaicājumā (string konkatenācija)
$rezultats = $pdo->query("SELECT * FROM lietotaji WHERE epasts = '" . $_POST['epasts'] . "'");
// Ievade: ' OR '1'='1  ⇒ vaicājums kļūst PATIESS visām rindām, atgriež VISUS lietotājus

// DROŠI — sagatavotie vaicājumi (prepared statements) ar parametru saistīšanu
$stmt = $pdo->prepare("SELECT * FROM lietotaji WHERE epasts = :epasts");
$stmt->execute(['epasts' => $_POST['epasts']]);
$rezultats = $stmt->fetchAll();

Prepared statements strādā, jo PDO parametrus (:epasts) nosūta serverim atsevišķi no paša SQL vaicājuma teksta — datubāze tos nekad neinterpretē kā daļu no SQL sintakses, lai arī ko lietotājs ievadītu. Pilnu PDO piemēru skati PHP → Datubāzes (PDO).

Ievades validācija & sanitizācija

Divi atšķirīgi jēdzieni: validācija pārbauda, vai dati atbilst gaidītajam formātam (un noraida, ja ne), sanitizācija tīra/pārveido datus, noņemot bīstamo saturu.

php// Validācija — noraida, ja e-pasts nav derīgā formātā
$epasts = filter_var($_POST['epasts'], FILTER_VALIDATE_EMAIL);
if ($epasts === false) {
    die('Nederīga e-pasta adrese');
}

// Sanitizācija — noņem bīstamās rakstzīmes, neatgriežot kļūdu
$komentars = filter_var($_POST['komentars'], FILTER_SANITIZE_FULL_SPECIAL_CHARS);

Validācija JavaScript pusē (piem., HTML5 required atribūts) ir tikai lietotāja ērtībai — jebkurš var apiet klienta pusi ar DevTools vai tiešu pieprasījumu. Vienmēr validē arī serverī — tā ir vienīgā validācija, kurai tiešām var uzticēties.

CSRF (Cross-Site Request Forgery)

Uzbrucēja lapa liek Tavam pārlūkam (kamēr esi pieteicies citā vietnē) nosūtīt pieprasījumu tavā vārdā — piem., paroles maiņu — izmantojot to, ka pārlūks automātiski pievieno sesijas sīkdatnes jebkuram pieprasījumam uz to domēnu.

php// 1) Ģenerē tokenu un saglabā sesijā (vienu reizi uz formu/sesiju)
session_start();
if (empty($_SESSION['csrf_token'])) {
    $_SESSION['csrf_token'] = bin2hex(random_bytes(32));
}
html<!-- 2) Ievieto formā kā paslēptu lauku -->
<form method="post" action="/saglabat">
    <input type="hidden" name="csrf_token" value="<?= htmlspecialchars($_SESSION['csrf_token']) ?>">
    ...
</form>
php// 3) Pārbauda pirms JEBKURAS darbības izpildes (nevis pēc)
if (!hash_equals($_SESSION['csrf_token'], $_POST['csrf_token'] ?? '')) {
    die('Nederīgs pieprasījums (CSRF)');
}

WordPress šo mehānismu jau realizē pats ar nonces (wp_nonce_field() + wp_verify_nonce()) — sk. WordPress → Drošība (nonce & escaping). hash_equals(), nevis ===, tiek izmantots tāpēc, ka tas salīdzina virknes nemainīgā laikā, novēršot "timing attack" — uzbrukumu, kas mēra atbildes laiku, lai uzminētu pareizo tokenu simbolu pa simbolam.

Paroļu hashošana

Paroles datubāzē nekad neglabā tekstā vai ar novecojušiem algoritmiem (MD5, SHA1) — tos var uzlauzt sekundēs ar gatavām "rainbow table" tabulām. PHP iebūvētās funkcijas dara visu pareizi automātiski.

php// Saglabājot paroli (piem., reģistrācijas laikā)
$hash = password_hash($parole, PASSWORD_DEFAULT); // bcrypt/Argon2, atkarībā no PHP versijas
// Saglabā $hash datubāzē — NEVIS pašu $parole

// Pārbaudot pieteikšanos
if (password_verify($ievaditaParole, $hash)) {
    echo 'Parole pareiza';
}

PASSWORD_DEFAULT tīši nenorāda konkrētu algoritmu — PHP izvēlas labāko pieejamo, un tas var mainīties nākotnes versijās. Tāpēc hash garums datubāzes kolonnā vienmēr jāatstāj vismaz 255 rakstzīmes, nevis fiksēts 32/40 (kā MD5/SHA1 laikos).

Sesiju drošība

PHP sesiju sīkdatnes pēc noklusējuma nav pilnībā aizsargātas — daži iestatījumi jāpieslēdz manuāli, pirms sesija sākas.

php// Jāiestata PIRMS session_start()
ini_set('session.cookie_httponly', 1); // JS nevar piekļūt cookie — aizsardzība pret XSS zādzību
ini_set('session.cookie_secure', 1);   // cookie sūta TIKAI pār HTTPS
ini_set('session.cookie_samesite', 'Lax'); // papildu aizsardzība pret CSRF
session_start();

// Pēc VEIKSMĪGAS pieteikšanās — vienmēr reģenerē sesijas ID
session_regenerate_id(true);

session_regenerate_id(true) pēc pieteikšanās novērš "session fixation" uzbrukumu — kad uzbrucējs uzspiež zināmu sesijas ID upurim PIRMS pieteikšanās, cerot to izmantot PĒC. Jauna ID ģenerēšana pēc pieteikšanās šo iepriekš zināmo ID padara nederīgu.

Brute-force aizsardzība (rate limiting)

Bez ierobežojuma uzbrucējs var automātiski izmēģināt tūkstošiem paroļu sekundē. Vienkāršākais aizsardzības līmenis — skaitīt neveiksmīgos mēģinājumus un īslaicīgi bloķēt.

phpsession_start();
$meginejumi = $_SESSION['login_attempts'] ?? 0;

if ($meginejumi >= 5) {
    die('Pārāk daudz mēģinājumu. Mēģini vēlreiz pēc 15 minūtēm.');
}

// ... pēc NEVEIKSMĪGA pieteikšanās mēģinājuma:
$_SESSION['login_attempts'] = $meginejumi + 1;

// ... pēc VEIKSMĪGAS pieteikšanās — atiestata skaitītāju
unset($_SESSION['login_attempts']);

Šis piemērs balstās sesijā, tāpēc uzbrucējs to var apiet, vienkārši dzēšot sīkdatnes starp mēģinājumiem. Ražošanas vidē skaitītāju labāk glabāt pēc IP adreses datubāzē vai Redis/Memcached, un WordPress projektos ērtāk lietot gatavu spraudni (piem., "Limit Login Attempts Reloaded").

HTTPS/TLS pamati

HTTPS šifrē datus starp pārlūku un serveri — bez tā jebkurš tajā pašā tīklā (piem., publiskā WiFi) var nolasīt paroles un sīkdatnes vienkāršā tekstā. Mūsdienās HTTPS ir obligāts standarts, ne izvēle.

text# .htaccess — piespiedu novirzīšana no HTTP uz HTTPS
RewriteEngine On
RewriteCond %{HTTPS} off
RewriteRule ^(.*)$ https://%{HTTP_HOST}%{REQUEST_URI} [L,R=301]

Bezmaksas, automātiski atjaunojamu SSL sertifikātu (Let's Encrypt) šodien piedāvā gandrīz katrs hostings — nav iemesla maksāt par sertifikātu. Vairāk par pašiem SSL/TLS pamatiem un DNS ierakstiem skati Tīkls kategorijā.

Drošības HTTP galvenes

HTTP atbildes galvenes, kas pasaka pārlūkam ievērot papildu drošības noteikumus — lēts, ātrs veids, kā aizvērt veselas uzbrukumu klases.

phpheader('X-Content-Type-Options: nosniff');       // aizliedz pārlūkam "uzminēt" faila tipu
header('X-Frame-Options: DENY');                 // aizliedz lapu ielikt <iframe> (clickjacking)
header('Strict-Transport-Security: max-age=31536000; includeSubDomains'); // piespiež HTTPS
header('Referrer-Policy: strict-origin-when-cross-origin'); // ierobežo URL noplūdi caur Referer

Pārbaudi savas vietnes galvenes bez koda rakstīšanas ar securityheaders.com — ielīmē URL un tas parāda, kuras galvenes trūkst un kāpēc katra svarīga.

Content Security Policy (CSP)

Galvene, kas norāda pārlūkam, no kurām vietnēm drīkst ielādēt skriptus, stilus, attēlus u.c. — pat ja XSS uzbrukums izdodas iesmidzināt <script> tagu, CSP var neļaut tam izpildīties, ja tas nenāk no atļautā avota.

phpheader("Content-Security-Policy: default-src 'self'; script-src 'self' https://www.google-analytics.com; style-src 'self' 'unsafe-inline';");

Ieviešot CSP esošā projektā, vispirms izmanto Content-Security-Policy-Report-Only galveni tā vietā — tā ziņo par pārkāpumiem konsolē, bet nebloķē neko. Tas ļauj redzēt, ko politika sabojātu, pirms to reāli aktivizē un salauž vietni.

Atkarību ievainojamības

bash# JavaScript/Node.js projektiem

GitHub repozitorijiem ieslēdz "Dependabot" (Settings → Security) — tas automātiski skenē atkarības un atver Pull Request ar labojumu, tiklīdz atklāj ievainojamību, bez manuālas npm audit palaišanas.

Failu augšupielādes drošība

Ja lapa ļauj lietotājiem augšupielādēt failus, tā ir viena no biežākajām ievainojamībām — uzbrucējs var augšupielādēt izpildāmu PHP failu, izliekoties par attēlu.

php$atlautie = ['image/jpeg', 'image/png', 'image/webp'];
$failaTips = mime_content_type($_FILES['attels']['tmp_name']); // pārbauda REĀLO tipu, ne tikai .jpg paplašinājumu

if (!in_array($failaTips, $atlautie, true)) {
    die('Nederīgs faila tips');
}

// Pārsauc failu ar nejaušu nosaukumu — novērš path traversal un uzminamus URL
$jaunaisNosaukums = bin2hex(random_bytes(16)) . '.jpg';
move_uploaded_file($_FILES['attels']['tmp_name'], $uploadDir . $jaunaisNosaukums);

Faila paplašinājums (.jpg) ir tikai nosaukums, ne garantija — uzbrucējs var nosaukt PHP failu par attels.jpg.php vai pat attels.jpg ar PHP saturu iekšā. mime_content_type() pārbauda faila reālo saturu, ne tikai nosaukumu, kas ir daudz drošāk. Augšupielāžu mapei arī vēlams liegt PHP izpildi servera konfigurācijā.

Kļūdu ziņojumi & informācijas noplūde

PHP kļūdu ziņojumi izstrādes vidē ir noderīgi, bet ražošanā tie atklāj uzbrucējam faila ceļus, datubāzes struktūru un pat daļu no koda — informāciju, kas atvieglo turpmāku uzbrukumu plānošanu.

php// Ražošanā (production) — NEKAD nerādi kļūdas apmeklētājam
ini_set('display_errors', 0);
ini_set('log_errors', 1);
ini_set('error_log', '/var/log/php-errors.log');

Kļūdas nekur nepazūd — tās joprojām tiek pilnībā pierakstītas (error_log), tikai vairs netiek rādītas apmeklētājam. Šī ir tā pati loģika, kas jau apskatīta WordPress → "There has been a critical error" — WordPress šo pašu pieeju izmanto pēc noklusējuma.
