Sākums Git

Git

Pilns iesācēja ceļvedis: kas ir versiju kontrole, kā strādāt ar Git ikdienā un kā droši sadarboties ar citiem caur GitHub - ar reāliem, darbojošos komandu piemēriem.

Kas ir Git?

Git ir versiju kontroles sistēma - programma, kas saglabā katras faila izmaiņas kā atsevišķu, laikā izsekojamu "momentuzņēmumu" (snapshot). Tā vietā, lai glabātu failus projekts_final.zip, projekts_final_v2.zip, projekts_TIESAM_final.zip, Git saglabā katru jēgpilnu izmaiņu soli ar aprakstu, un jebkurā brīdī var atgriezties pie jebkura iepriekšējā stāvokļa.

📸 Commit

Viens "momentuzņēmums" - konkrēts izmaiņu kopums ar aprakstošu ziņojumu, kāpēc tas izdarīts.

🌿 Branch (zars)

Neatkarīga izstrādes līnija - ļauj strādāt pie jaunas funkcijas, neietekmējot galveno kodu.

🔀 Merge

Apvieno viena zara izmaiņas atpakaļ citā (parasti galvenajā) zarā.

☁️ Remote

Attālināta repozitorija kopija (piem., GitHub) - ļauj dalīties ar citiem un veidot dublējumu.

Git ir izplatīta (distributed) sistēma - katram izstrādātājam datorā ir pilna projekta vēsture, ne tikai pašreizējā versija. Tāpēc lielākā daļa darbību (skatīties vēsturi, izveidot commit, salīdzināt versijas) strādā bez interneta savienojuma - tas vajadzīgs tikai, lai sinhronizētos ar citiem (skat. Remotes & clone).

Git (programma/rīks) un GitHub (mitināšanas serviss internetā) nav tas pats - Git strādā lokāli tavā datorā pat bez GitHub konta. GitHub (vai GitLab, Bitbucket) ir tikai vieta, kur glabāt attālinātu repozitorija kopiju un sadarboties ar citiem. Šī lapa apraksta gan Git pašu, gan GitHub darbam ar to.

Instalācija & konfigurācija

textWindows: lejupielādē no git-scm.com (iekļauj arī Git Bash termināli)
Mac:     brew install git   (vai jau iepriekš instalēts)
Linux:   sudo apt install git   (Debian/Ubuntu)

Pēc instalēšanas jāiestata vārds un e-pasts - tie parādīsies pie katra tavis izveidotā commit kā autors:

bashgit config --global user.name "Tavs Vārds"
git config --global user.email "tavs@epasts.lv"

# Pārbauda, kas tieši ir iestatīts
git config --list

--global nozīmē - šie iestatījumi der visiem repozitorijiem tavā datorā. Ja konkrētam projektam vajag citu e-pastu (piem., darba projektam), palaid to pašu komandu bez --global, atrodoties tā projekta mapē - tas pārraksta iestatījumu tikai tur.

Pirmais repozitorijs

Repozitorijs (repository, saīsināti "repo") ir mape, ko Git izseko - tā satur slēptu apakšmapi .git, kurā glabājas visa vēsture. Divi veidi, kā to sākt:

bash# 1. variants - jauns, tukšs repo esošā mapē
cd mans-projekts
git init

# 2. variants - lejupielādē jau esošu repo no GitHub (skat. #remotes)
git clone https://github.com/lietotajs/repo.git

Trīs pamata komandas, kas veido ikdienas ciklu:

bash# Parāda, kuri faili mainīti, jauni vai gatavi commit'am
git status

# "Sagatavo" konkrētus failus nākamajam commit - konkrētu failu vai visus
git add index.html
git add .

# Saglabā sagatavotās izmaiņas kā jaunu momentuzņēmumu ar aprakstu
git commit -m "Pievieno lietotāja reģistrācijas formu"

"Sagatavošana" (git add) ir savs, atsevišķs solis - Git NEsaglabā izmaiņas commit'ā automātiski, tikai tās, kuras skaidri pievienoji ar add. Tas ļauj izvēlēties, kuras no vairākām vienlaicīgi izdarītām izmaiņām iet vienā commit'ā, kuras citā - git status vienmēr rāda, kas tieši ir "sagatavots" un kas vēl nav.

Vēsture (log, diff)

bash# Visu commit'u saraksts, jaunākais augšā
git log

# Kompaktāks, viena rinda katram commit
git log --oneline

# Kas tieši mainījās konkrētā commit
git show a1b2c3d

# Kas mainījies kopš pēdējā commit (bet vēl nav "add"-ots)
git diff

# Kas mainījies un JAU ir "add"-ots (gatavs commit'am)
git diff --staged

Katram commit ir unikāls identifikators (piem., a1b2c3d...) - pietiek ar pirmajiem 7 simboliem, lai uz to atsauktos jebkurā komandā.

Zari (branches)

Zars ir neatkarīga izstrādes līnija - ļauj strādāt pie jaunas funkcijas vai labojuma, neietekmējot galveno (main vai master) zaru, kamēr darbs nav pabeigts un pārbaudīts.

bash# Parāda visus zarus, zvaigznīte pie pašreizējā
git branch

# Izveido jaunu zaru (bet vēl nepārslēdzas uz to)
git branch jauna-funkcija

# Pārslēdzas uz esošu zaru
git checkout jauna-funkcija
git switch jauna-funkcija    // jaunāka, skaidrāka alternatīva checkout

# Izveido UN uzreiz pārslēdzas - visbiežāk lietotais variants
git checkout -b jauna-funkcija
git switch -c jauna-funkcija

# Izdzēš zaru (tikai, ja tas jau apvienots - droši)
git branch -d jauna-funkcija

Prakses standarts - main zars vienmēr satur stabilu, strādājošu kodu. Katrai jaunai funkcijai vai labojumam izveido jaunu zaru (piem., funkcija/pieteiksanas-forma vai fix/salauzta-navigacija), strādā tur, un apvieno atpakaļ main tikai tad, kad darbs pabeigts un pārbaudīts.

Apvienošana (merge)

Kad darbs zarā pabeigts, tā izmaiņas jāapvieno atpakaļ galvenajā zarā:

bash# Vispirms pārslēdzies UZ to zaru, kurā izmaiņas jāievieto
git checkout main

# Tad apvieno otra zara izmaiņas šeit
git merge jauna-funkcija

Ja kopš zara atdalīšanas main nav mainījies, Git veic fast-forward apvienošanu - vienkārši pārvieto main rādītāju uz priekšu, bez jauna commit. Ja abi zari mainījušies neatkarīgi, Git izveido jaunu merge commit, kas apvieno abas vēstures līnijas.

Merge konflikti

Konflikts rodas, ja divi zari maina tās pašas koda rindas atšķirīgi - Git nevar pats izlemt, kura versija pareiza, un aptur apvienošanu, gaidot cilvēka lēmumu.

text<<<<<<< HEAD
<h1>Sveiki, pasaule!</h1>
=======
<h1>Laipni lūdzam!</h1>
>>>>>>> jauna-funkcija

Konflikta failā Git iezīmē abas versijas - augšējā (starp <<<<<<< HEAD un =======) ir tava pašreizējā zara versija, apakšējā (starp ======= un >>>>>>>) - otra zara versija. Risinājums:

text1. Atver failu redaktorā
2. Izvēlies pareizo tekstu (vienu, otru, vai apvieno abus pēc jēgas)
3. Izdzēs VISAS marķējuma rindas (<<<<<<<, =======, >>>>>>>)
4. git add [fails]
5. git commit   (Git jau sagatavojis merge commit ziņojumu)

Ja konflikts izskatās pārāk sarežģīts vai sāc apjukt, droši var atcelt visu mēģinājumu ar git merge --abort un sākt no jauna ar mierīgu prātu - tas atgriež visu tieši tādā stāvoklī, kāds bija pirms merge komandas, neko nezaudējot.

Rebase

Rebase ir alternatīva merge - tā vietā, lai izveidotu jaunu "apvienošanas" commit, tā pārliek tavus commit'us tā, it kā tu tos būtu uzrakstījis, sākot no jaunākās main versijas. Rezultāts - lineāra, tīrāka vēsture bez merge commit "mezgliem".

bashgit checkout jauna-funkcija
git rebase main

Zelta likums - nekad nedari rebase zaram, ko jau nosūtījis (push) un ko lieto/lejupielādējis kāds cits. Rebase pārraksta commit vēsturi (jauni ID katram commit); ja kāds cits jau strādā ar veco versiju, viņa Git nespēs to salīdzināt ar tavu jauno, un rodas sajukums. Iesācējam drošāk sākumā palikt pie merge un rebase izmantot tikai lokāliem, vēl nenosūtītiem zariem.

Remotes & clone

Remote ir saite uz attālinātu repozitorija kopiju - visbiežāk GitHub. origin ir standarta nosaukums galvenajam remote.

bash# Lejupielādē jau esošu repo, ar VISU vēsturi, savā datorā
git clone https://github.com/lietotajs/repo.git

# Pievieno remote esošam, lokāli izveidotam repo (git init)
git remote add origin https://github.com/lietotajs/repo.git

# Parāda, kādi remotes ir pievienoti
git remote -v

push / pull / fetch

bash# Nosūta tavus lokālos commit'us uz remote
git push origin main

# Pirmajai push reizei jaunam zaram - iestata sekošanas saiti,
# lai turpmāk pietiek ar vienkāršu "git push"
git push -u origin jauna-funkcija

# Lejupielādē UN uzreiz apvieno citu jaunās izmaiņas no remote
git pull

# Tikai lejupielādē jaunāko info par remote, NEAPVIENO neko
git fetch

git pull ir īsumā git fetch + git merge vienā komandā. Ja gribi vispirms redzēt, KAS tieši mainījies attālinātajā versijā, pirms to apvieno ar savu darbu, izmanto fetch atsevišķi un pārbaudi ar git log origin/main, tad lem, vai merge vai rebase.

SSH atslēgas GitHub autentifikācijai

Pieslēdzoties GitHub caur https:// adresi, katru push reizi jāievada lietotājvārds/tokens. Ērtāk - izveidot SSH atslēgu pāri un pieslēgties caur git@github.com:... adresi, kur autentifikācija notiek automātiski (skat. arī vispārīgo SSH skaidrojumu par pašu protokolu):

bash# 1. Izveido atslēgu pāri (ja vēl nav)
ssh-keygen -t ed25519 -C "tavs@epasts.lv"

# 2. Nokopē PUBLISKĀS atslēgas saturu (Windows piemērs)
type %USERPROFILE%\.ssh\id_ed25519.pub | clip

# 3. GitHub → Settings → SSH and GPG keys → New SSH key → ielīmē

# 4. Pārbauda, vai savienojums strādā
ssh -T git@github.com

Pēc atslēgas pievienošanas jauniem repo klonē ar SSH adresi (nevis https://):

bashgit clone git@github.com:lietotajs/repo.git

Repo, kas jau klonēts ar https://, var pārslēgt uz SSH bez atkārtotas klonēšanas:

bashgit remote set-url origin git@github.com:lietotajs/repo.git

Pull requesti (PR)

Pull request (GitLab sauc to par Merge Request) nav Git komanda - tā ir GitHub/GitLab funkcija virs Git: pieprasījums apvienot izmaiņas no viena zara citā, ar iebūvētu vietu diskusijai, koda pārskatīšanai (code review) un automātiskām pārbaudēm (CI), pirms izmaiņas nonāk galvenajā zarā.

text1. Izveido jaunu zaru, izdari izmaiņas, nosūti (push) uz GitHub
2. GitHub lapā parādās poga "Compare & pull request"
3. Uzraksti aprakstu - KO un KĀPĒC šī izmaiņa dara
4. Pieprasi pārskatīšanu (review) no komandas biedra
5. Pēc apstiprinājuma - "Merge pull request"

Daudzi projekti iestata branch protection - noteikumu, ka main zarā nevar nosūtīt (push) tieši, tikai caur apstiprinātu pull request. Tas pasargā no nejaušām, nepārbaudītām izmaiņām galvenajā, vienmēr strādājošajā kodā.

.gitignore

Fails .gitignore projekta saknē pasaka Git, kurus failus/mapes nekad nesekot un neieteikt pievienot - parasti ģenerētus failus, atkarības un slepenus datus, kam nav vietas versiju kontrolē.

text# .gitignore
node_modules/
vendor/
.env
*.log
.DS_Store
/dist

.gitignore darbojas tikai failiem, kas Git vēl NAV izsekojis. Ja fails (piem., .env ar slepenām atslēgām) kādreiz jau tika pievienots ar git add un commit'ots, tas paliks vēsturē pat pēc pievienošanas .gitignore - jāizmanto git rm --cached fails, lai to izņemtu no izsekošanas (bet tas nedzēš no vēstures - jau nosūtītas atslēgas jāuzskata par kompromitētām un jānomaina).

Izmaiņu atsaukšana

Vairāki līmeņi, atkarībā no tā, cik "dziļi" jāatsaucas:

KomandaKo dara
git restore fails.txtAtceļ nesaglabātas izmaiņas failā, atgriežot to uz pēdējo commit
git reset --soft HEAD~1Atceļ pēdējo commit, bet SAGLABĀ izmaiņas kā "sagatavotas"
git reset HEAD~1Atceļ pēdējo commit, izmaiņas paliek, bet vairs nav "sagatavotas"
git reset --hard HEAD~1Atceļ pēdējo commit UN pilnībā izdzēš izmaiņas - neatgriezeniski
git revert a1b2c3dIzveido JAUNU commit, kas atceļ norādītā commit izmaiņas - vēsture paliek neskarta

git reset --hard neatgriezeniski dzēš nesaglabātu darbu - pirms to lietot, pārliecinies, ka tiešām neko nevajag. Ja commit jau nosūtīts (push) uz remote, ko lieto citi, izmanto git revert nevis reset - revert nemaina vēsturi, tikai pievieno "labojošu" commit, tāpēc nesajauc citu izstrādātāju kopijas.

git stash

Kad darbs vidū, bet steidzami jāpārslēdzas uz citu zaru (piem., steidzams labojums), git stash īslaicīgi "noliek plauktā" nesaglabātās izmaiņas, atgriežot darba mapi tīru:

bash# Noliek pašreizējās nesaglabātās izmaiņas plauktā
git stash

# ... pārslēdzies, izdari steidzamo labojumu, commit, push ...

# Atgriež pēdējo noliktās izmaiņas atpakaļ un izņem no plaukta
git stash pop

# Parāda visu, kas šobrīd atrodas plauktā
git stash list

📦 Mazi, atomiski commit

Katrs commit - viena loģiska izmaiņa. Vieglāk pārskatīt, vieglāk atsaukt tikai to vienu, ja vajag.

🔄 Bieža sinhronizācija

Regulārs pull/push mazina konfliktu risku - jo ilgāk zars atdalīts, jo vairāk tas atšķiras.

🚫 Nekad secrets Git

Atslēgas/paroles Git vēsturē paliek uz visiem laikiem, pat pēc izdzēšanas no faila (skat. .gitignore).
