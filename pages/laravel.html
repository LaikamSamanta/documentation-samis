Sanctum vs sesiju autentifikācija (Inertia)

Inertia + Fortify

  • Viens projekts, viens deploy, sesiju auth.
  • Vienkāršāk, mazāk kustīgu daļu.
  • Filament strādā arī šeit - bet tikai kā cits route (piem. /admin) tajā pašā vienā appā/portā, ne atsevišķi.

Trūkums: mobile app vai atsevišķa izvietošana = pārtaisīt no nulles.

Sanctum + React Router

  • API (service-platform) + frontend (service-platform-public), katrs savs deploy.
  • API gatavs jauniem klientiem (mobile, trešā puse).
  • Filament dzīvo service-platform (API) pusē - tas jau ir atsevišķs deploy/ports no service-platform-public, kur klienti ielogojas.

Trūkums: CORS, tokeni, divi deploy procesi - attaisnojas tikai izmantojot elastīgumu.

Kāpēc tieši tokens, nevis sesijas cookie

Vienā domēnā pārlūks pievieno cookie pats; atsevišķos domēnos backend to nesaņem, tāpēc frontend katram pieprasījumam manuāli pievieno tokenu.

Kods: Inertia (cookie) vs Sanctum (tokens)

Inertia - sesijas cookie (automātiski)

js// POST - cookie pārlūks pievieno pats, papildu koda nav
const res = await fetch("/api/orders", {
  method: "POST",
  headers: { "Content-type": "application/json" },
  body: JSON.stringify({ product_id: 5 }),
});
const order = await res.json();

// PUT - tas pats, tikai body mainās
await fetch(`/api/orders/${order.id}`, {
  method: "PUT",
  headers: { "Content-type": "application/json" },
  body: JSON.stringify({ qty: 2 }),
});

// DELETE - body nav vajadzīgs, cookie vienalga automātisks
await fetch(`/api/orders/${order.id}`, { method: "DELETE" });

Sanctum - Bearer tokens (manuāli)

js// 1) POST /login - ATBILDES (response) body satur tokenu
const res = await fetch(`${apiUrl}/login`, {
  method: "POST",
  headers: { "Content-type": "application/json" },
  body: JSON.stringify({ email, password }),
});
const { token } = await res.json();
localStorage.setItem("token", token);

// 2) GET /user - PIEPRASĪJUMA (request) header nes tokenu, ne body
const res2 = await fetch(`${apiUrl}/user`, {
  method: "GET",
  headers: { Authorization: `Bearer ${token}` },
});
const user = await res2.json();

// 3) PUT - header paliek tas pats, papildus nāk body
await fetch(`${apiUrl}/user/${user.id}`, {
  method: "PUT",
  headers: { "Content-type": "application/json", Authorization: `Bearer ${token}` },
  body: JSON.stringify({ name: "Jauns vārds" }),
});

// 4) DELETE - header vienmēr jāpievieno, body nevajag
await fetch(`${apiUrl}/user/${user.id}`, {
  method: "DELETE",
  headers: { Authorization: `Bearer ${token}` },
});

Sanctum vajag, ja: (1) vairāk kā viens klients (web + mobile, trešā puse), VAI (2) frontend ir atsevišķs projekts uz cita domēna.

Postman + CSRF: 419 kļūda

web maršrutiem ir CSRF aizsardzība - POST bez derīga tokena dod 419. Risinājums:

  • GET lapu → dabū XSRF-TOKEN cookie → pievieno kā X-XSRF-TOKEN galveni POST, vai
  • Postman: ieslēdz cookie pārvaldību, tad GET → POST.

Factory vs Seeder

factory definē veidni - kā izskatās viens fake ieraksts. seeder izpilda to veidni - izsauc to un faktiski ieraksta datus datubāzē, kad palaid php artisan db:seed.

Standarta secība, veidojot jaunu funkciju

Jaunai admin sadaļai (piem. "Products") - vienmēr šī secība, jo kontrolieris izmanto modeli (Product::all()), un modelim jāzina sava tabula/kolonnas:

1. Migrācija - tabulas struktūra

bashphp artisan make:migration create_products_table
# rediģē database/migrations/..._create_products_table.php
php artisan migrate

2. Modelis - PHP klase, kas savieno ar tabulu

bashphp artisan make:model Product

3. Kontrolieris - loģika, kas apstrādā pieprasījumus

bashphp artisan make:controller Admin/ProductController --resource

--resource uzreiz uzģenerē visas CRUD metodes: index, create, store, edit, update, destroy.

4. Maršruti

phpRoute::resource('admin/products', Admin\ProductController::class);

Atkarīgs no auth veida (sk. augstāk). Sanctum/API: publiskie maršruti web.php, token API maršruti api.php (bez sesijām). Sesiju/Inertia (tavs gadījums): viss paliek web.php - api.php pēc noklusējuma nesniedz sesijas/CSRF.

5. Frontend (Inertia lapa)

resources/js/components/admin/Products.jsx (+ pages/admin/Products.jsx re-export). Kontroliera index() metode atgriež inertia('admin/Products', ['products' => Product::all()]).

Paātrinājums - Migrāciju + Modeli + Kontrolieri var izveidot vienā komandā: php artisan make:model Product -mcr (-m = migration, -c = controller, -r = resource metodes).

fetch() - GET vs POST

fetch() pēc noklusējuma vienmēr izmanto GET metodi, ja method nav norādīts.

fetch.js

fetch(url) // nav method → GET

fetch(url, { method: "POST", ... }) // jānorāda skaidri

GET (noklusējums - method nav norādīts)

jsconst res = await fetch(`${apiUrl}/categories/list`);
const result = await res.json();

if (result.status == 200) {
  setCategories(result.data);
}

POST (method jānorāda skaidri)

jsconst res = await fetch(`${apiUrl}/categories`, {
  method: "POST",
  headers: { "Content-type": "application/json" },
  body: JSON.stringify(data),
});
const result = await res.json();

Kas vēl jāzina par fetch()

  • GET pieprasījumam nedrīkst sūtīt body - dati jāliek URL/query parametros, ne pieprasījuma ķermenī.
  • Atbilde jāparsē ar .json() - arī tas ir Promise, tāpēc parasti ir divi await: viens fetch(), otrs .json().
  • POST/PUT/PATCH ar JSON datiem vienmēr vajag headers: {"Content-type": "application/json"} un body: JSON.stringify(...) - bez tā serveris datus pareizi nesapratīs.

fetch() nemet kļūdu HTTP kļūdas gadījumā (piem. 404, 500) - Promise noraidās tikai tad, ja pieprasījums vispār neaizsniedz serveri (tīkla kļūda). Lai noķertu HTTP kļūdas, pirms .json() pašam jāpārbauda res.ok vai res.status.

Inertia.js - kas tā ir un kāpēc

Inertia ir "līme" starp Laravel (backend) un React/Vue/Svelte (frontend). Tā ļauj taisīt vienas lapas (SPA) sajūtu bez atsevišķa API un bez frontend maršrutētāja - maršruti, kontrolieri, validācija un autentifikācija paliek Laravel pusē. Šī lapa ir vispārīga: kā Inertia darbojas, kur kas atrodas projektā, kā reģistrēt middleware un kādas kļūdas gadās visbiežāk. Piemēri ņemti no reāla Laravel + React + Vite projekta.

Klasisks Laravel (Blade)

  • Katrs klikšķis = pilna lapas pārlāde.
  • UI rakstīts Blade šablonos.
  • Nav "lietotnes" sajūtas, bet viss vienā vietā.

Laravel API + atsevišķs React

  • Divi projekti, CORS, tokeni, divi deploy.
  • Frontend pats dara routing un auth.
  • Elastīgi, bet daudz kustīgu daļu.

Inertia

  • Viens projekts, viens deploy, sesiju auth.
  • Kontrolieris atgriež komponenti + datus, nevis HTML vai JSON.
  • Klikšķi ir XHR pieprasījumi, lapa nepārlādējas.

Inertia nav framework un nav API bibliotēka. Tā ir tikai protokols (kā servera atbilde tiek pārvērsta par frontend lapu) + divi mazi pakotņu komplekti: inertiajs/inertia-laravel (PHP) un @inertiajs/react (JS).

Kā tas darbojas - pieprasījuma cikls

Pirmais pieprasījums atdod pilnu HTML ar sākuma datiem. Pēc tam Inertia visus <Link> klikšķus pārtver un dabū tikai JSON.

"Page objekts" - viss, ko serveris atgriež

Inertia atbilde (gan HTML iekšā, gan JSON) vienmēr ir viens un tas pats objekts:

json{
  "component": "Product",          // kuru lapas komponenti rādīt
  "props": {                        // dati komponentei (kontrolieris + shared data)
    "product": { "id": 5, "title": "..." },
    "auth": { "user": null },
    "errors": {}
  },
  "url": "/product/5",
  "version": "c32b8e4965f418..."  // assetu versija (sk. zemāk)
}

Asset versijas pārbaude (409)

Katrā pieprasījumā klients nosūta savu version. Ja pēc deploy tā vairs nesakrīt ar servera versiju (version() metode middleware), serveris atbild 409 Conflict un Inertia veic pilnu pārlādi, lai lietotājs dabūtu jaunos JS/CSS failus. Tāpēc pēc deploy reizēm redzama viena "nepamatota" pārlāde - tā ir normāla.

Middleware: kur to atrast, kā reģistrēt (mapot)

1. Pats middleware fails

Inertia middleware ir parasta Laravel klase, kas paplašina Inertia\Middleware. To izveido ar:

bashphp artisan inertia:middleware
# → app/Http/Middleware/HandleInertiaRequests.php

2. Reģistrācija - bootstrap/app.php (Laravel 11+)

Middleware "mapošana" jeb pieslēgšana notiek tikai šeit. Inertia jāpievieno web grupas beigās (append), lai sesija un cookie jau būtu apstrādāti:

php->withMiddleware(function (Middleware $middleware): void {
    // globāli - visiem pieprasījumiem (piem. proxy uzticēšanās)
    $middleware->trustProxies(at: '*');

    // sīkdatnes, kuras NEšifrē (frontend tās lasa pats)
    $middleware->encryptCookies(except: ['appearance', 'sidebar_state']);

    // web grupa - visi maršruti no routes/web.php
    $middleware->web(append: [
        HandleAppearance::class,
        HandleInertiaRequests::class,   // ← Inertia
        AddLinkHeadersForPreloadedAssets::class,
    ]);
})

Trīs veidi, kā piesaistīt middleware

LīmenisKāKad lietot
Globāli$middleware->append(X::class)Jādarbojas visam, arī API un /up health-check.
Grupai$middleware->web(append: [...]) / ->api(...)Jādarbojas visām web lapām. Inertia dzīvo šeit.
Konkrētam maršrutamRoute::get(...)->middleware('auth') vai Route::middleware('auth')->group(...)Aizsargāt daļu lapu (piem. /admin/*).
 
php// vairāki maršruti zem viena middleware - nav jāatkārto katram
Route::middleware(['auth'])->prefix('admin')->group(function () {
    Route::inertia('/dashboard', 'admin/Dashboard')->name('admin.dashboard');
});

Ja Inertia middleware nav reģistrēts, inertia(...) joprojām atgriež lapu, bet share() dati (auth, errors...) nenonāk frontendā un XHR navigācija/versijas pārbaude nestrādā pareizi.

3. Ko var iestatīt pašā HandleInertiaRequests

phpclass HandleInertiaRequests extends Middleware
{
    // Blade fails, kas tiek ielādēts pirmajā apmeklējumā
    protected $rootView = 'app';

    // assetu versija - mainās pēc build → 409 → pilna pārlāde
    public function version(Request $request): ?string
    {
        return parent::version($request);
    }

    // props, kas nonāk KATRĀ lapā
    public function share(Request $request): array
    {
        return [
            ...parent::share($request),
            'name' => config('app.name'),
            'auth' => ['user' => $request->user()],
            'categories' => fn () => Category::where('status', 1)->get(),
        ];
    }
}

4. Shared data lasīšana frontendā

jsximport { usePage } from "@inertiajs/react";

export default function Header() {
  // viss, kas atgriezts no share() vai kontroliera, ir usePage().props
  const { categories, auth } = usePage().props;
  ...
}

Ja vērtība ir closure (fn () => ...), tā tiek izpildīta tikai tad, kad tiešām vajadzīga - un partial reload gadījumā to var izlaist. Ja tā ir tieša vērtība, DB vaicājums notiek katrā pieprasījumā.

Visi props ir redzami pārlūkā (View Source / Network). $request->user() nodod visus modeļa laukus, ja tie nav slēpti ($hidden). Nekad neliec shared data parolēm, tokeniem vai iekšējiem laukiem - atlasi tikai to, ko UI tiešām vajag.

Servera puse - kā atgriezt lapu

Trīs ekvivalenti veidi

Pēc formas iesniegšanas - redirect, nevis JSON

phppublic function update(ProfileUpdateRequest $request): RedirectResponse

Inertia pieprasījumam Laravel jāatgriež redirect vai Inertia atbilde. Ja atgriež parastu response()->json(...), Inertia rāda kļūdu "All Inertia requests must receive a valid Inertia response" (modālis pārlūkā).

Lapas vs komponentes - biežs sajaukums

Mapē pages/ ir tikai tas, ko var atgriezt no kontroliera. Praktiska pieeja: lapas fails ir plāns re-export, reālā UI dzīvo components/:

jsx// resources/js/pages/admin/Login.jsx
export { default } from '@/components/admin/Login';

Tas ļauj @ aliasam (vite.config) norādīt uz resources/js un turēt lapu mapi tīru.

Otrs veids - fetch + JSON (bieži sastopams "hibrīds")

Var arī iekš Inertia lapas izsaukt fetch/axios uz endpointu, kas atgriež response()->json(...) (piem. admin CRUD ar react-hook-form), un tad pašiem apstrādāt status/errors, pēc tam router.visit(...). Tas strādā, jo endpoints nav Inertia pieprasījums, bet:

  • validācijas kļūdas nenonāk automātiski props.errors - jāapstrādā manuāli;
  • paši jāpiemin CSRF (X-XSRF-TOKEN no cookie) - useForm/router to dara pats;
  • tas ir puse "API" un puse "Inertia" - jāsaprot, kāpēc, lai nesajauktu (sk. Sanctum vs sesijas).

Flash ziņojumi

Inertia::flash('toast', [...]) servera pusē → frontendā to nolasa no usePage().props (vai flash, atkarībā no versijas) un parāda kā toast/paziņojumu. Dati pazūd pēc nākamā pieprasījuma.

Redirect kodi

PUT/PATCH/DELETE pēc redirect jāatgriež kā 303 See Other, citādi pārlūks atkārto to pašu metodi uz jaunā URL. Inertia middleware to pārveido automātiski, tāpēc parasts redirect() kontrolierī ir pietiekams.

Kā debugot

  • Network cilnē filtrē uz Fetch/XHR - Inertia pieprasījumiem ir galvene X-Inertia: true, atbilde ir page objekts (component, props).
  • Pirmajā HTML atbildē (View Source) redzams sākuma page objekts saknes elementā.
  • Sarakstu ar visiem maršrutiem: php artisan route:list - lai pārbaudītu, kuri maršruti ir web un kuri aizsargāti.
