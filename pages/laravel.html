Sanctum vs sesiju autentifikācija (Inertia)

Reāla arhitektūras izšķiršanās no service-platform projekta - kāpēc tas šobrīd ir divi atsevišķi projekti ar Sanctum tokeniem, nevis viens Inertia + Fortify monolīts, un kad tas otrs variants būtu bijis vienkāršāk.

Inertia + Fortify (nav izmantots)

  • Viens Laravel projekts, viens deploy - backend un frontend kopā.
  • Autentifikācija caur sesijām, bez tokenu pārvaldības.
  • Admin panelis jāraksta pašam ar React/Inertia lapām (nav Filament gatavo tabulu/formu).
  • Vienkāršāk uzturēt, mazāk kustīgu daļu, ātrāk attīstīt.

Trūkums: ja kādreiz tomēr gribēsies mobilo app vai atsevišķu izvietošanu - jāpārtaisa arhitektūra no nulles.

Sanctum + React Router (tā ir tagad)

  • Divi atsevišķi projekti - Laravel API (service-platform) + React Router frontend (service-platform-public), katrs ar savu deploy.
  • Autentifikācija caur Sanctum tokeniem.
  • Admin panelis caur Filament - gatavas tabulas/formas bez pašrakstīšanas.
  • Elastīgāk - API gatavs jauniem klientiem (mobile, trešā puse) bez pārtaisīšanas.

Trūkums: vairāk sarežģītības (CORS, tokeni, divi deploy procesi) - attaisnojas tikai tad, ja tas elastīgums tiešām tiek izmantots.

Kopsavilkums: ar Filament un iespējamu nākotnes API patērētāju Sanctum izvēle ir pamatota. Bez tiem diviem iemesliem Inertia + Fortify būtu bijusi vienkāršāka, tikpat laba izvēle.

Kāpēc tieši tokens, nevis sesijas cookie

Viss kopā (Inertia) - frontend un backend ir viena aplikācija, viens domēns. Pārlūks automātiski glabā un sūta sesijas cookie, tāpēc backend katrā pieprasījumā jau zina, kurš tu esi - tokens būtu lieks.

Sanctum gadījumā (atsevišķi) - frontend un backend ir divas atšķirīgas programmas, varbūt pat citi domēni. Cookie automātiski nesūtīsies pāri uz backend, tāpēc vajag citu veidu, kā backend zina, kurš pieprasījumu sūta - tas ir tokens, ko frontend pats glabā un pievieno katram pieprasījumam.

Tātad Sanctum vajag, ja: (1) ir vairāk kā viena frontend/klienta aplikācija (web + mobile, vai tava app + trešā puse), VAI (2) frontend ir pilnīgi atsevišķs projekts uz cita domēna, kur cookie sesijas automātiski nedarbotos. Ja tavu projektu kādreiz sadalītu divās daļās (piem., backend paliek Laravel, bet frontend pārtaisītu par atsevišķu React app citā portā/domēnā) - tad pēkšņi vajadzētu Sanctum, jo cookie vairs automātiski nestrādātu pāri šai robežai.

Postman + CSRF: 419 kļūda

Laravel web maršrutiem pēc noklusējuma ir CSRF aizsardzība - ja Postman sūta POST bez derīga CSRF tokena, dabū 419 kļūdu, nevis savu loģiku. Lai to apietu testēšanai:

  • vispirms izsauc GET uz kādu lapu, lai dabūtu XSRF-TOKEN cookie, un pievieno to kā X-XSRF-TOKEN galveni POST pieprasījumam, vai
  • Postman kolekcijas iestatījumos ieslēdz cookie pārvaldību un izmanto pareizo secību (GET → paņem token → POST ar to).

Factory vs Seeder

factory definē veidni - kā izskatās viens fake ieraksts. seeder izpilda to veidni - izsauc to un faktiski ieraksta datus datubāzē, kad palaid php artisan db:seed.

Standarta secība, veidojot jaunu funkciju

Ikreiz, kad service-platform vajag jaunu admin sadaļu (piem. "Products" - redzams sidebar), šie pieci soļi vienmēr notiek šādā secībā. Iemesls, kāpēc secība ir svarīga: kontrolieris izmanto modeli (Product::all(), Product::create()), un modelim jāzina, kādai tabulai/kolonnām tas atbilst - tāpēc migrācija un modelis vienmēr ir pirms kontroliera, ne otrādi.

1. Migrācija - tabulas struktūra

bashphp artisan make:migration create_products_table
# rediģē database/migrations/..._create_products_table.php
php artisan migrate

2. Modelis - PHP klase, kas savieno ar tabulu

bashphp artisan make:model Product

3. Kontrolieris - loģika, kas apstrādā pieprasījumus

bashphp artisan make:controller Admin/ProductController --resource

--resource uzreiz uzģenerē visas CRUD metodes: index, create, store, edit, update, destroy.

4. Maršruti

phpRoute::resource('admin/products', Admin\ProductController::class);

Kurā failā šo raksta ir atkarīgs no projekta autentifikācijas veida (sk. Sanctum vs sesiju autentifikācija augstāk). Sanctum/API projektos publiskie/lapu maršruti iet web.php (sesijas, CSRF), bet token-autentificētie API maršruti iet api.php (bez sesijām, ar /api prefiksu) - tā api grupa ir domāta tikai token autentifikācijai, ne sesiju autentifikācijai. Sesiju/Inertia projektos (tavs gadījums) viss paliek web.php, jo visam vajag sesijas/CSRF, ko api.php grupa pēc noklusējuma nesniedz.

5. Frontend (Inertia lapa)

resources/js/components/admin/Products.jsx (+ pages/admin/Products.jsx re-export). Kontroliera index() metode atgriež inertia('admin/Products', ['products' => Product::all()]).

Paātrinājums - Migrāciju + Modeli + Kontrolieri var izveidot vienā komandā: php artisan make:model Product -mcr (-m = migration, -c = controller, -r = resource metodes).
