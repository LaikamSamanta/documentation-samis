Sākums Laravel

Laravel

Pilns iesācēja ceļvedis PHP framework Laravel - routing, Eloquent ORM, Blade veidnes, autentifikācija, queues un testēšana. Visi piemēri pārbaudīti pret reālu Laravel 13 projektu.

Kas ir Laravel?

Laravel ir PHP framework - gatavs, strukturēts pamats web lietotņu veidošanai, kas jau atrisina biežākās problēmas (routing, datubāzes pieslēgšana, autentifikācija, e-pasti, kešošana), lai programmētājam nav jāraksta tas viss no nulles katrā projektā. Salīdzinājumā ar "tīru" PHP vai WordPress - Laravel neuzspiež gatavu satura struktūru (ierakstus, lapas), bet dod arhitektūru jebkurai lietotnei (API, SaaS produkts, iekšējs rīks, e-komercija).

MVC arhitektūra

Model (dati, Eloquent) - View (Blade veidnes) - Controller (loģika starp tiem). Katrai daļai sava, paredzama vieta failu struktūrā.

Kad izvēlēties Laravel

Lietotnēm ar pielāgotu datu modeli, API, lietotāju kontiem, maksājumiem - kur WordPress satura struktūra būtu šķērslis, nevis palīdzība.

Kad NEizvēlēties

Vienkāršai satura vietnei/blogam - WordPress vai statisks ģenerators (skat. Tīkls) būs ātrāk uzstādāms un vieglāk uzturams saturam.

Šī dokumentācija izmanto vienu caurviju piemēru - emuāra Post (raksts) un Comment (komentārs) modeļus ar lietotāju - lai katras sadaļas kods dabiski savienotos ar iepriekšējo, tāpat kā reālā projektā.

Instalācija & projekta struktūra

Laravel prasa PHP 8.2+ un Composer - jauns projekts vienmēr sākas ar composer create-project, nevis lejupielādējot ZIP failu.

bash# Izveido jaunu Laravel projektu mapē "mans-projekts"
composer create-project laravel/laravel mans-projekts

cd mans-projekts

# Iebūvētais dev serveris - der lokālai izstrādei, nevis produkcijai
php artisan serve
# → http://127.0.0.1:8000

Svarīgākās mapes, ar kurām strādāsi ikdienā:

textapp/Models/          - Eloquent modeļi (dati)
app/Http/Controllers/ - Controllers (pieprasījumu loģika)
app/Http/Middleware/  - Middleware
app/Http/Requests/    - Form Request validācijas klases
routes/web.php        - Maršruti pārlūkam (ar sesijām, CSRF)
routes/api.php        - Maršruti API (bez sesijām, stateless)
routes/console.php    - Artisan komandas + Task Scheduling
database/migrations/  - Datubāzes shēmas izmaiņas
database/factories/   - Testa datu ģeneratori
resources/views/      - Blade veidnes
bootstrap/app.php      - Vidusprogrammatūras, izņēmumu, routing konfigurācija

Laravel 11+ (arī šeit aprakstītajā 13. versijā) vairs nav app/Http/Kernel.php vai app/Providers/EventServiceProvider.php - middleware, izņēmumu apstrāde un routing tagad konfigurēti tieši bootstrap/app.php failā. Ja redzi tutoriālu, kas piemin Kernel.php, tas raksta par veco (10. vai senāku) versiju - struktūra kopš tā laika mainījusies.

Routing

Maršruti savieno URL ar kodu, kas to apstrādā - definēti routes/web.php (parastām lapām) vai routes/api.php (JSON API).

phpuse Illuminate\Support\Facades\Route;

// Vienkāršs maršruts ar closure
Route::get('/sveiciens/{vards}', function (string $vards) {
    return "Sveiki, {$vards}!";
});

// Maršruts, kas ved uz controller metodi
Route::get('/posts/{post}', [PostController::class, 'show']);

// Viens ieraksts reģistrē VISUS CRUD maršrutus uzreiz (index/store/show/update/destroy)
Route::resource('posts', PostController::class);

// Tas pats, bet bez create/edit (JSON API neko nerāda formās)
Route::apiResource('posts', PostController::class);

// Grupa - visiem iekšā esošajiem maršrutiem piemēro middleware uzreiz
Route::middleware('auth')->group(function () {
    Route::resource('posts', PostController::class)->except(['index', 'show']);
});

{post} parametrā notiek route model binding - Laravel pats atrod Post ierakstu pēc ID no URL un padod GATAVU modeli controller metodei (skat. Controllers), nevis tikai skaitli, ko pašam vēl jāmeklē datubāzē.

Visus reģistrētos maršrutus (arī tos, ko pievieno spraudņi/paketes) redzi ar php artisan route:list - noder, ja "404" parādās negaidīti un jāpārbauda, vai maršruts vispār eksistē tādā formā, kā domāts.

Controllers

Controller pieņem pieprasījumu, izsauc vajadzīgo loģiku (parasti caur modeli) un atgriež atbildi. Resource controller jau iepriekš sagatavo 7 standarta metodes pilnam CRUD.

bashphp artisan make:controller PostController --resource
phpclass PostController extends Controller
{
    public function index()
    {
        $posts = Post::withCount('comments')->latest()->paginate(10);

        return new PostResource::collection($posts);
    }

    public function store(StorePostRequest $request)
    {
        $post = $request->user()->posts()->create($request->validated());

        return new PostResource($post);
    }

    // {post} no maršruta URL automātiski pārvēršas par ŠO, jau ielādētu Post modeli
    public function show(Post $post)
    {
        return new PostResource($post->load('user')->loadCount('comments'));
    }

    public function destroy(Post $post)
    {
        $post->delete();

        return response()->noContent();
    }
}

$request->user()->posts()->create(...) ir droši pēc konstrukcijas - jaunais raksts VIENMĒR pieder pieteikušamies lietotājam, jo user_id aizpilda pati attiecība (skat. Attiecības), nevis kaut kas no pieprasījuma datiem, ko varētu viltot.

Blade veidnes

Blade ir Laravel veidņu dzinējs - parasts HTML ar īpašiem {{ }} (izvada, automātiski aizsargā pret XSS) un @ direktīvām. Faili beidzas ar .blade.php.

Layout (kopīgs karkass)

html<!-- resources/views/layouts/app.blade.php -->
<!doctype html>
<html>
<head><title>@yield('title', 'Mana vietne')</title></head>
<body>
    <main>@yield('content')</main>
</body>
</html>

Konkrēta lapa, kas izmanto layout

html<!-- resources/views/posts/index.blade.php -->
@extends('layouts.app')

@section('title', 'Visi raksti')

@section('content')
    <x-alert type="success">Ielādēti {{ $posts->count() }} raksti.</x-alert>

    @forelse ($posts as $post)
        <article>
            <h2>{{ $post->title }}</h2>
            @if ($post->published)
                <span>Publicēts</span>
            @endif
        </article>
    @empty
        <p>Nav rakstu.</p>
    @endforelse
@endsection

Pielāgots komponents ar slot

html<!-- resources/views/components/alert.blade.php -->
     lieto kā <x-alert type="success">...</x-alert> -->
<div class="alert alert-{{ $type ?? 'info' }}">
    {{ $slot }}
</div>

{{ }} vs {!! !!}

Divkāršās figūriekavas automātiski "escapo" HTML (pasargā no XSS). {!! !!} izvada NEfiltrētu HTML - lieto tikai uzticamam saturam.

@yield vs $slot

@yield/@section der VESELAI lapai, kas manto layout. $slot der mazam, atkārtoti lietojamam komponentam (poga, karte, brīdinājums).

Automātiska komponentu atrašana

<x-alert> automātiski atrod resources/views/components/alert.blade.php - nekas papildus jāreģistrē.

Migrations

Migration ir versionēts datubāzes shēmas izmaiņu apraksts kodā - komandas biedri palaiž to pašu migrāciju un iegūst identisku shēmu, bez manuālas SQL kopēšanas (skat. arī Datubāzes / SQL vispārīgam SQL pamatam).

bash# Izveido migrāciju UN modeli UN factory vienā komandā
php artisan make:model Post -mf
php// database/migrations/..._create_posts_table.php
return new class extends Migration
{
    public function up(): void
    {
        Schema::create('posts', function (Blueprint $table) {
            $table->id();
            $table->foreignId('user_id')->constrained()->cascadeOnDelete();
            $table->string('title');
            $table->text('body');
            $table->boolean('published')->default(false);
            $table->timestamps();
        });
    }

    public function down(): void
    {
        Schema::dropIfExists('posts');
    }
};
bash# Palaiž visas vēl nepalaistās migrācijas
php artisan migrate

# Atceļ pēdējo migrāciju partiju UN palaiž no jauna - noder izstrādē
php artisan migrate:fresh

migrate:fresh izdzēš VISAS tabulas un izveido no jauna - lieto tikai lokālai izstrādei, nekad produkcijā (tur dati tiešām pazūd, ne tikai shēma atiestatās).

foreignId('user_id')->constrained() īsceļš pats uzmin, ka atsauce ved uz users tabulas id kolonnu - garā forma būtu foreignId('user_id')->constrained('users', 'id'). cascadeOnDelete() nozīmē - izdzēšot lietotāju, automātiski izdzēšas arī visi tā raksti.

Eloquent modeļi

Eloquent ir Laravel ORM (Object-Relational Mapping) - katra datubāzes tabula atbilst vienai PHP klasei, katra rinda vienam objektam. Nav jāraksta neviena SQL rinda pamata darbībām.

phpclass Post extends Model
{
    use HasFactory;

    // Kuras kolonnas drīkst masveidā aizpildīt caur create()/fill() - aizsardzība
    // pret "mass assignment" - lai kāds nepaslīdinātu iekšā kolonnu, kas nebija domāta
    protected $fillable = ['title', 'body', 'published', 'user_id'];

    // Automātiski pārvērš tipu, lasot/rakstot - šeit "0"/"1" no DB kļūst par īstu bool PHP pusē
    protected $casts = [
        'published' => 'boolean',
    ];
}
php// Pamata darbības - visas šīs ģenerē un izpilda SQL "aiz kadra"
Post::create(['title' => 'Jauns raksts', 'body' => '...', 'user_id' => 1]);
Post::find(1);                       // atgriež null, ja neatrasts
Post::findOrFail(1);                 // izmet 404, ja neatrasts - der controlleros
Post::all();
$post->update(['title' => 'Mainīts nosaukums']);
$post->delete();

Laravel 13 arī pieļauj $fillable/$hidden deklarēt kā PHP atribūtus (#[Fillable([...])] virs klases) - tas ir jaunāks, alternatīvs sintakses veids tam pašam mērķim. Šī dokumentācija izmanto klasisko protected $fillable īpašību, jo tā strādā VISĀS Laravel versijās un ir biežāk sastopama esošā kodā.

Attiecības (relationships)

Attiecības apraksta, kā modeļi savā starpā savienoti - definē vienreiz modelī, tad lieto kā parastu īpašību/metodi jebkur citur.

Katrai attiecībai ir sava "otra puse" - ja Post belongsTo User, tad User hasMany Post. Abas puses jāapraksta atsevišķi, katra savā modelī.

phpclass Post extends Model
{
    public function user(): BelongsTo
    {
        return $this->belongsTo(User::class);
    }

    public function comments(): HasMany
    {
        return $this->hasMany(Comment::class);
    }
}

class User extends Authenticatable
{
    public function posts(): HasMany
    {
        return $this->hasMany(Post::class);
    }
}
php$post->user;              // -> User modelis (BEZ iekavām - "magic property")
$post->comments;          // -> Collection ar visiem komentāriem
$user->posts()->count();  // -> ar iekavām, jo šeit tālāk piebūvē vaicājumu (count/where/...)

belongsToMany

Daudzi-pret-daudziem (piem., raksti un birkas) - prasa starpposma tabulu, konvencijā nosauktu abu vārdu alfabētiskā secībā (post_tag).

hasOne

Kā hasMany, bet gaida tikai VIENU rezultātu (piem., User hasOne Profile).

N+1 problēma

Cikls pār 50 rakstiem, katram lasot $post->user, izpilda 51 vaicājumu. Skat. with()/load() zemāk - viens no biežākajiem veiktspējas kļūdu avotiem.

Post::with('user')->get() ielādē VISU rakstu autorus VIENĀ papildu vaicājumā (nevis pa vienam katram rakstam) - tas ir risinājums N+1 problēmai. $post->load('user') dara to pašu jau ielādētam, atsevišķam modelim.

Query Builder

Kad Eloquent modeļa metodes nepietiek (sarežģītāki filtri, agregācijas) - Query Builder ļauj sacerēt vaicājumu soli pa solim, ķēdes stilā, joprojām bez tiešas SQL rakstīšanas.

phpPost::where('published', true)
    ->where('created_at', '>=', now()->subDays(7))
    ->orderBy('created_at', 'desc')
    ->withCount('comments')
    ->paginate(10);

// orWhere, whereIn, whereBetween - tāpat ķēdē
Post::whereIn('id', [1, 2, 3])->get();

// Agregācijas bez visu rindu ielādēšanas atmiņā
Post::where('published', true)->count();
Post::max('views');

paginate(10) ne tikai ierobežo rezultātu skaitu - tā arī automātiski nolasa ?page= no URL un atgriež gatavu lapošanas metadatus (kopējais skaits, nākamā/iepriekšējā lapa), ko var tieši izvadīt Blade veidnē vai JSON API atbildē (skat. API Resources).

Seeders & Factories

Factory apraksta, kā ģenerēt VIENU reālistisku testa ierakstu. Seeder izmanto factory, lai piepildītu datubāzi ar daudziem ierakstiem uzreiz - abi der izstrādei un testiem, nevis reāliem lietotāja datiem.

php// database/factories/PostFactory.php
class PostFactory extends Factory
{
    public function definition(): array
    {
        return [
            'user_id' => User::factory(),
            'title' => $this->faker->sentence(),
            'body' => $this->faker->paragraphs(3, true),
            'published' => $this->faker->boolean(70), // 70% ticamība, ka true
        ];
    }

    // Nosaukts "state" - piemēro tikai vajadzīgo pārrakstījumu virs pamata definition()
    public function published(): static
    {
        return $this->state(fn () => ['published' => true]);
    }
}
php// Tinker vai seeder iekšā:
User::factory()->create();                          // 1 lietotājs
Post::factory()->count(20)->create();                // 20 raksti, katram SAVS jauns lietotājs
Post::factory()->for($user)->published()->create();  // 1 raksts KONKRĒTAM lietotājam, ar "published" state

Factories un seeders NEKAD nedrīkst palaist pret produkcijas datubāzi - tie ģenerē izdomātus (Faker) datus, kas sajauktos ar reāliem lietotāju ierakstiem. Der tikai lokālai izstrādei un CI testu videi.

Middleware

Middleware pārtver pieprasījumu PIRMS tas sasniedz controlleru - der piekļuves pārbaudēm, kas atkārtojas vairākos maršrutos (autentifikācija, abonementa statuss, API atslēgas pārbaude).

bashphp artisan make:middleware EnsureUserIsSubscribed
phpclass EnsureUserIsSubscribed
{
    public function handle(Request $request, Closure $next): Response
    {
        if (!$request->user() || !$request->user()->subscribed) {
            return response()->json(['message' => 'Nepieciešams aktīvs abonements.'], 403);
        }

        return $next($request); // laiž tālāk - uz nākamo middleware vai controlleru
    }
}

Reģistrē alias bootstrap/app.php failā, lai maršrutos varētu norādīt to ar īsu nosaukumu:

php->withMiddleware(function (Middleware $middleware): void {
    $middleware->alias([
        'subscribed' => \App\Http\Middleware\EnsureUserIsSubscribed::class,
    ]);
})
phpRoute::middleware('subscribed')->get('/premium', fn () => 'Premium saturs');

Ja handle() atgriež atbildi PIRMS $next($request) izsaukuma - pieprasījums apstājas tur, un controller vispār nekad neizpildās. Tieši tā šis piemērs nobloķē pieprasījumu ar 403, ja lietotājs nav abonējis (pārbaudīts reāli - atgriež precīzi šo statusu un ziņojumu).

Form Requests & validācija

Form Request ir sava klase validācijas noteikumiem - notur controlleru tīru no validācijas loģikas un ļauj to atkārtoti lietot.

bashphp artisan make:request StorePostRequest
phpclass StorePostRequest extends FormRequest
{
    public function authorize(): bool
    {
        return true; // vai pielāgota atļauju pārbaude, piem. $this->user()->can(...)
    }

    public function rules(): array
    {
        return [
            'title' => ['required', 'string', 'max:255'],
            'body' => ['required', 'string', 'min:10'],
            'published' => ['sometimes', 'boolean'],
        ];
    }
}

Controller metodē tips StorePostRequest $request vietā Request automātiski palaiž validāciju PIRMS metodes koda:

phppublic function store(StorePostRequest $request)
{
    // Šeit koda jau NEKAD nesasniedz, ja validācija neizietu -
    // Laravel pats atgriež 422 ar kļūdu sarakstu, pirms šī rinda paspēj izpildīties
    $post = $request->user()->posts()->create($request->validated());
}
json// Reāla 422 atbilde, ja "title" un "body" trūkst (pārbaudīts):
{
  "message": "The title field is required. (and 1 more error)",
  "errors": {
    "title": ["The title field is required."],
    "body": ["The body field is required."]
  }
}

$request->validated() atgriež TIKAI datus, kas aprakstīti rules() - ja pieprasījumā nāk papildu, neaprakstīts lauks (piem., mēģinājums uzspiest is_admin), tas šeit vienkārši netiks iekļauts, pat ja tas ir pieprasījuma "body" daļā.

Request & Response

Illuminate\Http\Request ietver visu par ienākošo pieprasījumu - ievades datus, faila augšupielādes, galvenes, autentificēto lietotāju.

php$request->input('title');          // viena vērtība no formas/JSON
$request->title;                    // tas pats, "magic property" veidā
$request->all();                     // viss kā masīvs
$request->only(['title', 'body']);   // tikai norādītie lauki
$request->has('title');            // vai lauks vispār eksistē
$request->user();                    // pieteikušais lietotājs (vai null)
$request->file('attēls');          // augšupielādēts fails

Atbildes (Response) var atgriezt vairākos veidos - Laravel pats izvēlas pareizo Content-Type:

phpreturn 'Vienkāršs teksts';                       // text/html
return view('posts.index', ['posts' => $posts]);   // Blade veidne
return response()->json(['ok' => true]);          // application/json
return response()->json(['error' => '...'], 404);  // ar pielāgotu statusa kodu
return redirect('/posts');                     // 302 pāradresācija
return redirect()->route('posts.index');         // pāradresācija pēc maršruta VĀRDA, ne URL

Sesijas & Flash dati

Sesija saglabā datus starp vairākiem pieprasījumiem no TĀ PAŠA apmeklētāja (parasti caur sīkdatni). Flash dati ir īpaši - pieejami TIKAI nākamajā pieprasījumā, tad automātiski pazūd - ideāli īslaicīgiem paziņojumiem pēc pāradresācijas.

php// Parasta sesija - paliek, kamēr pats neizdzēš vai sesija nebeidzas
session(['grozs_id' => 42]);
session('grozs_id');

// Flash - pieejams TIKAI vienu pieprasījumu uz priekšu
session()->flash('status', 'Saglabāts veiksmīgi!');
return redirect('/posts');

// Nākamajā lapā (piem., Blade veidnē pēc pāradresācijas):
@if (session('status'))
    <div class="alert">{{ session('status') }}</div>
@endif

Ļoti bieži lietots kopā ar validāciju - ja forma neizietu, lietotājs redz atpakaļ savus ievadītos datus, nevis tukšu formu:

phpreturn redirect('/posts/create')->withInput(); // saglabā visu, ko lietotājs bija ierakstījis

// Blade veidnē - aizpilda lauku ar VECO vērtību, ja tāda ir (pēc neveiksmīgas validācijas)
<input name="email" value="{{ old('email') }}">

Ja validācija rules() Form Request klasē (skat. augstāk) neizietu parastā (nevis API) maršrutā, Laravel AUTOMĀTISKI izdara tieši šo - pāradresē atpakaļ ar withInput() un flash kļūdām, bez papildu koda rakstīšanas.

Artisan CLI

Artisan ir Laravel iebūvētais komandrindas rīks - php artisan list parāda visas pieejamās komandas. Pielāgotas komandas noder atkārtotiem administratīviem uzdevumiem.

bashphp artisan make:command PublishScheduledPosts

bashphp artisan app:publish-scheduled-posts

Laravel 13 make:command pēc noklusējuma ģenerē tieši šo, atribūtu balstīto sintaksi (#[Signature]/#[Description]) - vecāki tutoriāli rādīs protected $signature/protected $description īpašības. Abi veidi strādā, bet atribūtu forma tagad ir jaunā komanda ģenerēta pēc noklusējuma.

Autentifikācija

Laravel pats nesatur gatavu pieteikšanās/reģistrācijas UI - to pievieno kā oficiālu, atsevišķu paketi, atkarībā no projekta vajadzības.

Laravel Breeze

Minimāla, "redzi visu kodu" pieteikšanās/reģistrācijas/paroles atjaunošanas sistēma - der, ja gribi pats kontrolēt un mainīt UI. Uzstāda ar laravel new --breeze vai composer require laravel/breeze + artisan breeze:install.

Laravel Sanctum

Vienkārši API tokeni (nevis pilna OAuth sistēma) - der, kad frontend (piem., React lietotne) sazinās ar Laravel backend caur API, nevis Blade veidnēm.

Laravel Jetstream

Pilnīgāks risinājums - komandas, profila pārvaldība, divfaktoru autentifikācija - der lielākiem, no paša sākuma "produktu" tipa projektiem.

php// Pēc autentifikācijas pakotnes uzstādīšanas - pārbaude jebkurā vietā:
if (Auth::check()) { ... }        // vai auth()->check()
$lietotajs = Auth::user();      // vai auth()->user()

// Maršrutā - piespiež pieteikšanos, ja lietotājs nav autentificēts
Route::middleware('auth')->group(function () {
    Route::get('/dashboard', DashboardController::class);
});

Nekad neveido pieteikšanās/paroles hash loģiku pašrocīgi "vienkāršības labad" - Breeze/Sanctum/Jetstream jau pareizi apstrādā paroļu hash (bcrypt), rate limiting pret bruteforce un CSRF aizsardzību. Pašrocīgi rakstīta versija gandrīz vienmēr izlaiž kādu no šiem.

API Resources

API Resource kontrolē, kā Eloquent modelis pārvēršas par JSON - atdala datubāzes kolonnu nosaukumus no tā, ko tiešām grib rādīt API patērētājam (frontend, mobilā app).

bashphp artisan make:resource PostResource
phpclass PostResource extends JsonResource
{
    public function toArray(Request $request): array
    {
        return [
            'id' => $this->id,
            'title' => $this->title,
            'body' => $this->body,
            'published' => $this->published,
            // Rāda "author" TIKAI, ja user attiecība jau ielādēta ar with()/load() -
            // pretējā gadījumā klusē izlaiž lauku, nevis izmet papildu vaicājumu (N+1)
            'author' => $this->whenLoaded('user', fn () => $this->user->name),
            'comments_count' => $this->whenCounted('comments'),
            'created_at' => $this->created_at->toIso8601String(),
        ];
    }
}
phpreturn new PostResource($post);                 // viens ieraksts
return PostResource::collection($posts);       // vairāki, ar automātisku lapošanu, ja $posts nāk no paginate()

Bez Resource, atgriežot modeli tieši (return $post;), API atklāj VISAS datubāzes kolonnas, ieskaitot iekšējas (piem., nākotnē pievienotu internal_notes). Resource ir apzināts "atļauto sarakstu" filtrs - jaunas kolonnas datubāzē automātiski NEparādās API, kamēr apzināti nepievieno tās toArray().

Events & Listeners

Event/Listener atdala "kas notika" no "ko tāpēc darīt" - noder, kad viena darbība (raksta publicēšana) izraisa VAIRĀKAS neatkarīgas sekas (e-pasts, žurnāls, statistika), kuras nevajag sabāzt vienā controller metodē.

bashphp artisan make:event PostPublished
php artisan make:listener SendPostPublishedNotification --event=PostPublished
phpclass PostPublished
{
    use Dispatchable, SerializesModels;

    public function __construct(public Post $post) {}
}

class SendPostPublishedNotification implements ShouldQueue
{
    public function handle(PostPublished $event): void
    {
        Log::info("Jauns raksts publicēts: {$event->post->title}");
    }
}
phpevent(new PostPublished($post));

Laravel 11+ AUTOMĀTISKI atklāj listeneru savienojumus ar eventiem, balstoties uz to handle() metodes tipa deklarāciju (šeit PostPublished $event) - nekas nav manuāli jāreģistrē EventServiceProvider failā, jo tāda faila projektā pēc noklusējuma vairs nav (pārbaudīts: event() izsaukums uzreiz izpilda listeneru bez papildu konfigurācijas).

Jobs & Queues

Job ir viens, atkārtoti izpildāms uzdevums, ko var nolikt rindā (queue) - tas izpildās FONĀ, atsevišķi no lietotāja pieprasījuma, lai lēns darbs (e-pasta sūtīšana, PDF ģenerēšana) nepiespiestu lietotāju gaidīt.

bashphp artisan make:job SendWeeklyDigest
phpclass SendWeeklyDigest implements ShouldQueue
{
    use Queueable;

    public function __construct(public User $user) {}

    public function handle(): void
    {
        $postsCount = $this->user->posts()->count();
        Log::info("Iknedēļas kopsavilkums lietotājam {$this->user->name}: {$postsCount} raksti");
    }
}
phpSendWeeklyDigest::dispatch($user);                    // noliek rindā, atgriežas UZREIZ
SendWeeklyDigest::dispatch($user)->delay(now()->addMinutes(10)); // izpildīsies pēc 10 min
bash# Procesa, kas tiešām izpilda rindā gaidošos darbus - jāpalaiž atsevišķi (produkcijā ar Supervisor)
php artisan queue:work

Pēc noklusējuma jauns Laravel projekts izmanto QUEUE_CONNECTION=database vai sync (.env failā) - sync izpilda job'us UZREIZ, tajā pašā pieprasījumā (labi lokālai izstrādei/testiem, bet zaudē visu queue jēgu). Produkcijā vajag īstu queue driveri (database, Redis) UN palaistu queue:work procesu - bez tā rindā noliktie darbi vienkārši sakrājas un nekad neizpildās.

Task Scheduling

Laravel iebūvētais plānotājs aizstāj vairāku atsevišķu cron ierakstu rakstīšanu serverī - visi plānotie uzdevumi definēti VIENĀ vietā, kodā, versiju kontrolē.

php// routes/console.php
use Illuminate\Support\Facades\Schedule;

Schedule::command('app:publish-scheduled-posts')->weeklyOn(1, '08:00'); // katru pirmdienu 8:00
Schedule::command('model:prune')->daily();

Serverim jāiestata TIKAI VIENS reāls cron ieraksts, kas palaiž Laravel plānotāju katru minūti - tas pats izlemj, kurš no augstāk aprakstītajiem uzdevumiem tobrīd tiešām jāizpilda:

bash# Servera crontab (viens ieraksts der VISIEM Laravel plānotajiem uzdevumiem)
* * * * * cd /ceļš/uz/projektu && php artisan schedule:run >> /dev/null 2>&1
bash# Pārbauda, kas ieplānots un kad nākamā izpilde (pārbaudīts - rāda pareizu cron izteiksmi)
php artisan schedule:list

Šis ir pilnībā atšķirīgs mehānisms no WordPress WP-Cron, kas darbojas TIKAI, kad kāds apmeklē vietni. Laravel plānotājs balstās uz reālu servera cron ierakstu, tāpēc uzdevumi izpildās precīzi ieplānotajā laikā, pat ja vietni nekas neapmeklē.

.env fails glabā videi specifiskus iestatījumus (datubāzes paroli, API atslēgas) - ĀRPUS Git repozitorija (skat. arī .env PHP kategorijā vispārīgam PHP skaidrojumam).

text# .env

APP_DEBUG=false
DB_CONNECTION=mysql

// Pārējā kodā vienmēr lasi caur config(), ne env() tieši:

Testēšana (PHPUnit)

Jauns Laravel projekts pēc noklusējuma nāk ar PHPUnit uzstādītu un konfigurētu - testi dalās Feature (pilna pieprasījuma plūsma, ar HTTP un datubāzi) un Unit (izolēta klase/metode, bez Laravel konteksta).

bashphp artisan make:test PostApiTest
phpclass PostApiTest extends TestCase
{
    use RefreshDatabase; // katram testam TĪRA, jauna testa datubāze

    public function test_guest_can_list_published_posts(): void
    {
        Post::factory()->count(3)->published()->create();

        $response = $this->getJson('/api/posts');

        $response->assertOk()->assertJsonCount(3, 'data');
    }

    public function test_creating_post_requires_title(): void
    {
        $user = User::factory()->create();

        $response = $this->actingAs($user)->postJson('/api/posts', [
            'body' => 'Saturs bez virsraksta.',
        ]);

        $response->assertStatus(422)->assertJsonValidationErrors('title');
    }
}
bashphp artisan test --filter=PostApiTest
# → PASS  Tests\Feature\PostApiTest (2 testi, 5 apgalvojumi) - pārbaudīts reāli

RefreshDatabase pirms KATRA testa migrē tīru datubāzi no nulles - testi nekad neietekmē cits citu ar palikušiem datiem no iepriekšējā testa, pat ja testi izpildās neparedzamā secībā.

Daudzi Laravel projekti izmanto Pest - alternatīvu, kodolīgāku sintaksi virs tā paša PHPUnit dzinēja (nevis pilnīgi cita testēšanas sistēma). Šeit izmantota klasiskā PHPUnit sintakse, jo tā ir tas, ko composer create-project laravel/laravel uzstāda pēc noklusējuma.

Kļūdu apstrāde & logging

Pielāgotas izņēmumu klases ļauj katrai kļūdai piešķirt savu HTTP atbildi un žurnalēšanas uzvedību - bez if/else virknes controlleros.

bashphp artisan make:exception PostLimitExceededException
phpclass PostLimitExceededException extends Exception
{
    public function render(): JsonResponse
    {
        return response()->json(['message' => 'Sasniegts maksimālais rakstu skaits.'], 429);
    }
}

Papildu žurnalēšana (bez atbildes maiņas) reģistrē bootstrap/app.php:

php->withExceptions(function (Exceptions $exceptions): void {
    $exceptions->report(function (PostLimitExceededException $e) {
        Log::warning('Rakstu limits pārsniegts: '.$e->getMessage());
    });
})

Kad kods to izmet, atbilde un žurnāla ieraksts notiek automātiski (pārbaudīts - atgriež tieši šo statusu un ziņojumu):

phpthrow new PostLimitExceededException('limit sasniegts');
// → HTTP 429, {"message": "Sasniegts maksimālais rakstu skaits."}
// → storage/logs/laravel.log: "Rakstu limits pārsniegts: limit sasniegts"

Jauns projekts pēc noklusējuma jau satur $exceptions->shouldRenderJsonWhen(...) - tas nosaka, vai kļūdas jārāda kā JSON (API pieprasījumiem) vai kā HTML kļūdas lapa (parastiem pārlūka pieprasījumiem). Parasti to nevajag mainīt, ja vien projektam nav neparasta API/web sadalījuma.

Deploy pamatprakse

Laravel projekta izvietošana atšķiras no WordPress (skat. WordPress problēmas salīdzinājumam) - nav vienkārši failu kopēšana, jo projekts prasa Composer atkarības, konfigurācijas kešu un pareizas mapes tiesības.

Composer produkcijas režīmā

composer install --optimize-autoloader --no-dev - izlaiž izstrādes rīkus (PHPUnit, Pail) un paātrina klašu ielādi.

Kešu apkopošana

artisan config:cache, route:cache, view:cache - katru reizi PĒC koda izvietošanas, ne tikai reizi.

Migrācijas

artisan migrate --force - --force nepieciešams, jo Laravel pēc noklusējuma atsakās palaist migrācijas APP_ENV=production bez apstiprinājuma.

Document root

Servera konfigurācijai jārāda uz public/ apakšmapi, NEVIS projekta sakni - pretējā gadījumā .env un pārējais projekta kods kļūst tieši lejupielādējams.

bash# Tipiska deploy soļu secība pēc koda izvietošanas serverī
composer install --optimize-autoloader --no-dev
php artisan migrate --force
php artisan config:cache
php artisan route:cache
php artisan view:cache
php artisan queue:restart  # liek queue:work procesiem pārlasīt JAUNO kodu

queue:restart ir viegli aizmirst - jau strādājošie queue:work procesi PALIEK ar VECO koda versiju atmiņā, kamēr netiek piespiesti pārstartēties. Bez šī soļa nesen izvietotas izmaiņas jobos var klusi nestrādāt, kaut arī pārējais kods jau atjaunināts.
